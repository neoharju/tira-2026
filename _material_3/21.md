# 21. Text Search

Weeks 18–20 were about road networks. This week we build the data structure behind every search box: the search of Wikipedia, the code search of GitHub, the log search of a server farm, and the shop that finds "red running shoes" among a million products. The question is always the same. Given a few words, which of millions of documents contain them, and which of those are the best?

The answer is the **inverted index**. For every word it stores the sorted list of the documents that contain the word. A query then becomes work on sorted lists of integers:

* An **AND query** intersects the lists of its words. We make the intersection fast with _galloping_ when one list is short, and with **SIMD** when both are long.
* A **ranked query** gives every document a score with the **BM25** formula and returns the best $$k$$ documents, using a heap. **MaxScore** skips the documents that cannot get into the top $$k$$.
* **Compression** with gaps and _varints_ makes the lists three times smaller, and **Roaring bitmaps** store dense lists as bits.
* Building the index is **parallel**: every thread indexes its own _shard_ of the documents.

You will meet the CSR arrays of week 18 again: an inverted index is a graph from words to documents.

## From text to tokens

The template cannot ship Wikipedia, so it generates documents. They look like this:

```console
Deba ba gibo bi nada fo be dikiba ba dubi tapodo ba? Nuba todube sibo suvebi
sebuda gi vomibo li. Di, figi vefebe, ku bukebe me badi buda vubube rufe luba.
```

The words are nonsense, but their statistics are those of real text. The words of a language follow **Zipf's law**: the $$r$$-th most common word occurs about $$1/r$$ times as often as the most common one. In English, "the" is about 7 % of all words, "of" about half of that, and most words are rare. Our 20,000 generated documents have 4.4 million words, and the same law holds:

{: .grid-head }
| Word | ba | be | bi | bo | bu |
| --- | --- | --- | --- | --- | --- |
| Share of all words | 8.6 % | 4.3 % | 2.9 % | 2.2 % | 1.7 % |
| Documents that contain it | 19,976 | 19,770 | 19,376 | 18,893 | 18,366 |

The first step of indexing is **tokenization**: cutting the text into words. Our rule is simple: a token is a longest run of letters and digits, in lower case, so "Deba," and "deba" are the same token. Real search engines do more: they handle all of Unicode, they _stem_ words ("running" and "runs" become "run"), and they may drop very common _stop words_ such as "the".

```cpp
using DocId = std::uint32_t;

// Calls f(token) for every token of the text, in lower case. The token is a
// string_view into `buffer`.

```

## The inverted index

The index at the end of a book lists, for every important word, the pages where it appears. An inverted index does the same for documents. A **term** is a distinct token, and its **posting list** holds the documents that contain it, in increasing order, together with how many times it occurs there:

```console
ba:   (0, 24) (1, 18) (2, 23) (3, 26) (4, 30) ...   19,976 postings
gibo: (0, 1) (3, 1) (16, 1) (24, 1) (30, 1) ...      1,337 postings
```

We store all posting lists in the CSR form of week 18: one array for all document ids, one for all frequencies, and an array `offset` that says where the list of every term begins.

{: .code-title }
week21/index.hpp (shortened)

```cpp
struct Index {
    std::vector<std::string> terms;         // the text of every term
    std::vector<std::uint32_t> offset;      // terms.size() + 1 values
    std::vector<DocId> docs;                // increasing within every term
    std::vector<std::uint32_t> freqs;       // how many times the term occurs
    std::vector<std::uint32_t> doc_length;  // the tokens of every document

    std::span<const DocId> postings(TermId t) const {
        return {docs.data() + offset[t], offset[t + 1] - offset[t]};
    }
};
```

Building the index has two parts. First, every token gets a term id from a **dictionary**: a hash map from the text of a term to its id. New terms get the next free id, so the ids follow the order in which the terms first appear. The postings are collected in document order. Second, a counting sort by term turns them into the CSR arrays, exactly like the arcs of a graph in week 18. The sort is stable, so the documents of every term stay in increasing order.

{% include viz.html id="inverted-index" alt="Three short documents are cut into tokens. Each new token gets a term id in the dictionary, and its postings (document, count) are collected. A counting sort by term then fills the arrays offset, docs and freqs." %}

One detail of modern C++ makes the dictionary much faster. The tokens are `string_view`s, but the map stores `std::string`s, and normally `find` would need a `std::string` to search for, which means a copy of every token. A hash map with a *transparent* hash and `std::equal_to<>` can search with the `string_view` directly (C++20):

```cpp
struct Hash {
    using is_transparent = void;  // find() may take a string_view
    std::size_t operator()(std::string_view s) const noexcept {
        return std::hash<std::string_view>{}(s);
    }
};
std::unordered_map<std::string, TermId, Hash, std::equal_to<>> ids;

if (auto it = ids.find(token); it != ids.end()) {  // no std::string is made
    // ...
}
```

The template starts with a version that uses `std::map<std::string, TermId>`: a balanced tree that compares strings on every level, with a new `std::string` for every token and a separate vector for every term. On our test machine (GCC 16) it indexed the 20,000 documents in 1.76 seconds. With the hash map and the counting sort it took 0.53 seconds, 120 ns per token. Of that, cutting the text into tokens took about a fifth, the hash map about a third, and collecting and sorting the postings the rest.

## AND queries

The query "ka AND lo" asks for the documents that contain both words: the **intersection** of two posting lists. Both lists are sorted, so a merge with two pointers works. Look at the smaller of the two current values and move its pointer; when they are equal, output the value and move both:

```cpp
std::size_t i{}, j{};

while (i < a.size() && j < b.size()) {
    if (a[i] < b[j])
        ++i;
    else if (b[j] < a[i])
        ++j;
    else {
        out.push_back(a[i]);
        ++i;
        ++j;
    }
}
```

This takes $$O(m + n)$$ time for lists of $$m$$ and $$n$$ values. A query with more words intersects the lists one by one. Start with the **shortest list**: the result can only get smaller, so every later step works on a short list.

## Galloping: when one list is short

Often one word is rare and the other is common: 50 documents against 20,000. The merge still walks through all 20,000 values of the long list. Searching for each of the 50 values in the long list with binary search would take only $$50 \cdot \log_2 20{,}000 \approx 700$$ steps.

**Galloping** (also called exponential search) is even better, because the values that we search for are increasing. Each search starts where the previous one ended. It first jumps 1, 2, 4, 8, … positions forward until it passes the value, and then it does a binary search in the last jump:

```cpp
std::size_t lo{};  // b[0 .. lo) is smaller than the value we look for

for (DocId x : a) {
    std::size_t hi = lo, step = 1;

    while (hi < b.size() && b[hi] < x) {  // jump 1, 2, 4, 8, ... forward
        lo = hi + 1;
        hi += step;
        step *= 2;
    }
    lo = std::lower_bound(b.begin() + lo, b.begin() + std::min(hi, b.size()), x) - b.begin();
    if (lo < b.size() && b[lo] == x)
        out.push_back(x);
}
```

If the values of `a` are spread over `b` with gaps of $$g = n/m$$, every search jumps about $$\log_2 g$$ times, and the total is $$O(m \log(n/m))$$ instead of $$O(m + n)$$. When the lists have about the same length, the jumps do not pay off and the merge is faster. Good implementations choose: they gallop only when one list is many times longer (the reference solution uses 32 times).

{% include viz.html id="intersect-gallop" alt="Two sorted lists: a short list of 4 values and a long list of 40 values. The merge moves through the long list one value at a time; galloping jumps 1, 2, 4 and 8 positions and then searches inside the last jump, with far fewer comparisons." %}

On our test machine, a list of 1,024 values against a list of a million took 0.71 ms with `std::set_intersection` and 0.10 ms with galloping.

## SIMD: many comparisons at once

When both lists are long, the merge has another problem: its `if` goes left or right at random, so the CPU guesses wrong about half of the time (week 17). A **branchless** merge computes both pointer updates as numbers instead:

```cpp
const DocId x = a[i], y = b[j];
out[k] = x;    // write always, keep it only if x == y
k += x == y;
i += x <= y;
j += y <= x;
```

For two lists of a million values, `std::set_intersection` took 11.9 ms and the branchless loop 5.4 ms. It still compares one pair of values at a time. With SIMD we compare a **block** of values from `a` with a block from `b` at once.

Take 4 values of `a` and 4 values of `b` in two SSE registers. One `_mm_cmpeq_epi32` compares the lanes pairwise. Rotating the register of `b` by one lane, three times, brings every value of `b` to every lane, so four comparisons check all 16 pairs. An OR of the four results has all ones in lane $$i$$ if `a[i]` is somewhere in the block of `b`, and `_mm_movemask_ps` turns that into a 4-bit number:

```cpp
const __m128i va = _mm_loadu_si128(reinterpret_cast<const __m128i*>(a + i));
__m128i vb = _mm_loadu_si128(reinterpret_cast<const __m128i*>(b + j));
__m128i eq = _mm_cmpeq_epi32(va, vb);
for (int r = 1; r < 4; ++r) {
    vb = _mm_shuffle_epi32(vb, _MM_SHUFFLE(0, 3, 2, 1));  // rotate by one lane
    eq = _mm_or_si128(eq, _mm_cmpeq_epi32(va, vb));
}
const int mask = _mm_movemask_ps(_mm_castsi128_ps(eq));  // bit k: a[i + k] matched
```

Now the matching values must be written to the output, packed together. A table of $$2^4 = 16$$ shuffles, one for every mask, moves the matching lanes to the front, and one store writes all 4 lanes; the output position then moves by `std::popcount(mask)`. Finally, the block whose last value is smaller is finished: move it forward by 4 (both blocks if their last values are equal).

{% include viz.html id="simd-intersect" alt="Eight values of list a and eight of list b in AVX2 registers. The register of b is rotated seven times, and each comparison marks the lanes of a whose value is in b. The marked lanes form an 8-bit mask; a shuffle from a table packs the matches to the front and they are stored." %}

The store writes all lanes, also the ones that did not match, past the end of the result. That is why the output buffer of task 6 has room for 8 more values. In AVX2, a register holds 8 values: 8 rotations (`_mm256_permutevar8x32_epi32`) check 64 pairs, the mask has 8 bits and the table has 256 entries. With AVX2, the two lists of a million values took 1.2–1.8 ms: 3 to 4.5 times faster than the branchless loop and 6 to 8 times faster than `std::set_intersection`. For a short list against a long one, galloping remains the best.

## Ranking with BM25

An AND query is often too strict, and it does not tell which documents are the best. Search engines **rank**: every document that contains at least one query word gets a score, and the user sees the best ones first. Two ideas give a good score:

* A word that occurs many times in a document says more about it (*term frequency*). But the tenth occurrence adds less than the first.
* A rare word says more than a common one (*inverse document frequency*). A document that contains "gibo" is special; one that contains "ba" is not.

The **BM25** formula, from the 1990s, combines them and is still the standard first stage of search engines (Lucene, and so Elasticsearch, OpenSearch and Solr, use it by default). The score of document $$d$$ for query $$Q$$ is

$$\text{score}(d) = \sum_{t \in Q} \text{idf}(t) \cdot \frac{f \cdot (k_1 + 1)}{f + k_1 \cdot \left(1 - b + b \cdot \frac{\text{len}(d)}{\text{avg}}\right)}, \qquad \text{idf}(t) = \ln\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right),$$

where $$f$$ is how many times $$t$$ occurs in $$d$$, $$N$$ is the number of documents, $$n_t$$ the number of documents that contain $$t$$, and $$\text{avg}$$ the average length of a document. The usual constants are $$k_1 = 1.2$$ and $$b = 0.75$$.

In our collection of 20,000 documents, a term that occurs in 200 documents has $$\text{idf} = 4.60$$, and a term that occurs in half of them only $$0.69$$. For a document of average length, the second factor is $$1.0$$ for $$f = 1$$, $$1.375$$ for $$f = 2$$ and $$1.77$$ for $$f = 5$$, and it never reaches $$k_1 + 1 = 2.2$$: this is the **saturation** of the term frequency. A long document is a little less important per occurrence, because it has more words anyway; $$b$$ says how much less.

{% include viz.html id="bm25-curve" alt="An interactive chart of the BM25 term factor as a function of the term frequency f, for a short, an average and a long document. Sliders change k1 and b: with a larger k1 the curves rise longer before they flatten, and with b = 0 the length of the document does not matter." %}

We make one change to the formula. We multiply each term's contribution by 1000, round it to an integer, and call it the **impact** of the posting (at least 1). The score of a document is the sum of its impacts. Sums of integers do not depend on the order of the additions, so every correct method gives exactly the same scores and the same top $$k$$, which the tests can check. Search engines that precompute the impacts round them in the same way, often to 8 bits.

{: .code-title }
week21/index.hpp (shortened)

```cpp
struct Scores {
    std::vector<std::uint32_t> impact;      // one per posting, like Index::docs
    std::vector<std::uint32_t> max_impact;  // the largest impact of every term
};
Scores bm25_scores(const Index& index);

struct Hit {
    DocId doc;
    std::uint32_t score;
};
// a is better than b: a larger score, or the same score and a smaller document
constexpr bool better(const Hit& a, const Hit& b);
```

## The best k documents

The simplest way to compute all scores is **term at a time**: an array with one accumulator per document, and for every query term, one pass over its posting list that adds the impacts to the accumulators. The arrays are read in order, so this is fast: on our machine about 4 ns per posting.

Then we need the $$k$$ best documents, for example $$k = 10$$. Sorting all scored documents would take $$O(n \log n)$$ time. A **heap of size $$k$$** is better: it holds the best $$k$$ documents so far, with the *worst* of them on top. A new document goes in only if it is better than the top, which is then removed:

```cpp
auto worse_on_top = [](const Hit& a, const Hit& b) { return better(a, b); };
std::priority_queue<Hit, std::vector<Hit>, decltype(worse_on_top)> heap(worse_on_top);
for (DocId d : touched) {
    const Hit h{d, sum[d]};

    if (heap.size() < k)
        heap.push(h);
    else if (better(h, heap.top())) {
        heap.pop();
        heap.push(h);
    }
}
```

This takes $$O(n \log k)$$ time, and most documents are rejected with one comparison against the top.

## MaxScore: skip what cannot win

Term at a time reads every posting of every query term, also of very common terms with long lists. But once we have $$k$$ documents, the score of the $$k$$-th best one is a **threshold** $$\theta$$: a new document must score more than $$\theta$$ to get in. Every term $$t$$ has a largest impact $$\text{max}(t)$$, stored in the index. A document that contains only terms whose largest impacts add up to at most $$\theta$$ cannot get in, however many of those terms it has.

**MaxScore** (Turtle and Flood, 1995) uses this. It sorts the query terms by their largest impact. The first terms, whose largest impacts add up to at most $$\theta$$, are **non-essential**: a document that has only them is hopeless. Only the lists of the other, **essential** terms give candidate documents. The algorithm works **document at a time**:

1. The next candidate is the smallest document in the essential lists. Add up its essential impacts.
2. Go through the non-essential terms, the largest first. If the score plus the largest impacts of the remaining terms is at most $$\theta$$, stop: the candidate cannot get in. Otherwise search for the candidate in the term's list with galloping and add its impact.
3. If the score is more than $$\theta$$, put the candidate in the heap. When $$\theta$$ grows, more terms become non-essential.

{% include viz.html id="maxscore" alt="Three posting lists with impacts, sorted by their largest impact. As the heap of the best two documents fills, the threshold rises, and the term with the smallest largest impact becomes non-essential: its list is no longer scanned, only searched for the candidates of the other lists." %}

The common terms, which have long lists but small impacts, become non-essential first, and their lists are only searched. On our 20,000 documents and 2000 random queries, MaxScore took only 26 % of the postings as candidates. But it was not faster. A candidate of MaxScore costs about four times as much as a posting of term at a time, with its cursors, comparisons and searches, and the 4 ns of term at a time are hard to beat. The pruning wins when the lists are long. With 100,000 documents, MaxScore took 14 % of the postings as candidates and was 1.5 times faster, and the gain grows with the collection. Lucene uses MaxScore and a newer variant, block-max WAND, for collections of billions of documents.

## Compressing posting lists

A document id takes 4 bytes, and our 3.2 million postings take 12.7 MB. But a posting list is increasing, so we can store the **gaps** between consecutive ids instead: (75, 231, 302) becomes (75, 156, 71). The lists of common terms have small gaps, and small numbers need fewer bits.

**Varint** coding (also called LEB128) stores a number in 1–5 bytes: 7 bits per byte, the lowest bits first, and the highest bit of a byte says whether another byte follows. Numbers below 128 take one byte, below 16,384 two bytes, and so on. For example, 300 is 100101100 in binary; its low 7 bits 0101100 go into the first byte with the high bit set, and the remaining bits 10 into the second byte: `0xAC 0x02`.

```cpp
while (x >= 128) {
    out.push_back(static_cast<std::uint8_t>(x | 128));  // 7 bits, "more follows"
    x >>= 7;
}
out.push_back(static_cast<std::uint8_t>(x));            // the last byte
```

With gaps and varints, our index takes 1.32 bytes per posting instead of 4, and 68 % of the gaps fit in one byte. Decoding is a short loop with a branch that is almost always predicted right; it took about 3 ns per posting.

{% include viz.html id="varint" alt="Doc ids are turned into gaps and the gaps into varint bytes, with the continuation bit of every byte shown. Below, Stream VByte stores the lengths of four numbers in one control byte and the data bytes separately, so that one shuffle moves the bytes of four numbers into four 32-bit lanes." %}

A varint decoder handles one byte at a time, and its branch depends on the data. **Stream VByte** (Lemire, Kurz and Rupp, 2018) stores the *lengths* apart from the data: one control byte holds the lengths (1–4 bytes) of four numbers, 2 bits each. The control byte selects one of 256 precomputed shuffle masks, and a single `pshufb` (`_mm_shuffle_epi8`) moves the data bytes of four numbers into the four 32-bit lanes of a register. There is no branch per number, and a prefix sum in the register turns the gaps back into ids. We implement it in week 40.

## Roaring bitmaps

For a common term, a **bitmap** with one bit per document is smaller than a list: the list of "ba" with 19,976 of 20,000 documents takes 80 KB as 4-byte ids but only 2.5 KB as bits. A bitmap is also fast to intersect: an AND of two 64-bit words intersects 64 documents at once. But for a rare term a bitmap is huge and empty. **Roaring bitmaps** (Chambi, Lemire, Kaser and Godin, 2016) choose the best form for every part of a set.

A Roaring bitmap splits the 32-bit values by their high 16 bits into chunks of 65,536 values. Every chunk is a **container** of the low 16 bits, of one of three kinds:

* **array**: at most 4096 values, sorted, 2 bytes each;
* **bitmap**: 65,536 bits in 1024 words of 64 bits, always 8 KB;
* **run**: pairs (start, length) for runs of consecutive values, 4 bytes per run.

At 4096 values an array takes 8 KB, as much as a bitmap; with more values the bitmap is smaller. A run container wins when the values come in long runs, as ids of related documents often do.

{% include viz.html id="roaring" alt="A set of 32-bit values divided into chunks by the high 16 bits. A slider changes how dense the values are and another how much they cluster into runs; every chunk shows the size of an array, a bitmap and a run container, and the smallest one is chosen." %}

Two Roaring bitmaps are intersected chunk by chunk, like a merge of their keys, and two containers by their kinds. Two bitmaps: AND the 1024 words and count the ones with `std::popcount`; if at most 4096 remain, convert to an array. An array and a bitmap: test the bit of every array value. Two arrays: merge or gallop, or use SIMD as above. Runs can be expanded into a bitmap a word at a time.

```cpp
std::uint32_t count{};

for (std::size_t i = 0; i < 1024; ++i) {
    w[i] = a[i] & b[i];                 // 64 values at once
    count += std::popcount(w[i]);
}
```

We measured four pairs of sets over $$2^{24}$$ values, against the sorted vectors of the same sets:

{: .grid-head }
| Sets | Memory of the first set | Intersection |
| --- | --- | --- |
| dense 40 % and 25 % (bitmaps) | 26.8 MB → 2.1 MB | 67 ms → 0.58 ms |
| dense 25 % and sparse 0.5 % | 16.8 MB → 2.1 MB | 3.0 ms → 0.46 ms |
| runs of about 2000 values | 16.8 MB → 0.01 MB | 8.8 ms → 0.75 ms |
| sparse 1 % and 2 % (arrays) | 0.7 MB → 0.34 MB | 2.0 ms → 1.5 ms |

Roaring bitmaps are used in Lucene, Apache Spark, Druid, ClickHouse, Pinot and many other systems, for example to store which documents match a filter.

## Parallel: one shard per thread

Indexing a collection is work for many cores. The simplest way to split it is by documents: every thread indexes its own **shard**, a range of consecutive documents, with its own dictionary and its own posting lists. No thread touches the data of another, so there are no data races. Then the shards are merged:

1. **Dictionaries**: go through the shards in order and give every new term the next global id. Because the shards are in document order, a term gets the same id as it would get from one thread.
2. **Offsets**: count the postings of every term over all shards and compute the offsets with a prefix sum. For every term and shard, this also gives the position where the shard's postings of the term go.
3. **Copy**: every thread copies its postings to their positions. The positions of different threads do not overlap, and a term's postings come shard by shard, so its documents stay in increasing order without sorting.

{: .code-title }
The structure of task 8

```cpp
#pragma omp parallel
{
    // 1. index the documents of this thread's shard (local term ids)
#pragma omp barrier
#pragma omp single
    {
        // 2. merge the dictionaries in shard order, count, prefix sums
    }   // the implicit barrier: everybody waits for the positions
    // 3. copy this shard's postings to their positions
}
```

Step 2 runs on one thread, but it only touches the dictionaries, which are much smaller than the text. With 4 threads, our index was built 2.5 to 3 times faster.

Search engines split by documents in the same way. An Elasticsearch or OpenSearch index consists of shards, and every shard is a complete Lucene index. A query goes to all shards in parallel, every shard returns its own top $$k$$, and the results are merged. Inside a shard, Lucene writes new documents into small *segments* and merges them into bigger ones in the background, just like step 3.

One kind of model, *learned sparse retrieval* (for example SPLADE), turns a document into a list of terms with weights: the network decides that a text about "cars" should also match "vehicle", with some weight. The weights are stored as impacts in an ordinary inverted index, and the queries run with the same algorithms as in this chapter: posting lists, top $$k$$ heaps and dynamic pruning such as MaxScore. The other kind, dense vector search, is the topic of weeks 23 and 24.

Task 5: Roaring intersection (1 point)
<div class="note" markdown="1">

Write `intersect` for two Roaring bitmaps in `task5_roaring.cpp` (see `roaring.hpp`). In the result, a container with at most 4096 values is an array, a larger one is a bitmap, and there are no empty containers and no run containers. The tests check these rules and compare the values with `std::set_intersection`, for all pairs of container kinds. Goal: 8 times faster than intersecting the same sets as sorted vectors. Expand a run a word at a time, not a bit at a time.

</div>

Task 6: SIMD intersection (1 point)
<div class="note" markdown="1">

Automatic vectorization is turned off for this file. The tests use short lists of every length, lists with many and with few common values, and values of $$2^{31}$$ or more. Goal: 2.5 times faster than the branchless scalar loop, for two lists of a million values.

## Code to read

* Apache Lucene, the library inside Elasticsearch, OpenSearch and Solr: the postings formats in `org.apache.lucene.codecs` (blocks of 128 documents with packed integers and skip data), and `MaxScoreBulkScorer` and `WANDScorer` in `org.apache.lucene.search`.
* CRoaring, the C library of Roaring bitmaps: `array_util.c` has SIMD intersections of arrays of 16-bit values. Daniel Lemire et al.: _Roaring Bitmaps: Implementation of an Optimized Software Library_ (Software: Practice and Experience, 2018).

* Daniel Lemire, Nathan Kurz and Christoph Rupp: _Stream VByte: Faster Byte-Oriented Integer Compression_ (Information Processing Letters, 2018).

* Howard Turtle and James Flood: _Query Evaluation: Strategies and Optimizations_ (1995), the MaxScore paper; Stephen Robertson and Hugo Zaragoza: _The Probabilistic Relevance Framework: BM25 and Beyond_ (2009).
