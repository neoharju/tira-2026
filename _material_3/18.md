# 18. Dijkstra at Scale

In Part II you learned Dijkstra's algorithm, which finds shortest paths in a graph whose edge weights are not negative. It is still one of the most used algorithms in the world: map apps, network routers and games all run it or its descendants.

In Part II the graphs had a few nodes and the code was in Python. This week the graph is a real road network with hundreds of thousands of nodes, and the code is C++. We look at three questions that do not appear with small graphs:

1. How should a big graph be stored in memory?
2. Which priority queue makes Dijkstra fast, and can SIMD help?
3. How do we answer many queries at the same time on all cores?

## Road networks as graphs

A road network is a directed graph: the nodes are crossings and the arcs (directed edges) are road segments. The weight of an arc is its length or the time to drive along it. A two-way road is two arcs.

In 2006 the *9th DIMACS Implementation Challenge* published the road networks of the USA in a simple text format, and they became the standard test data for shortest-path research. The network of New York has 264,346 nodes and 733,846 arcs; the network of the whole USA has about 24 million nodes and 58 million arcs. The file format is simple. Here is a small example with 3 nodes and 4 arcs:

```
c lines that start with c are comments
p sp 3 4
a 1 2 803
a 2 1 803
a 2 3 158
a 3 2 158
```

The line `p sp n m` gives the number of nodes and arcs, and every line `a u v w` is an arc from node `u` to node `v` with weight `w`. The nodes are numbered from 1.

The template can download the New York network with `tools/download_dimacs.sh`. Without it, the benchmarks use a generated road network of the same size. It is a grid of $$514 \times 514$$ crossings. Every row is a road, and about 40 % of the crossings are also connected to the crossing below. It has 264,196 nodes and 738,782 arcs, 2.8 arcs per node, like New York.

Road networks have two properties that matter for speed. They are **sparse**: a node has only a few arcs (on average 2.8). And they are almost **planar**: drawn on a map, roads rarely cross without a crossing node. Because of this, Dijkstra's frontier (the nodes in the priority queue) stays small, as we will see.

## Compressed sparse row

In Python we stored a graph as a list of neighbour lists. In C++ the same idea is `std::vector<std::vector<Edge>>`. It works, but for a big graph it has two problems. Every node's list is a separate allocation, somewhere in memory, so walking through the graph jumps around in memory and causes cache misses. And every `std::vector` costs 24 bytes of bookkeeping, plus the overhead of its allocation, which is often more than its 2–3 arcs.

The standard layout for a graph that does not change is **compressed sparse row** (CSR). All arcs are in one array, sorted by their start node, and a second array says where the arcs of each node begin:

```cpp
struct Graph {
    std::vector<std::uint32_t> offset;  // n + 1 values, offset[0] == 0
    std::vector<Node> target;           // one value per arc
    std::vector<std::uint32_t> weight;  // one value per arc
};
```

The arcs that leave node `u` are at the indices `offset[u]`, …, `offset[u + 1] - 1` of `target` and `weight`:

```cpp
for (std::uint32_t e = g.offset[u]; e < g.offset[u + 1]; ++e) {
    Node v = g.target[e];
    std::uint32_t w = g.weight[e];
    // ... the arc u -> v with weight w
}
```

For New York the three arrays take 6.9 MB in total, and the arcs of a node are always next to each other: one cache miss usually brings all of them. The name comes from sparse matrices: the same three arrays describe a matrix that has few non-zero values.

### Building CSR with counting

The input is a list of arcs in any order. One way to build CSR is to sort the arcs by their start node, which takes $$O(m \log m)$$ time. But the start nodes are integers from $$0$$ to $$n - 1$$, so we can do better with counting, in $$O(n + m)$$ time:

1. Count the arcs of every node: for every arc $$u \rightarrow v$$, add 1 to `offset[u + 1]`.
2. Compute the prefix sum of the counts (as in week 17). Now `offset[u]` is the position where the arcs of node `u` start.
3. Copy `offset` into an array `next`, the next free position of each node. Go through the arcs again in input order and put every arc $$u \rightarrow v$$ at position `next[u]`, then add 1 to `next[u]`.

{% include viz.html id="csr" alt="A graph of 5 nodes and 8 arcs. Counting gives offsets 0, 2, 3, 6, 7, 8, and the arcs are placed so that targets are 1, 2, 3, 0, 3, 1, 4, 0." %}

This is a **counting sort**. It is **stable**: the arcs of a node stay in the order of the input. In task 1 you implement it; on our test machine it was about 4 times faster than sorting.

## Dijkstra with lazy deletion

Dijkstra's algorithm keeps a distance estimate for every node, at first 0 for the source and $$\infty$$ for the others. Then it repeats these steps:

1. Take the unsettled node $$u$$ with the smallest estimate.
2. Mark $$u$$ **settled**: its distance is now final.
3. **Relax** the arcs of $$u$$: for every arc $$u \rightarrow v$$ with weight $$w$$, if $$d(u) + w < d(v)$$, set $$d(v) = d(u) + w$$.

A priority queue (a heap) finds the node with the smallest estimate. When $$d(v)$$ gets smaller, the heap should learn about it. There are two ways to do that:

* **decrease-key**: find $$v$$ in the heap and move it up. The heap must know where every node is, which needs an extra array and extra work in every operation.
* **lazy deletion**: push a new key for $$v$$ and leave the old one in the heap. When an old key comes out of the heap later, we notice that it does not match $$d(v)$$ and skip it.

Lazy deletion makes the heap simpler and is usually faster, so we use it. `std::priority_queue` has no decrease-key anyway.

### One 64-bit key

A heap entry needs a distance and a node. We pack both into one 64-bit integer: the distance in the upper 32 bits and the node in the lower 32 bits.

```cpp
constexpr std::uint64_t make_key(Dist d, Node v) { return std::uint64_t{d} << 32 | v; }
constexpr Dist key_dist(std::uint64_t key) { return static_cast<Dist>(key >> 32); }
constexpr Node key_node(std::uint64_t key) { return static_cast<Node>(key); }
```

Comparing two keys as integers compares the distances first and, if they are equal, the nodes. So nodes with the same distance always come out in the order of their numbers, and the order in which the nodes are settled is the same on every computer. The tests use this: they check the exact settle order. A key is also small, 8 bytes, and comparing two keys is one instruction.

Here is the main loop:

```cpp
dist.assign(g.nodes(), INF);
dist[source] = 0;
heap.push(make_key(0, source));
while (!heap.empty()) {
    std::uint64_t key = heap.pop();  // remove and return the smallest key
    Node u = key_node(key);
    Dist d = key_dist(key);
    if (d != dist[u]) continue;  // an old key: u was settled with a smaller distance
    for (std::uint32_t e = g.offset[u]; e < g.offset[u + 1]; ++e) {
        Node v = g.target[e];
        Dist nd = d + g.weight[e];
        if (nd < dist[v]) {
            dist[v] = nd;
            heap.push(make_key(nd, v));
        }
    }
}
```

The following figure runs it on a small graph. Watch the heap at the bottom: old keys stay in it until they come out, and then they are skipped.

{% include viz.html id="dijkstra-lazy" alt="Dijkstra with lazy deletion on 6 nodes: three old keys are popped and skipped, and two keys with distance 9 come out in the order of their nodes." %}

With lazy deletion the heap can hold more keys than there are nodes, but at most one per successful relaxation. On our generated road network the heap never had more than 945 keys at the same time: the frontier of an almost planar graph is small.

### Stopping early

To find the distance from $$s$$ to one target $$t$$, we can stop as soon as $$t$$ is settled: its distance is final. On average this settles about half of the nodes. To find the path itself, remember for every node $$v$$ the node $$u$$ whose arc gave $$v$$ its current distance: `parent[v] = u`. Then follow the parents back from $$t$$ to $$s$$ and reverse the list.

## d-ary heaps

`std::priority_queue` is a **binary heap**: an array where the children of index $$i$$ are $$2i + 1$$ and $$2i + 2$$. A binary heap with $$n$$ keys has $$\log_2 n$$ levels, and `pop` moves a key down through all of them, with one unpredictable comparison per level.

A **d-ary heap** gives every node $$d$$ children: the children of index $$i$$ are $$di + 1, \ldots, di + d$$, and the parent of index $$i > 0$$ is $$\lfloor (i - 1) / d \rfloor$$. The heap has only $$\log_d n$$ levels: with $$d = 4$$, half as many as a binary heap.

{% include viz.html id="dary-heap" alt="Removing the minimum from a 4-ary heap of 13 keys: the last key 14 moves down two levels, past 2 and 4." %}

The number of comparisons in `pop` does not get smaller: $$\log_4 n$$ levels with 4 children cost about as many comparisons as $$\log_2 n$$ levels with 2. But two things get better:

* **Fewer levels, so fewer steps that wait for each other.** Finding the smallest of 4 children can be done without branches, and the 4 children are next to each other in memory (32 bytes, half a cache line).
* **`push` is faster**: it moves a key *up* and compares only with the parent, so fewer levels mean fewer comparisons.

In Dijkstra, a 4-ary heap was 1.3–1.4 times faster than `std::priority_queue` on our test machine. In task 4 you write one.

## An 8-ary heap with AVX-512

With $$d = 8$$ and 64-bit keys, the 8 children of a node are 64 bytes: exactly one cache line. Can we compare all 8 of them with one SIMD instruction?

First we need the children to *be* one cache line, not two halves of two lines. The trick is to put the root not at index 0 but at slot 7 of an array that starts at a 64-byte boundary. Heap index $$h$$ is stored in slot $$h + 7$$, so the children $$8h + 1, \ldots, 8h + 8$$ are in the slots $$8h + 8, \ldots, 8h + 15$$, and $$8h + 8$$ is always a multiple of 8. The empty slots after the last key hold the largest possible key, `~0` (all bits 1). So every group of 8 is full, and the code needs no special case for the last group.

AVX-512 has the two instructions that we need for 64-bit keys:

* `_mm512_min_epu64(a, b)`: the smaller of two unsigned 64-bit values, in each of 8 lanes;
* `_mm512_cmpeq_epu64_mask(a, b)`: compares 8 lanes and returns a **mask**, an 8-bit number with bit $$j$$ set if lane $$j$$ is equal.

AVX2 has neither: it has no 64-bit minimum, no unsigned 64-bit comparison and no mask registers. That is why this heap uses AVX-512.

To find the smallest child we need the minimum *over* the lanes, not between two registers. Three steps do it: swap the halves of the register and take the lane-wise minimum, then swap the quarters, then neighbouring lanes. After that every lane holds the minimum. A comparison with the original register gives a mask with a 1 bit for the smallest child, and `std::countr_zero` (from `<bit>`) gives its position.

{% include viz.html id="heap8-simd" alt="The 8 children of the root in slots 8 to 15 are loaded into a 512-bit register; three shuffle and minimum steps give the minimum 2 in every lane; the comparison mask has bit 4 set, so the smallest child is heap index 5." %}

```cpp
#include <immintrin.h>

#include <bit>
#include <cstddef>
#include <cstdint>

// The heap index of the smallest child of h.
[[gnu::target("avx512f")]] std::size_t min_child(const std::uint64_t* a, std::size_t h) {
    __m512i k = _mm512_load_si512(a + 8 * h + 8);                       // 8 children, one line
    __m512i m = _mm512_min_epu64(k, _mm512_shuffle_i64x2(k, k, 0x4E));  // halves
    m = _mm512_min_epu64(m, _mm512_shuffle_i64x2(m, m, 0xB1));          // quarters
    m = _mm512_min_epu64(m, _mm512_shuffle_epi32(m, _MM_PERM_BADC));    // neighbours
    __mmask8 is_min = _mm512_cmpeq_epu64_mask(k, m);                     // bit j: child j
    return 8 * h + 1 + std::countr_zero(static_cast<unsigned>(is_min));
}
```

`[[gnu::target("avx512f")]]` compiles only this function for AVX-512; the rest of the program stays AVX2. It must only be called on a CPU that has AVX-512, which `__builtin_cpu_supports("avx512f")` can check. If several children are equal, the lowest set bit wins, so the leftmost child is chosen, as in the scalar version.

The AVX2 version (task 6) needs two registers of 4 keys and more work. AVX2 can only compare *signed* 64-bit integers, with `_mm256_cmpgt_epi64`. A trick fixes that: flipping the highest bit of both values (XOR with `0x8000000000000000`) turns the unsigned order into the signed order. The minimum is then `_mm256_blendv_epi8(a, b, _mm256_cmpgt_epi64(a, b))`, and `_mm256_movemask_pd` turns a comparison into a 4-bit number.

If your computer has no AVX-512, you can still test the code with [Intel SDE](https://www.intel.com/content/www/us/en/developer/articles/tool/software-development-emulator.html), which emulates newer CPUs: `sde64 -skx -- ./build/debug/week18/w18_test -tc="task5*"`. Measure on the course machine.

## Measuring the heaps

We ran Dijkstra from the same sources on the generated road network with each heap. The times are for one Dijkstra (all 264,196 nodes), the median of 3 rounds, compiled with GCC 13 and Clang 18 on our test machine with AVX-512:

| Heap | GCC | Clang | Speedup |
| --- | --- | --- | --- |
| `std::priority_queue` (binary heap) | 30.4 ms | 29.8 ms | 1.0× |
| 4-ary heap | 21.9 ms | 21.8 ms | 1.4× |
| 8-ary heap, AVX2 | 22.8 ms | 19.3 ms | 1.3–1.5× |
| 8-ary heap, AVX-512 | 20.6 ms | 19.5 ms | 1.5× |

The d-ary heaps are about 1.4 times faster than the binary heap. But the AVX-512 heap is only 6–12 % faster than a plain 4-ary heap. Why so little?

Remember **latency and throughput** from week 17. `pop` is a chain of steps that depend on each other: we cannot load the next level before we know which child was the smallest. SIMD increases throughput: it does 8 comparisons with few instructions. It does not shorten the chain: the load, the three shuffle-and-minimum steps, the comparison and `countr_zero` take roughly 20–25 cycles one after another for every level. The 4-ary heap needs 1.5 times as many levels, but each level is a shorter chain. And the heap here is small (at most 945 keys, 7.5 KB), so it is always in the L1 cache, and needing fewer cache lines does not help either.

This is a typical result, and an important lesson: **measure before you believe**. SIMD gives big speedups for long loops over data (like the blending of week 17), where many independent operations run at the same time. It gives little for a short chain of dependent steps.

## Many queries in parallel

A route planner answers millions of queries. Every query is independent of the others, so the easy way to use all cores is to run different queries on different threads:

```cpp
#pragma omp parallel for schedule(dynamic)
for (std::size_t i = 0; i < queries.size(); ++i) {
    // answer queries[i] and write the distance to out[i]
}
```

Two details matter.

**Every thread needs its own memory for the search**: its own distance array and its own heap. If the threads shared them, they would have data races. The simple way is to create them inside a `#pragma omp parallel` region, before the loop. Then each thread creates its own copy once and reuses it for all its queries. The graph itself is only read, so all threads can share it.

**Queries take very different times.** A query between two nearby crossings settles a few hundred nodes; a query across the map settles most of the graph. With the default `schedule(static)`, every thread gets a fixed, equal number of queries, and one thread can get many long queries while the others wait. `schedule(dynamic)` gives the next query to whichever thread is free.

On our 4-core machine, 32 random queries ran 4 times faster this way than one after another.

## Versioned distance arrays

When a thread reuses its distance array for the next query, the array must start again as all $$\infty$$. Writing $$\infty$$ to all 264,000 nodes takes about ten times as long as a short query, so for short queries most of the time would go to clearing memory.

The trick is to give every node a **version**: the number of the query that last wrote its distance. A distance counts only if its version is the current query's number. Then starting a new query is just adding 1 to the counter, and nothing has to be cleared:

{% include viz.html id="versioned" alt="Distances and versions of 8 nodes: query 2 starts by changing the counter to 2, so the values written by query 1 count as infinity without being cleared." %}

There is one catch, shown at the end of the figure: a 32-bit counter goes around to 0 after $$2^{32} - 1$$ queries. In task 8 you handle that case too. With versions, 2000 short queries ran about 10 times faster on our machine.

## In production

* **Boost.Graph**, a widely used C++ graph library, runs `dijkstra_shortest_paths` with a 4-ary heap (`d_ary_heap_indirect` with arity 4) for the reasons in this chapter.
* **Network routers** run Dijkstra all the time. Internet providers and companies use the routing protocols OSPF and IS-IS inside their networks. With them, every router receives the map of the whole network and computes a shortest-path tree from itself with Dijkstra, which is called SPF (*shortest path first*) there. When a link breaks, all routers run it again.
* **Map services** cannot run plain Dijkstra on a continent for every request. They precompute extra data that makes queries thousands of times faster. We look at such methods in weeks 19 and 20; contraction hierarchies (week 20) are used, for example, in the open-source route planner OSRM.

### Bonus: radix heaps

Dijkstra pops keys in increasing order: a popped key is never smaller than the one before it. A priority queue that uses this property is called **monotone**. A *radix heap* is one: it puts every key into a bucket according to the highest bit in which it differs from the last popped key. Keys move only to lower buckets, so every key moves at most 32 times for 32-bit distances. In practice radix heaps are often faster than binary heaps for Dijkstra with integer weights. Try one, and measure it against your 4-ary heap.
