# 23. Vector Search I: Exact Search and Quantization

Ask a photo app for "a dog on a beach", and it finds photos whose files contain no words at all. A neural network has turned every photo, and your question, into a **vector**: a list of a few hundred numbers, made so that similar meanings give nearby vectors. Searching by meaning becomes a question of geometry: which vectors are nearest to the vector of the query?

This is **nearest neighbour search**, and it is everywhere: in image and music search, in recommendations ("people who liked this also liked..."), in finding copies and spam, and in chatbots that look up documents before they answer (*retrieval-augmented generation*, RAG). A vector database answers thousands of such queries per second, over millions or billions of vectors.

This week and the next we build the main methods. This week:

* **Exact search by brute force**, made fast with FMA instructions and several accumulators, and the best $$k$$ with a heap.
* **k-d trees**, which are excellent in 2 or 3 dimensions and useless in 128.
* **k-means** and the **inverted file**, which searches only the clusters nearest to the query.
* **Product quantization**, which shrinks a vector of 512 bytes to 16 and computes distances with table lookups, and **fast scan**, which does 32 of those lookups in one SIMD instruction.
* Many queries at once with threads, and **SimHash** for near duplicates.

## Meaning as numbers

Where do the vectors come from? A model is trained so that things that belong together get nearby vectors: two photos of dogs, a question and the paragraph that answers it, two songs that the same people like. Such vectors are called **embeddings**. Text embeddings of language models have a few hundred to a few thousand numbers. The model is expensive, but it runs once per item; the search then runs on the vectors alone.

Our vectors are older and simpler. A **SIFT descriptor** (Scale-Invariant Feature Transform, David Lowe, 1999) describes a small patch of an image with 128 numbers: how strong the edges are in 8 directions, in each cell of a 4 × 4 grid. Two patches that show the same corner of a building, photographed from a little different angle, get nearby descriptors. The SIFT1M data set of the TEXMEX corpus has one million of them, and it has been the standard test of vector search for 15 years.

The benchmarks use the first 200,000 vectors and 1000 queries of SIFT1M if you download it with `tools/download_sift.sh`. Otherwise they use generated SIFT-like vectors: 128 whole numbers from 0 to 255 (36 % of them zero), in clusters of different sizes, where the vectors of a cluster vary mostly along 16 directions. All numbers in this chapter are for the generated vectors, measured with GCC 16.

```cpp
using Id = std::uint32_t;

struct Dataset {  // n vectors of dim floats, one after another

    Id id;
    friend auto operator<=>(const Neighbor&, const Neighbor&) = default;

```

The task is: given a query $$q$$, find the $$k$$ vectors nearest to it, usually $$k = 10$$. An **exact** method finds exactly those. An **approximate** method may miss some, and we measure how many it finds: the **recall@k** is the fraction of the true $$k$$ nearest neighbours that are among its $$k$$ results. Recall 0.95 for $$k = 10$$ means that on average 9.5 of the 10 were found. Approximate methods can be hundreds of times faster, and for most applications a few misses are fine: the user does not know which photo was the 10th nearest.

## Distances

Three measures are common:

* The **Euclidean distance**, or L2: $$\lVert a - b \rVert^2 = \sum_i (a_i - b_i)^2$$. We use the square: it puts the vectors in the same order and needs no square root.
* The **inner product**: $$a \cdot b = \sum_i a_i b_i$$, where larger means more similar. It is used when the length of a vector means something, for example how popular an item is.
* The **cosine similarity**: $$\cos \theta = \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert}$$, which looks only at the direction.

{% include viz.html id="vec-metrics" alt="Points in the plane and a query that can be dragged. With the Euclidean distance the three nearest points lie inside a circle around the query; with the cosine similarity the three best are the points whose direction is closest to the query's; with the inner product they are the points farthest out in the direction of the query." %}

If all vectors have length 1, then $$\lVert a - b \rVert^2 = 2 - 2\, a \cdot b$$, and all three measures give the same order. So vector databases often normalize the vectors once and then use whichever is fastest. The same expansion for any vectors,

$$\lVert q - x \rVert^2 = \lVert q \rVert^2 - 2\, q \cdot x + \lVert x \rVert^2,$$

will be useful twice: in k-means and for many queries at once.

SIFT values are whole numbers below 256, so every partial sum of a distance of 128 values is a whole number below $$2^{24} = 16{,}777{,}216$$, and a `float` holds such numbers exactly. Then the distance is exact in any order of the additions: SIMD code gives exactly the bits of the scalar code. Our tests use this: most of them compare your results with the baseline exactly, and equal distances are common, so the rule "on equal distances, the smaller id first" matters. With general floats the order of the additions changes the last bits, and results must be compared with a tolerance.

## SIMD: distances with FMA

The scalar distance is three operations per value:

```cpp
float l2_squared(const float* a, const float* b, std::size_t dim) {
    float s{};

    for (std::size_t i = 0; i < dim; ++i) {
        const float d = a[i] - b[i];
        s += d * d;
    }

    return s;
}
```

The compiler does not vectorize this loop: vectorizing would change the order of the additions, and floating-point addition is not associative, so the result could change in the last bits. With `-ffast-math`, or `#pragma omp simd reduction(+ : s)` before the loop, we allow it. With intrinsics we decide ourselves.

AVX2 has **FMA**, fused multiply-add: `_mm256_fmadd_ps(x, y, z)` computes $$x \cdot y + z$$ for 8 floats with one rounding. One FMA does the multiplication and the addition of 8 values:

```cpp
__m256 sum = _mm256_setzero_ps();
std::size_t i{};

for (; i + 8 <= dim; i += 8) {
    const __m256 d = _mm256_sub_ps(_mm256_loadu_ps(a + i), _mm256_loadu_ps(b + i));
    sum = _mm256_fmadd_ps(d, d, sum);  // sum += d * d in 8 lanes
}
```

At the end, the 8 lanes of `sum` are added together (a *horizontal sum*), and the last `dim % 8` values need care. `_mm256_maskload_ps` loads only the lanes whose mask is set and never reads past the end of the array; a full 8-value load would, and AddressSanitizer would report it.

This loop has a hidden problem. A core can start two FMAs in every cycle, but the result of an FMA is ready only 4 cycles later: its **latency** is 4 cycles. Every FMA of the loop needs the `sum` of the one before, so each waits 4 cycles, and the FMA units are idle most of the time. The cure is **several accumulators**: four sums for four interleaved parts of the vector, added together at the end. Then four FMAs are in flight at the same time.

{% include viz.html id="fma-accumulators" alt="A timeline of the 16 FMAs of a distance of 128 values, one row for each accumulator. With one accumulator every FMA waits 4 cycles for the one before, 64 cycles in total; with two the chains overlap; with four a new FMA starts in every cycle, 16 cycles; eight are not faster than four." %}

On our machine a dot product of 4096 values (both in the L1 cache) took 2423 ns with the scalar loop, 524 ns with AVX2 and one accumulator, 269 ns with two, 162 ns with four and 165 ns with eight. Four are enough, because each FMA also needs two loads, and the loads allow only about one FMA per cycle. For our vectors of 128 values the loop is short (16 FMAs), and the horizontal sum and the function call matter too: a distance to vectors in the L2 cache took 71 ns with the scalar loop and 13.5 ns with four accumulators.

## Brute force and the best k

Brute force computes the distance from the query to every vector and keeps the best $$k$$. Sorting all $$n$$ distances to keep 10 of them is wasteful: in the baseline, sorting the 200,000 distances took 15.9 ms of its 41.6 ms per query. Better is a **max-heap** of the best $$k$$ so far. Its top is the worst of them, so a new vector needs a single comparison to be rejected, and almost all are rejected:

```cpp
if (heap.size() < k) {
    heap.push_back({d, id});
    std::ranges::push_heap(heap);
} else if (d < heap.front().distance) {
    std::ranges::pop_heap(heap);  // the worst moves to the back...
    heap.back() = {d, id};        // ...where the new one replaces it
    std::ranges::push_heap(heap);
}
```

The ids come in increasing order, so a later vector at the same distance as the worst has a larger id and never wins: comparing the distances is enough. At the end, `std::ranges::sort_heap` puts the $$k$$ results in order.

With the AVX2 distance and the heap, one query took **10.3 ms**. That is the time to read 200,000 × 512 bytes = 102 MB: 10 GB/s, the memory bandwidth of one core on our machine (in some runs it was 30 GB/s; the machine is shared). The arithmetic is not the limit any more: the vectors cannot arrive faster. So the rest of the chapter reads less data: fewer vectors (trees, the inverted file) or smaller vectors (product quantization).

## Trees fail in high dimensions

In the plane, a **k-d tree** (Jon Bentley, 1975) finds the nearest point among a million with a few dozen distances. It splits the points at the median of their x coordinates, then each half at the median of y, then x again, and so on, until at most a few points are left in a leaf. We store it without pointers: `std::nth_element` puts the median of a range in the middle of the range, the smaller values before it and the larger ones after it, so the ranges are the nodes and the middles are the splits.

The search goes first to the side of the query. Then it visits the other side only if the splitting plane is nearer than the $$k$$-th best distance so far: otherwise no point on the other side can be nearer.

```cpp
const float plane = query[axis] - points[mid][axis];
offer(mid);  // the median point itself

if (plane < 0) {
    visit(lo, mid, depth + 1);

    if (worth(plane))  // plane * plane <= the k-th best distance (or fewer than k found)
        visit(mid + 1, hi, depth + 1);
} else {
    visit(mid + 1, hi, depth + 1);

    if (worth(plane))
        visit(lo, mid, depth + 1);
}
```

{% include viz.html id="kdtree" alt="44 points in the plane. First the tree is built: split lines appear one by one, alternately vertical and horizontal, at the medians. Then a query searches the tree: it visits the leaves on its side, the circle of the best distance shrinks, and the parts whose split line is farther than the circle are skipped and shaded grey." %}

Now the same tree for uniform random points in more dimensions, 200,000 points and $$k = 10$$:

{: .grid-head }
| Dimensions | Points whose distance is computed | Against brute force |
| --- | --- | --- |
| 2 | 0.03 % | 368 times faster |
| 3 | 0.07 % | 132 times faster |
| 4 | 0.16 % | 47 times faster |
| 8 | 3.4 % | 11 times faster |
| 16 | 99.7 % | 2 times slower |
| 32, 64, 128 | 100 % | slower |

This is the **curse of dimensionality**. In high dimensions all distances are almost the same: the nearest point is not much nearer than a typical one, so the ball around the query that holds the nearest neighbours crosses almost every splitting plane, and nothing can be skipped. There is also too little data: a tree of 200,000 points has 17 levels, so in 16 dimensions every coordinate is split about once. On our SIFT-like vectors the tree computed 85 % of the distances and was no faster than brute force. Clusters help a little, but not enough. In high dimensions, fast search must give up exactness.

## k-means

Most approximate methods start by grouping similar vectors. **k-means** (Stuart Lloyd, 1957) finds $$k$$ centroids, points that represent the groups:

1. Choose $$k$$ starting centroids, for example $$k$$ random vectors of the data.
2. **Assign**: give every vector to its nearest centroid.
3. **Move**: move every centroid to the mean of its vectors.
4. Repeat 2 and 3 a fixed number of times, or until little changes.

Neither step can increase the mean squared distance from the vectors to their centroids, so it decreases until it settles (in a local minimum, which depends on the start).

{% include viz.html id="kmeans" alt="150 points in six groups and six centroids, which start at random points. In each round the points take the color of their nearest centroid, then the centroids move to the means of their points. The mean squared distance falls, quickly in the first rounds." %}

With 512 centroids on 20,000 of our vectors, the mean squared distance was 13,245 at the start, 8,309 after one round, 8,018 after four and 7,951 after ten: most of the gain comes in the first rounds. Almost all of the time goes to step 2: $$n \cdot k$$ distances, here 10 million per round. One round took 113 ms on one thread and 37 ms on four; the vectors are independent, so the threads only need their own sums for step 3. The expansion of the distance helps too: $$\lVert x \rVert^2$$ is the same for every centroid, so the nearest centroid is the one with the smallest $$\lVert c \rVert^2 - 2\, x \cdot c$$, one inner product per pair, with $$\lVert c \rVert^2$$ computed once per round.

## The inverted file

The **inverted file** (IVF) uses k-means to divide the vectors. It clusters them into `nlist` lists: every vector goes into the list of its nearest centroid. A query computes its distances to the `nlist` centroids, and then searches only the `nprobe` lists whose centroids are nearest. The name comes from the inverted index of week 21: there a list per word, here a list per centroid. The vectors of a list are stored one after another, so the search reads them in one stream; the lists are built with the counting sort of week 21.

{% include viz.html id="ivf-probe" alt="Points in six colored cells, one cell per centroid. A query can be dragged, and a slider sets nprobe. The points of the searched cells are colored, the others faded; the five nearest found are green, and true neighbours in cells that were not searched are red." %}

```cpp
// The nprobe nearest lists: (distance, number) pairs of the centroids.
std::ranges::partial_sort(lists, lists.begin() + nprobe);

for (std::size_t l = 0; l < nprobe; ++l) {
    const Id c = lists[l].id;

    for (std::uint32_t p = ivf.offset[c]; p < ivf.offset[c + 1]; ++p)
        offer({l2_squared(ivf.vectors[p], query, dim), ivf.ids[p]});
}
```

With 512 lists for our 200,000 vectors (390 vectors per list on average, but from 1 to 2329):

{: .grid-head }
| nprobe | Vectors searched | recall@10 | Faster than brute force |
| --- | --- | --- | --- |
| 1 | 0.4 % | 0.673 | 120–210 times |
| 4 | 1.4 % | 0.956 | 40–80 times |
| 16 | 3.7 % | 1.000 | 20–40 times |
| 64 | 15 % | 1.000 | 7–14 times |

A true neighbour is missed only if it lies in a cell that was not searched, near a border. The speedups vary between runs, because the speed of brute force depends on the memory bandwidth of the moment. A common rule is $$\sqrt{n}$$ to $$16\sqrt{n}$$ lists; more lists make each list shorter, but the query needs more of them for the same recall.

## Product quantization

The inverted file reads fewer vectors. **Product quantization** (PQ, Hervé Jégou, Matthijs Douze and Cordelia Schmid, 2011) makes every vector smaller. Cut a vector of 128 values into $$m = 16$$ parts of 8 values. For each part, run k-means with 256 centroids on that part of many vectors: 16 small codebooks. Then store each part of a vector as the number of its nearest centroid, one byte. A vector of 512 bytes becomes a **code** of 16 bytes, 32 times smaller. The 16 codebooks have only 16 × 256 centroids, but together they can describe $$256^{16} = 2^{128}$$ different vectors.

How do we compute a distance without the vector? For a query, first compute a **distance table**: for each part $$j$$ and each centroid $$c$$ of that part, the distance between part $$j$$ of the query and $$c$$. That is 16 × 256 values, 16 KB, and it fits in the L1 cache. The approximate distance to a vector is then the sum of one table entry per part, chosen by its code:

```cpp
float s{};

for (std::size_t j = 0; j < m; ++j)
    s += table[j * 256 + codes[i * m + j]];  // part j, the centroid of vector i
```

This is the **asymmetric distance**: the query is exact and only the database vectors are approximate, which is more accurate than coding the query too.

{% include viz.html id="pq-adc" alt="A vector of 8 numbers is cut into 4 parts of 2. Each part is drawn as a point among the 4 centroids of its codebook and replaced by the number of the nearest one, so the vector becomes a code of 4 small numbers. For a query, a table of 4 by 4 distances is computed, and the approximate distance is the sum of 4 table entries chosen by the code." %}

On our data the PQ scan took **5.4 ns per vector**, instead of about 50 ns for an exact distance read from memory, and the 200,000 codes take 3.2 MB instead of 102 MB. The table costs 15 µs per query. But PQ distances are approximate: of the true 10 nearest, PQ alone ranked 33 % among its best 10. The usual fix is **re-ranking**: take the best 100 by PQ distance, compute their exact distances from the original vectors, and keep the best 10. Then recall@10 was 0.810. The codes of a billion vectors fit in 16 GB of memory, and the original vectors can stay on an SSD: only 100 of them are read per query.

The scan itself has the latency problem of the distances: the sum of one vector is a chain of 16 dependent additions. Work on four vectors at a time, each with its own sum: four independent chains, as with the accumulators. Each sum still adds the parts in the order 0, 1, ..., 15, so the results are bit for bit those of the simple loop.

## Fast scan: tables in registers

**Fast scan** (Fabien André, Anne-Marie Kermarrec and Nicolas Le Scouarnec, 2015) goes further. Use 4-bit codes, 16 centroids per part, and twice as many parts: $$m = 32$$ parts of 4 values, still 16 bytes per vector. Now the table of a part has only 16 entries. Rounded to bytes with a common scale, it fills 16 bytes: half of an AVX2 register.

The instruction `vpshufb` (`_mm256_shuffle_epi8(table, index)`) looks up bytes in a table: byte $$i$$ of the result is the byte of the table at position $$\text{index}_i$$ (from 0 to 15), separately in each 128-bit half. With the table of part $$j$$ in both halves and the codes of 32 vectors as the indexes, **one instruction does 32 lookups**. The codes are stored in blocks of 32 vectors: for part $$j$$, 16 bytes, where byte $$i$$ has the code of vector $$i$$ in its low 4 bits and the code of vector $$16 + i$$ in its high 4 bits:

```cpp
const __m128i packed = _mm_loadu_si128(reinterpret_cast<const __m128i*>(block + j * 16));
// The low 4 bits (vectors 0-15) in the low half, the high 4 bits (16-31) in the high half.
const __m256i index = _mm256_and_si256(_mm256_set_m128i(_mm_srli_epi16(packed, 4), packed), low4);
const __m256i value = _mm256_shuffle_epi8(table_j, index);  // 32 lookups at once
```

The 32 bytes are then added to sums of 16 bits: 32 parts of at most 255 add up to at most 8160, so they never overflow.

{% include viz.html id="fast-scan" alt="A block of 32 vectors with 4-bit codes and four parts. For each part, the 16-byte table, the codes of the 32 vectors in the two halves of a register, the 32 bytes that vpshufb looks up, and the 16-bit sums of the 32 vectors, which grow part by part." %}

Fast scan took **1.36 ns per vector**, 10 times faster than the scalar loop over the same 4-bit codes (13.8 ns) and 4 times faster than the 8-bit PQ scan. The 4-bit codes are coarser: re-ranking the best 100 gave recall@10 0.557. But the scan is so fast that we can re-rank more: with the best 1000, recall@10 was 0.942.

## Parallel: many queries at once

Queries are independent, so a batch of queries is easy to run in parallel: an OpenMP loop over the queries, where every thread writes only the results of its own queries. In one run with 100 queries, brute force took 9.44 ms per query on one thread, 2.02 ms on two threads and 0.96 ms on four; over several runs, four threads were 4 to 10 times faster than one. More than 4 times is possible because brute force is limited by memory, and on our machine one core alone read memory at only 12–19 GB/s, but four cores together read at 117–156 GB/s.

A batch allows a much bigger saving: read each vector once for many queries. Take the vectors in chunks of 2048 (1 MB, which stays in the L2 cache), and compute the distances from each chunk to all the queries of a block before going to the next chunk. With blocks of 25 queries, one thread took 2.61 ms per query instead of 9.44 (in the same run), and four threads 0.74 ms. Now the vectors come from the cache, not from memory, and the arithmetic is the limit again.

Taken to the end, this is matrix multiplication. With $$\lVert q - x \rVert^2 = \lVert q \rVert^2 - 2\, q \cdot x + \lVert x \rVert^2$$, the inner products of a block of queries with a block of vectors are a matrix product, the most optimized operation in all of computing. FAISS calls a BLAS library for batches of 20 queries or more, and GPUs run exact search on their matrix units (tensor cores).

## SimHash

To find **near duplicates**, such as the same photo in another size or a copied web page, we need a tiny fingerprint and a very fast comparison. **SimHash** (Moses Charikar, 2002) uses random hyperplanes. Choose $$b$$ random vectors $$r_1, \ldots, r_b$$. Bit $$i$$ of the hash of $$x$$ is 1 if $$r_i \cdot x \ge 0$$, that is, if $$x$$ is on the positive side of the hyperplane of $$r_i$$. A random hyperplane separates two vectors with probability $$\theta / \pi$$, where $$\theta$$ is the angle between them. So the number of different bits, the **Hamming distance**, estimates the angle: $$\theta \approx \pi \cdot \text{hamming} / b$$.

{% include viz.html id="simhash" alt="Two arrows from the origin that can be dragged, and random lines through the origin. Each line gives one bit for each arrow: the side of the line it is on. Lines that separate the arrows are red, and the two rows of bits show where they differ; the number of different bits estimates the angle between the arrows." %}

The Hamming distance of two 64-bit hashes takes two instructions:

```cpp
#include <bit>

int hamming(std::uint64_t a, std::uint64_t b) {
    return std::popcount(a ^ b);  // XOR, then POPCNT counts the ones
}
```

Google used 64-bit SimHash fingerprints to find near-duplicate pages among billions of crawled web pages (Gurmeet Manku, Arvind Jain and Anish Das Sarma, 2007): pages whose fingerprints differ in at most 3 bits were near duplicates. *Locality-sensitive hashing* (LSH) goes one step further: it puts vectors whose hashes agree on some bits into the same bucket, so that only vectors in the same bucket need to be compared.

Going further: anisotropic quantization
<div class="note" markdown="1">

Google's ScaNN changes what quantization tries to keep. Plain PQ makes the reconstruction error small in every direction. But for the inner product, an error along the direction of the vector itself changes the score more than an error across it. ScaNN's *anisotropic* quantization weighs the two differently, and gets better recall from the same 4-bit codes, which it scans with SIMD table lookups just like fast scan.

</div>

Goal: 6 times faster than the scalar baseline, for 200,000 vectors with 32 parts.

## Code to read

* FAISS by Meta (Matthijs Douze, Hervé Jégou, Jeff Johnson and others): `IndexFlatL2` for brute force (it uses BLAS for batches of queries), `IndexIVFFlat`, `IndexIVFPQ`, and the fast scan indexes `IndexPQFastScan` and `IndexIVFPQFastScan` (`faiss/impl/pq4_fast_scan.h`).
* Hervé Jégou, Matthijs Douze and Cordelia Schmid: _Product Quantization for Nearest Neighbor Search_ (IEEE TPAMI, 2011), which introduced PQ, the asymmetric distance and the SIFT1M benchmark.
* Fabien André, Anne-Marie Kermarrec and Nicolas Le Scouarnec: _Cache locality is not enough: High-Performance Nearest Neighbor Search with Product Quantization Fast Scan_ (VLDB 2015).
* ScaNN by Google Research: anisotropic quantization (Ruiqi Guo et al., ICML 2020) and 4-bit table lookups with SIMD.
* nanoflann: a header-only k-d tree in C++, used in robotics and for point clouds in 3 dimensions, where k-d trees shine.
* Moses Charikar: _Similarity Estimation Techniques from Rounding Algorithms_ (STOC 2002), the random hyperplanes of SimHash; Gurmeet Manku, Arvind Jain and Anish Das Sarma: _Detecting Near-Duplicates for Web Crawling_ (WWW 2007).
