# 24. Vector Search II: Graph Indexes

Last week the inverted file reached recall 0.95 by reading about 1.4 % of the vectors. Graph indexes do much better. On our 100,000 vectors, **HNSW** reached recall 0.95 with about 320 distance computations per query, 0.3 % of the vectors, in **10 µs**: 90 times faster than brute force. HNSW (*Hierarchical Navigable Small World graphs*, Yury Malkov and Dmitry Yashunin, 2016) is the index of most vector databases: Lucene (and with it Elasticsearch and OpenSearch), pgvector for PostgreSQL, Qdrant, Weaviate, Milvus, Redis and FAISS all have it.

The idea is old and simple: link every vector to some of its neighbours, and search by walking along the links toward the query. This week:

* **Greedy and beam search** on a graph, and why a search gets stuck.
* **HNSW**: its layers, how a new vector is linked into the graph, and the heuristic that chooses its neighbours.
* **Recall against speed**: what the parameters `M`, `efConstruction` and `ef` do.
* **Byte vectors** with SIMD distances, **prefetching**, and many queries in parallel.

We store the vectors as **bytes**. SIFT values are whole numbers from 0 to 255, so nothing is lost: a vector takes 128 bytes instead of 512, and every distance is an exact whole number. So the searches are deterministic, and your searches must return exactly the results of the baseline. The benchmarks use 100,000 vectors (generated as in week 23, or the first ones of SIFT1M) and 1000 queries. All numbers in this chapter are for the generated vectors, measured with GCC 16.

```cpp
struct Neighbor {  // ordered by distance, then by id
    std::uint32_t distance;
    Id id;
    friend auto operator<=>(const Neighbor&, const Neighbor&) = default;
};

struct Hnsw {
    std::size_t m = 0, m0 = 0;  // the most links of a node: m on layers 1, 2, ..., m0 = 2m on layer 0
    std::vector<int> level;     // node i is in the layers 0 ... level[i]
    Id entry = 0;               // the entry point: a node of the highest level
    int top = -1;               // the highest level, -1 while empty
    std::span<const Id> links(Id node, int layer) const;
    void set_links(Id node, int layer, std::span<const Id> ids);
};
```

## Greedy search

Make a graph: every vector is a node, linked to some nodes near it. To search, start at some node and move to its neighbour that is nearest to the query; repeat until no neighbour is nearer than the current node. This is **greedy search**. It computes only the distances to the neighbours of the nodes on its path: a few dozen instead of all $$n$$.

{% include viz.html id="greedy-graph" alt="64 points in clusters, linked into a graph, and a query that can be dragged. Greedy search starts at a fixed point and moves step by step to the neighbour nearest to the query. In a graph that links every point to its three nearest, it often stops in a local minimum far from the nearest point; in the small world graph, long links take it across the plane in a few steps." %}

Greedy search can stop at a **local minimum**: a node that has no nearer neighbour, but is not the nearest node. The graph in the figure links every point to its 3 nearest, and such a graph has two problems: a path moves in small steps, so it is long, and different groups of points may not be linked at all. On our 100,000 vectors, greedy search on the bottom layer of HNSW, from a fixed start, found the true nearest neighbour for only 22 % of the queries.

## Beam search

A **beam search** keeps several ways open. It keeps the `ef` best nodes found so far, the *results*, and a set of *candidates* that it has not expanded yet:

```cpp
while (!candidates.empty()) {
    const Neighbor c = best(candidates);  // the nearest candidate

    if (results.size() >= ef && c > worst(results))
        break;  // nothing better can come from it

    remove(candidates, c);

    for (Id e : index.links(c.id, layer)) {
        if (seen(e))
            continue;

        mark_seen(e);
        const Neighbor n{l2_squared(data[e], query, dim), e};

        if (results.size() < ef || n < worst(results)) {
            add(candidates, n);
            add(results, n);  // and the worst result leaves if there are more than ef
        }
    }
}
```

The candidates are a min-heap (the best on top) and the results a max-heap (the worst on top). With `ef` = 1 this is greedy search; a larger `ef` looks at more nodes and gets stuck less often, but computes more distances.

{% include viz.html id="beam-search" alt="The same kind of graph, a query that can be dragged and a slider for ef. Step by step the search expands its best candidate; the panels show the results (at most ef) and the candidates with their distances. When it stops, the results are compared with the true ef nearest points, and missed ones are marked." %}

A search should allocate no memory. The marks of the seen nodes are an array with a version number, as in week 18: node $$i$$ is seen if `visited[i] == version`, and a new search increases the version instead of clearing 100,000 marks. The two heaps are vectors that are reused with `std::push_heap` and `std::pop_heap`. The baseline, with `std::unordered_set`, `std::priority_queue` and the scalar distance, took four to five times as long as our search with these arrays and the SIMD distance of this chapter.

## Small worlds

How should the graph look? Short links alone make long paths, and long links alone miss the details. A **navigable small world** (NSW, Malkov and others, 2014) has both. It is built by inserting the vectors one by one in a random order, each linked (in both directions) to its nearest among those inserted before it. The first vectors arrive when the graph is almost empty, so their nearest neighbours are far away: they get long links, highways across the space. The later ones get short links. A search crosses the space on the early links and finds the details on the late ones, like the letters of Stanley Milgram's experiment in 1967, which reached a stranger across the United States from hand to hand in about six steps. In the figure, switch the graph to "small world".

## HNSW: layers

HNSW makes the highways explicit, with **layers**. Every node gets a random **level**: all nodes have level 0 or more, about 1 in $$M$$ have level 1 or more, 1 in $$M^2$$ level 2 or more, and so on:

$$\text{level} = \lfloor -\ln(u) \cdot m_L \rfloor, \qquad u \text{ uniform in } (0, 1], \qquad m_L = 1 / \ln M.$$

Layer $$l$$ is a graph of the nodes with level $$l$$ or more. The top layers have a few nodes, far apart; layer 0 has all of them. With $$M = 16$$ our 100,000 nodes had the levels 0 (93,888 nodes), 1 (5,719), 2 (370), 3 (20) and 4 (3).

A search starts at the **entry point** on the top layer and goes greedily (`ef` = 1) toward the query. Where it stops, it goes down one layer and continues from the same node. On layer 0 it runs a beam search with `ef`, and returns the best $$k$$. Like a skip list, the top layers make big jumps and the lower ones small steps.

{% include viz.html id="hnsw-layers" alt="Three panels side by side: layer 2 with a few points, layer 1 with more, and layer 0 with all 72. The search starts at the entry point on layer 2, takes greedy steps toward the query, goes down to layer 1 at the same point and continues, and on layer 0 a beam search finds the nearest points." %}

On our data, greedy search from the top layer found the true nearest neighbour for 48 % of the queries, against 22 % on layer 0 alone. With `ef` = 20, the search from the top reached recall@10 0.969 with 359 distances per query; the same beam search on layer 0 alone, from the entry point, reached only 0.825, with 454 distances.

## Building the graph

HNSW is built by inserting the nodes one by one, like a small world, but layer by layer:

1. The new node gets its random level $$L$$.
2. From the entry point, search greedily (`ef` = 1) down to layer $$L + 1$$.
3. On every layer from $$\min(L, \text{top})$$ down to 0: a beam search with `ef` = `efConstruction` finds candidates for the neighbours; choose $$M$$ of them (next section) and link the new node with them in both directions. If a neighbour now has too many links (more than $$M$$, or $$2M$$ on layer 0), choose its links again among the old ones and the new node. The results of the layer are the starting points on the layer below.
4. If $$L$$ is above the top level, the new node becomes the entry point.

`efConstruction` is the `ef` of the searches during the build: larger gives a better graph and a slower build. $$M$$ is the number of links: more links give better recall per step, but more memory and more distances per step. With $$M = 16$$ and `efConstruction` = 200, building the index of 100,000 vectors took 9.8 s on one thread, 98 µs per vector. It takes 264 bytes per vector: 128 for the vector and 136 for the links. The links of layer 0 have a fixed place for every node, the count and room for $$2M$$ links, as in hnswlib.

## Choosing the neighbours

Which $$M$$ of the candidates should a new node link to? The obvious choice, the $$M$$ nearest, works badly on clustered data. The nearest candidates are often all on one side, in the same cluster, so the graph splits into clusters with few links between them. The **heuristic** of HNSW goes through the candidates from the nearest and keeps a candidate only if it is nearer to the new node than to every neighbour kept before it. A candidate that is nearer to a kept neighbour lies "behind" it: a search can reach it through that neighbour, so its link is not needed.

{% include viz.html id="select-heuristic" alt="A new point in the middle and ten candidates around it, several of them in a group on one side. With the rule of the m nearest, all chosen neighbours are in that group. With the heuristic, a candidate that is nearer to an already kept neighbour than to the new point is skipped, and the kept neighbours point in different directions." %}

On our data the difference is dramatic. With the $$M$$ nearest, recall@10 was 0.718 at `ef` = 20, and it never got above 0.86, even with `ef` = 160. With the heuristic, recall was 0.969 at `ef` = 20 and 1.000 at `ef` = 160. The same idea is behind the *relative neighbourhood graph* of computational geometry.

## Recall against speed

The `ef` of a search can be different for every query, so one index offers many speeds. With $$M = 16$$ and `efConstruction` = 200, on one thread:

| --- | --- | --- | --- |
| 10 | 0.896 | 249 | 7.5 µs |
| 16 | 0.954 | 316 | 10.2 µs |
| 24 | 0.979 | 403 | 14.4 µs |
| 32 | 0.990 | 485 | 21.2 µs |
| 64 | 0.999 | 766 | 33.0 µs |
| 160 | 1.000 | 1317 | 72.9 µs |

Brute force over the same bytes took 937 µs per query, and the inverted file of week 23 (316 lists) 44 µs for recall 0.963. The figure shows the trade-off for all of them; up and to the right is better.

{% include viz.html id="recall-qps" alt="A chart of recall@10 against queries per second on a logarithmic scale, for HNSW built with efConstruction 200 and 100, the inverted file and brute force. A slider sets the recall needed, and the fastest setting of each method that reaches it is marked." %}

`efConstruction` matters. With `efConstruction` = 100, recall stopped at 0.978, even with `ef` = 320. The missed neighbours were not unreachable: the search simply never came near them, because the graph had too few good links there. **A poorly built graph cannot be fixed by searching harder.** The build costs once; the searches happen millions of times.

## SIMD: bytes instead of floats

The distance of two byte vectors needs care, because the difference of two bytes does not fit in a byte, and its square needs more than 16 bits. AVX2 has the pieces: `_mm256_max_epu8` and `_mm256_min_epu8` give $$\lvert a - b \rvert = \max - \min$$ without overflow, `_mm256_unpacklo_epi8` and `_mm256_unpackhi_epi8` with zeros widen the bytes to 16 bits, and `_mm256_madd_epi16(d, d)` multiplies 16 pairs of 16-bit values and adds neighbouring products into eight 32-bit sums. One round handles 32 values. With AVX-512 VNNI, `_mm256_dpwssd_epi32` (with AVX-VNNI, `_mm256_dpwssd_avx_epi32`) does the multiplication and the addition to the sums in one instruction.

For a distance to 20,000 vectors on our machine: floats took 18.4 ns (the vectors are 10 MB), bytes 8.4 ns (2.5 MB), and bytes with the scalar loop 66.5 ns. Bytes are faster because a vector is two cache lines instead of eight. For real-valued embeddings, **scalar quantization** maps every value to a byte with a minimum and a scale per dimension. It loses a little accuracy for 4 times less memory, and Lucene, Qdrant and others offer it, even with 4 bits or 1 bit per value.

## Prefetching

A graph search jumps around in memory: the neighbours of a node are vectors at random places, so almost every vector is a cache miss. The CPU cannot guess which vector comes next, so it waits for each one. But we know: the next vectors are those of the links of the node being expanded. `_mm_prefetch(p, _MM_HINT_T0)` asks the CPU to start loading the cache line at `p` now, without waiting for it. As in hnswlib, the search first marks the unseen neighbours and prefetches all their vectors, and only then computes the distances:

```cpp
ids.clear();

for (Id e : index.links(c.id, layer)) {
    if (visited[e] == version)
        continue;

    visited[e] = version;
    ids.push_back(e);
    const char* p = reinterpret_cast<const char*>(data[e]);
    _mm_prefetch(p, _MM_HINT_T0);       // a vector of 128 bytes
    _mm_prefetch(p + 64, _MM_HINT_T0);  // is two cache lines
}

for (Id e : ids) {
    // The vectors are on their way, or already here.
    const Neighbor n{l2_squared(data[e], query, dim), e};
    // ...
}
```

{% include viz.html id="prefetch-timeline" alt="Two timelines for the six neighbours of a node. Without prefetching, each distance waits for its vector to arrive from memory, one after another. With prefetching, the six loads start together and the waits overlap, so the same work ends much earlier. A slider sets the memory latency." %}

Prefetching made our whole search 1.3–1.7 times faster. Our 100,000 vectors (12.8 MB) and their links (13 MB) fit in the 260 MB L3 cache of our machine, so the misses were L3 hits. With an index in main memory, each miss costs more, and so does not prefetching.

## Parallel: many queries

During queries the index is only read, so queries can run in parallel without locks. Each thread needs its own workspace: its own visited marks and heaps. At `ef` = 40 our search answered 45,000 queries per second on one thread, 91,000 on two and 166,000 on four.

Building in parallel is harder, because an insertion changes the links of its neighbours, and two threads may change the same node. hnswlib uses a mutex per node: a thread locks a node before it reads or changes its links. This is the next step of the concurrency ladder of the course, in Part IV.

## DiskANN and beyond

**DiskANN** (Suhas Jayaram Subramanya and others, Microsoft, 2019) is a graph index for more vectors than fit in memory. It has a single layer, built with a pruning rule like the heuristic but with a factor $$\alpha > 1$$: a candidate is skipped only if a kept neighbour is $$\alpha$$ times nearer to it. This keeps some longer links, so paths are short even without layers. The graph and the full vectors are stored on an SSD, one node with its links in one 4 KB block. PQ codes in memory guide the search, so every step reads one block. With this, a single machine searches a billion vectors in milliseconds.

Real applications also **filter**: "the nearest products that are in stock and cost less than 50 €". A graph search can skip such vectors in the results but still walk through them, or the database can keep a separate graph for a common filter. Vector databases differ most in how they handle this.

## Code to read

* Yury Malkov and Dmitry Yashunin: _Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs_ (arXiv 2016, IEEE TPAMI 2020), and Yury Malkov and others: _Approximate Nearest Neighbor Algorithm Based on Navigable Small World Graphs_ (Information Systems, 2014).
* hnswlib, the authors' header-only C++ library: in `hnswlib/hnswalg.h`, `searchBaseLayer` is our `search_layer`, `getNeighborsByHeuristic2` the heuristic and `mutuallyConnectNewElement` the linking of `insert`. Look for the `_mm_prefetch` calls, and for the mutex of every node that allows a parallel build.
* FAISS: `IndexHNSW` (`faiss/impl/HNSW.cpp`), also with scalar-quantized or PQ vectors.
* Lucene: `HnswGraphBuilder` and `HnswGraphSearcher` (Java), used by Elasticsearch and OpenSearch; pgvector, the vector index of PostgreSQL; Qdrant (Rust), Weaviate (Go) and Milvus (C++).
* Suhas Jayaram Subramanya and others: _DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node_ (NeurIPS 2019), and Microsoft's DiskANN repository.
* Martin Aumüller, Erik Bernhardsson and Alexander Faithfull: _ANN-Benchmarks: A Benchmarking Tool for Approximate Nearest Neighbor Algorithms_ (Information Systems, 2020): recall–speed charts like ours for dozens of libraries.
