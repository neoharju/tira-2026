# 17. C++ Tools, Hardware and First Kernels

In Parts I and II we measured algorithms by counting steps: an $$O(n \log n)$$ algorithm beats an $$O(n^2)$$ algorithm when $$n$$ is large. That is still true. But two programs with the same time complexity can differ in speed by a factor of 10 or 100. Large companies care about that factor: it is the difference between 10 servers and 1000 servers, or between a phone app that feels instant and one that feels slow.

In this part of the course we write C++ and make it fast. Every week has an algorithm and an *optimization part*. The optimization uses two tools that every modern CPU has:

* **SIMD** (single instruction, multiple data): one instruction works on many values at once, for example 8 additions in one step.
* **Threads**: several cores run parts of the program at the same time.

This first week has no new algorithm. Instead we learn the tools that you need every week: how to find bugs, how to measure, and how a CPU actually runs code. Then we write our first SIMD and parallel code, using small but real functions called **kernels**.

This part assumes that you can read and write basic C++: functions, `std::vector`, references and simple classes. If you need a refresher, [learncpp.com](https://www.learncpp.com/) is a good free tutorial.

### Sanitizers: let the program check itself

Here is a short program with a bug. Can you see it?

```cpp
#include <print>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3};
    int& first = v[0];
    v.push_back(4);             // may move the elements to a new array
    std::println("{}", first);  // reads the old array, which was freed
}
```

`first` refers to the first element of the vector. But `push_back` needs more space, so the vector allocates a bigger array, copies the elements there and frees the old array. Now `first` refers to freed memory. When we ran this program, it printed:

```
1476237434
```

The program did not crash. It printed a random number and continued, which is the worst kind of bug: it can stay hidden for a long time. In C++, reading freed memory is **undefined behaviour**: the language does not say what happens, and anything can happen.

A **sanitizer** is a compiler option that adds checks to the program. The `debug` preset uses two of them:

* **AddressSanitizer** finds memory errors: reading or writing outside an array, using memory after it was freed, and so on.
* **UndefinedBehaviorSanitizer** finds other undefined behaviour, for example an `int` that overflows.

With AddressSanitizer the same program stops immediately and says what went wrong (we shortened the output):

```
==10887==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010
READ of size 4 at 0x502000000010 thread T0
    ...
    #7 0x5558e56a2f0c in main uaf.cpp:8
```

The report says *what* happened (`heap-use-after-free`, a read of 4 bytes) and *where* (`uaf.cpp`, line 8). Further down, the report also shows where the memory was allocated and where it was freed. Programs run about 2 times slower with AddressSanitizer, which is fine while you write code.

UndefinedBehaviorSanitizer works the same way. This function overflows when `a + b` does not fit in an `int`:

```cpp
int average(int a, int b) { return (a + b) / 2; }
```

With the sanitizer, `average(2'000'000'000, 2'000'000'000)` gives:

```
overflow.cpp:3:39: runtime error: signed integer overflow: 2000000000 + 2000000000 cannot be represented in type 'int'
```

Without it, the function returned −147483648.

From now on, every task must pass its tests in the `debug` preset. The automatic grader checks this too.

### gdb: stop the program and look inside

A sanitizer tells you *where* a program goes wrong. To understand *why*, you often want to stop the program at that line and look at the variables. A **debugger** does that. On Linux the standard debugger is **gdb**.

```console
$ gdb --args ./build/debug/week17/w17_test -tc="task1*"
(gdb) break w17::moving_average
(gdb) run
(gdb) print i
(gdb) next
(gdb) backtrace
```

| Command | What it does |
| --- | --- |
| `break f` | Sets a breakpoint: the program stops when it reaches function `f` (or a line, `break file.cpp:17`). |
| `run` | Starts the program. |
| `print x` | Shows a variable or an expression. |
| `next` | Runs one line. |
| `step` | Runs one line, and goes into a function call. |
| `continue` | Runs until the next breakpoint. |
| `backtrace` | Shows the chain of function calls that led here. |

A breakpoint can also have a condition, for example `break file.cpp:17 if i == 1000`. Then the program stops only in the interesting round of a loop.

Use the `debug` preset with gdb. In the `release` build the compiler moves and removes code, and gdb often answers `<optimized out>`.

### Measuring with perf

Before you make code faster, measure where the time goes. On Linux the standard tool is **perf**:

```console
$ perf stat -e cycles,instructions,cache-misses,branch-misses ./build/release/week17/w17_bench task6
$ perf record -g ./build/release/week17/w17_bench task6
$ perf report
```

`perf stat` counts events while the program runs. The most useful numbers are:

* **cycles** and **instructions**. Their ratio, *instructions per cycle* (IPC), tells how busy the CPU is. A modern core can finish about 4 instructions per cycle. If your IPC is below 1, the CPU is mostly waiting, usually for memory.
* **cache-misses**: how often data was not in the cache (see the next sections).
* **branch-misses**: how often the CPU guessed the direction of an `if` wrong.

`perf record` stops the program a few thousand times per second and remembers which instruction was running. `perf report` then lists the functions that used the most time, and `perf annotate` shows the time of each line and instruction. The `release` preset adds debug information (`-g`), so perf can show source lines too.

perf reads the hardware counters of the CPU, so it does not work in every virtual machine. It works on the course machine and on most Linux computers.

### Compiler Explorer

[Compiler Explorer](https://godbolt.org/) shows the machine code that a compiler makes from your C++. Paste a function, choose GCC or Clang, and add the options `-O3 -march=x86-64-v3`. You will use it in this chapter to see whether a loop really uses SIMD instructions.

## How a CPU runs your code

A simple picture of a computer is: the CPU runs one instruction after another, and every instruction takes the same time. This picture is wrong in ways that matter for speed. Here is a more useful one.

**The CPU works on many instructions at the same time.** A modern core reads several instructions per cycle. It starts every instruction as soon as its inputs are ready, even if the instructions before it have not finished yet. One addition takes 1 cycle, but the core can start about 4 independent additions in every cycle. So there are two different numbers:

* **latency**: how long one instruction takes from its inputs to its result;
* **throughput**: how many such instructions the core can start per cycle.

When every instruction needs the result of the previous one (a **dependency chain**), only latency matters, and most of the core waits. When the instructions are independent, throughput matters, and the core is busy. Many optimizations in this course are about breaking long dependency chains.

**Memory is slow, so the CPU keeps copies in caches.** Reading a value from main memory (DRAM) takes about 80–100 ns. In that time a core could run several hundred instructions. That is why every core has small, fast memories called **caches**:

| Level | Typical size | Time to read |
| --- | --- | --- |
| L1 cache | 32–48 KB per core | about 1 ns (4–5 cycles) |
| L2 cache | 1–2 MB per core | about 4 ns |
| L3 cache | 16–64 MB, shared by the cores | about 15–20 ns |
| Main memory | many GB | about 80–100 ns |

If the data that you need is in L1, a read is almost free. If it is only in main memory, the read is about 100 times slower. For many programs, the number of cache misses decides the speed more than the number of instructions.

**The CPU guesses the direction of every branch.** An `if` statement becomes a *branch* instruction. The core does not wait to know which way the branch goes: it guesses and continues. If the guess was wrong, it throws the work away and starts again, which costs about 15–20 cycles. Branches that follow a pattern (like a loop condition) are guessed almost always right. Branches that depend on random data are guessed wrong half of the time. Sometimes it is faster to compute both results and choose one without a branch.

## Memory and cache lines

Memory moves between main memory and the caches in blocks of 64 bytes, called **cache lines**. When you read one `int` (4 bytes), the CPU loads the whole line: that `int` and the 15 next to it. Reading those 15 is now almost free.

This has a big effect on how you should walk through data. The following figure reads a $$4 \times 16$$ matrix of `int`s. C++ stores a matrix row by row, so every row is exactly one cache line. The cache in the figure has room for only 2 lines (a real L1 cache has about 500–800, but real data is also much bigger).

{% include viz.html id="cache-lines" alt="A 4 by 16 matrix of ints, one cache line per row, read row by row (4 misses) and column by column (64 misses) through a cache of two lines." %}

Reading row by row, one miss brings 16 values, so there are only 4 misses. Reading column by column, every read jumps to another line, and a line is thrown out of the cache before we come back to it. Every read is a miss: the same work is about 13 times slower. The rule is simple: **access memory in the order in which it is stored**, and keep the data that you use together close together.

### Array of structs or struct of arrays

This rule also decides how to store data. Take an image of RGBA pixels, where every pixel has a red, green, blue and alpha (transparency) value of one byte each. There are two natural ways to store it:

```cpp
// Array of structs (AoS): R, G, B, A, R, G, B, A, ...
struct Rgba { std::uint8_t r, g, b, a; };
std::vector<Rgba> image;

// Struct of arrays (SoA): all reds, then all greens, ...
struct Planar { std::vector<std::uint8_t> r, g, b, a; };
```

In the **array of structs** (AoS) layout one pixel is in one place: good if you usually need all 4 values of a pixel. In the **struct of arrays** (SoA) layout every value is in its own array, called a *plane*: good if you process one kind of value for many pixels at once. The SoA layout is often much better for SIMD, as we will see next.

## SIMD

A normal (scalar) instruction adds two numbers. A **SIMD** instruction adds two *vectors* of numbers: the CPU has wide **registers** that hold many values, and one instruction works on all of them. Each value in a register is in its own **lane**.

On x86-64 CPUs there are several generations of SIMD instructions. This course uses two:

* **AVX2** has 16 registers of 256 bits. A register holds 32 bytes, 16 values of 16 bits, 8 `int`s or `float`s, or 4 values of 64 bits. All Intel CPUs since 2013 and AMD CPUs since 2017 have AVX2. The template compiles everything with `-march=x86-64-v3`, which allows AVX2.
* **AVX-512** has 32 registers of 512 bits, and *mask registers* that we use in week 18. Intel server CPUs and the newest AMD CPUs (Zen 4 and newer) have it. The course machine has it.

The following figure adds two arrays of 19 `int`s, first one element at a time, then 8 at a time with AVX2.

{% include viz.html id="simd-lanes" alt="Adding two arrays of 19 ints: one at a time takes 19 additions, AVX2 takes 2 vector additions and 3 single ones." %}

The AVX2 version needs only 2 vector additions for the first 16 elements. The last 3 elements do not fill a register, so a second, normal loop handles them. Every SIMD loop needs such a **tail**. Another way is to make the arrays a multiple of 8 long.

There are three ways to get SIMD code, from easy to hard.

### 1. Automatic vectorization

The easiest way is to let the compiler do it. With `-O3`, GCC and Clang try to **vectorize** every loop: they rewrite it to use SIMD instructions. The compiler can tell you whether it succeeded. Add these options to the compile command (or to `CMAKE_CXX_FLAGS`):

| Compiler | Successes | Failures and reasons |
| --- | --- | --- |
| GCC | `-fopt-info-vec-optimized` | `-fopt-info-vec-missed` |
| Clang | `-Rpass=loop-vectorize` | `-Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize` |

For example, this is GCC's report for a loop that it vectorized:

```
task2_blend_plane.cpp:10:31: optimized: loop vectorized using 32 byte vectors
task2_blend_plane.cpp:10:31: optimized:  loop versioned for vectorization because of possible aliasing
```

*32 byte vectors* means AVX2 registers. *Versioned because of possible aliasing* means this: the compiler could not be sure that the output array does not overlap the input arrays. So it made two versions of the loop, and the program chooses one when it runs.

The compiler gives up quickly. Typical reasons are:

* The loop calls a function that the compiler cannot see, for example a function in another `.cpp` file. The compiler does not know what the function does, so it cannot run 8 calls at once.
* The loop has an early `break`, or the number of rounds is not known when the loop starts.
* One round needs the result of the previous round, like `a[i] += a[i - 1]`.
* The data is not contiguous, for example `a[index[i]]` or a linked list.

Small changes help too. Use the smallest type that is large enough: 16 values of 16 bits fit in an AVX2 register, but only 8 values of 32 bits. If the compiler thinks it is unsafe to vectorize but you know it is safe, you can say so with `#pragma omp simd` before the loop. It needs the compiler option `-fopenmp` or `-fopenmp-simd` (the template uses `-fopenmp`).

### 2. Intrinsics

When the compiler does not find a good SIMD version, we write it ourselves with **intrinsics**: functions that each become one SIMD instruction. They are declared in `<immintrin.h>`. The names look strange at first but follow a pattern:

* `_mm256_` is a 256-bit (AVX2) instruction, `_mm512_` is AVX-512 and `_mm_` is 128-bit SSE;
* then comes the operation, for example `add`, `min`, `loadu` (load from any address);
* the end says the type of the lanes: `epi8`, `epi16`, `epi32` and `epi64` are signed integers of 8 to 64 bits, `epu8` and so on are unsigned, `ps` is `float` and `pd` is `double`.

The types `__m256i` and `__m512i` are registers of integers. The [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html) lists every intrinsic with its latency and throughput.

Our first example makes an image brighter: it adds a constant to every byte. A byte is at most 255, so the sum must stop at 255 instead of wrapping around: 200 + 100 must give 255, not 44. This is called **saturating** arithmetic, and SIMD has instructions for it: `_mm256_adds_epu8` adds 32 pairs of unsigned bytes with saturation.

```cpp
#include <immintrin.h>

#include <algorithm>
#include <cstdint>
#include <span>

// Adds `amount` to every byte, but not above 255.
void brighten(std::span<std::uint8_t> pixels, std::uint8_t amount) {
    const __m256i add = _mm256_set1_epi8(static_cast<char>(amount));  // 32 copies
    std::size_t i = 0;
    for (; i + 32 <= pixels.size(); i += 32) {
        auto* p = reinterpret_cast<__m256i*>(pixels.data() + i);
        _mm256_storeu_si256(p, _mm256_adds_epu8(_mm256_loadu_si256(p), add));
    }
    for (; i < pixels.size(); ++i)  // the tail: at most 31 bytes
        pixels[i] = static_cast<std::uint8_t>(std::min(255, pixels[i] + amount));
}
```

`_mm256_set1_epi8` makes a register with 32 copies of the same byte. `_mm256_loadu_si256` loads 32 bytes from any address, and `_mm256_storeu_si256` stores them back. The `u` means *unaligned*: the address does not need to be a multiple of 32.

### 3. Wider lanes for multiplication

Blending two images needs multiplication: the result is between the source pixel $$s$$ and the destination pixel $$d$$, depending on the alpha value $$a$$ of the source:

$$\text{out} = \frac{s \cdot a + d \cdot (255 - a) + 127}{255}$$

(rounded down; the $$+127$$ rounds to the nearest value). The products do not fit in a byte: $$255 \cdot 255 = 65025$$. So we first **widen** the bytes to 16-bit lanes, compute, and then **narrow** the result back to bytes:

* `_mm256_unpacklo_epi8(x, zero)` and `_mm256_unpackhi_epi8(x, zero)` make two registers of sixteen 16-bit lanes from one register of 32 bytes. Be careful: AVX2 works in two 128-bit halves, so `unpacklo` takes bytes 0–7 *and* 16–23, and `unpackhi` takes bytes 8–15 and 24–31.
* `_mm256_mullo_epi16` multiplies sixteen 16-bit lanes and `_mm256_add_epi16` adds them.
* `_mm256_packus_epi16(lo, hi)` packs two registers of 16-bit lanes back to 32 bytes. It works in the same two halves, so after an `unpacklo`/`unpackhi` pair the bytes come back in their original order.

There is no instruction for dividing integers. But division by a constant can be done with a multiplication: for every 16-bit $$x$$,

$$\left\lfloor \frac{x}{255} \right\rfloor = \left\lfloor \frac{x \cdot 32897}{2^{23}} \right\rfloor.$$

The intrinsic `_mm256_mulhi_epu16(x, c)` computes the upper 16 bits of the 32-bit product $$x \cdot c$$, that is, $$\lfloor x \cdot c / 2^{16} \rfloor$$, and `_mm256_srli_epi16(y, 7)` shifts right by 7 more bits. Compilers use the same trick when you write `x / 255`.

In the array-of-structs layout there is one more problem: every byte must be multiplied by the alpha value of *its own* pixel, but alpha is only in every 4th byte. The following figure shows how the two layouts look in a register.

{% include viz.html id="aos-soa" alt="AoS: 8 pixels fill one 32-byte register and alpha must be copied to every byte of its pixel with a shuffle. SoA: 32 values of one plane fill a register and no shuffle is needed." %}

`_mm256_shuffle_epi8(x, mask)` builds a new register from the bytes of `x`: byte $$j$$ of the result is the byte of `x` whose index is in byte $$j$$ of `mask`. With the mask $$3, 3, 3, 3, 7, 7, 7, 7, 11, \ldots$$ every byte gets the alpha of its pixel. (This shuffle also works in two 128-bit halves, so the mask uses indices 0–15 in both halves.)

Task 2 blends planes in the SoA layout and lets the compiler vectorize. Task 3 blends RGBA pixels with intrinsics. On our test machine (a 4-core Intel Xeon of the Emerald Rapids generation, with GCC 16) both were about 9 times faster than the one-pixel-at-a-time version, for an image of $$512 \times 512$$ pixels.

### When SIMD does not help: the memory wall

We measured the AVX2 blending of task 3 for images of different sizes:

| Image | 256 × 256 | 512 × 512 | 1024 × 1024 | 2048 × 2048 | 4096 × 4096 |
| --- | --- | --- | --- | --- | --- |
| Data (input + output) | 768 KB | 3 MB | 12 MB | 48 MB | 192 MB |
| AVX2 speedup | 12× | 9.4× | 9.0× | 6.5× | 4.0× |

For small images all the data fits in the L2 or L3 cache, and the speedup is close to what the instructions allow. (The L3 cache of our test machine is large: 260 MB, shared by all cores of the processor.) For large images the CPU must bring every byte from main memory, and memory cannot deliver bytes as fast as AVX2 uses them. The loop is then **memory-bound**: its speed depends on the memory bandwidth, not on the instructions. Faster instructions cannot help anymore, but using fewer bytes can (for example, smaller types or fewer passes over the data).

## Threads with OpenMP

SIMD makes one core faster. To use all cores, we need **threads**: parts of the program that run at the same time. Our test machine has 4 cores, the course machine has more, and big servers have over 100.

The easiest way to use threads in C++ is **OpenMP**, a standard that most compilers support (with the option `-fopenmp`, which the template uses). You add a `#pragma` line before a loop, and OpenMP splits the rounds of the loop between threads:

```cpp
#include <cstdint>
#include <span>

std::int64_t sum(std::span<const std::int32_t> a) {
    const std::int32_t* p = a.data();
    const std::size_t n = a.size();
    std::int64_t s = 0;
#pragma omp parallel for reduction(+ : s)
    for (std::size_t i = 0; i < n; ++i) s += p[i];
    return s;
}
```

`#pragma omp parallel for` starts a team of threads (by default one per hardware thread; the environment variable `OMP_NUM_THREADS` changes this) and gives every thread a part of the rounds. `reduction(+ : s)` gives every thread its own copy of `s`, and at the end OpenMP adds the copies together. Without `reduction`, the threads would all update the same `s`, and the result would be wrong, as we will see in the next section.

`#pragma omp parallel for simd` asks for SIMD inside each thread too.

### The same with std::jthread

OpenMP is convenient, but it is good to know what it does for you. C++20 has `std::jthread`, a thread that waits for its function to finish when the `std::jthread` object is destroyed:

```cpp
#include <cstdint>
#include <numeric>
#include <span>
#include <thread>
#include <vector>

std::int64_t sum_threads(std::span<const std::int32_t> a, unsigned threads) {
    std::vector<std::int64_t> part(threads);
    {
        std::vector<std::jthread> pool;
        for (unsigned t = 0; t < threads; ++t) {
            pool.emplace_back([&, t] {
                std::size_t begin = a.size() * t / threads, end = a.size() * (t + 1) / threads;
                std::int64_t s = 0;  // a local variable: no other thread uses it
                for (std::size_t i = begin; i < end; ++i) s += a[i];
                part[t] = s;  // one write at the end
            });
        }
    }  // here the destructors of the jthreads wait for the threads to finish
    return std::reduce(part.begin(), part.end());
}
```

Thread `t` sums the part of the array from `a.size() * t / threads` to `a.size() * (t + 1) / threads`. Then the main thread adds the partial sums. This pattern is called **partition and merge**, and most parallel code in this part of the course uses it. Split the work into independent parts. Let every thread work on its own part, with its own variables. Combine the results at the end.

The lambda captures `t` by value (`[&, t]`) and everything else by reference. If it captured `t` by reference, the thread could see a later value of the loop variable.

### Amdahl's law

If a program takes time 1 with one thread, and a fraction $$p$$ of the work can run in parallel, then with $$T$$ threads it takes at least $$(1 - p) + p / T$$. The **speedup** is at most

$$\frac{1}{(1 - p) + p / T}.$$

This is **Amdahl's law**. The sequential part $$1 - p$$ does not get faster, and it soon decides the total time:

{% include viz.html id="amdahl" alt="Speedup as a function of the number of threads for p = 0.5, 0.9, 0.95 and 0.99: the curves flatten at 2, 10, 20 and 100." %}

With $$p = 0.9$$, 64 threads give a speedup of only 8.8, and no number of threads gives more than 10. So in parallel code we must make *everything* parallel: also the merging of the results, the allocation of memory, and the reading of the input.

There is a second limit: the memory bandwidth. On our test machine, one thread summed 1 GB of `int`s at about 8 GB/s, and four threads at about 27 GB/s, so the sum was about 3.5 times faster. One core cannot use all of the bandwidth, because it can wait for only a limited number of cache misses at a time. But all cores share the same memory, so with enough threads a memory-bound loop stops getting faster. A loop that does more work per byte scales further.

## Data races

Threads make a new kind of bug possible. Let's run the sum without `reduction`:

```cpp
#include <print>
#include <vector>

int main() {
    std::vector<int> a(1'000'000, 1);
    long sum = 0;
#pragma omp parallel for
    for (std::size_t i = 0; i < a.size(); ++i) sum += a[i];
    std::println("{}", sum);
}
```

The right answer is 1000000. With 4 threads the program printed:

```
250000
```

The following figure shows what goes wrong. `sum += a[i]` is not one step for the CPU but three: load `sum` into a register, add, and store the register back.

{% include viz.html id="data-race" alt="Two threads load sum = 5, both add 1 and both store 6, so one addition is lost. With a reduction each thread has its own sum and the result is 7." %}

When two threads do this at the same time, they can both load the same old value, and one of the two updates is lost. (Our program lost even more. The compiler kept `sum` in a register for the whole loop, so every thread stored only its own total, and the last store won.)

This is a **data race**: two threads access the same memory at the same time, at least one of them writes, and nothing forces an order between them. In C++ a data race is undefined behaviour, just like reading freed memory. The result depends on timing, so it can be right in a test and wrong in production.

The `tsan` preset compiles with **ThreadSanitizer**, which finds data races while the program runs. It reports the race above like this (shortened):

```
WARNING: ThreadSanitizer: data race (pid=10920)
  Write of size 8 at 0x7fffe2c85478 by thread T3:
    #0 main.omp_outlined_debug__ race.cpp:8:52
  Previous write of size 8 at 0x7fffe2c85478 by thread T1:
    #0 main.omp_outlined_debug__ race.cpp:8:52
```

ThreadSanitizer finds the race even in a run where the result happens to be right. Every parallel task in this course must pass its tests in the `tsan` preset.

A practical detail: GCC's OpenMP library is not built for ThreadSanitizer and causes false reports. That is why the `tsan` preset uses Clang with LLVM's OpenMP library, which tells ThreadSanitizer about OpenMP's own synchronization. The test preset also sets `TSAN_OPTIONS=ignore_noninstrumented_modules=1` for the same reason.

In Parts III and IV we avoid most races with one rule: **a thread writes only to memory that no other thread uses at the same time**. Reductions, per-thread copies and partition-and-merge all follow this rule. Locks and atomic operations come later, in Parts IV and V.

## Contention and false sharing

The simplest way to fix the race in a histogram is an **atomic** operation:

```cpp
#pragma omp parallel for
for (std::size_t i = 0; i < n; ++i) {
#pragma omp atomic
    ++counter[p[i]];
}
```

`#pragma omp atomic` makes the increment one indivisible step, so no update is lost. The result is correct. But for a histogram of $$2^{22}$$ values with 65,536 counters, four threads were **about 2.5 times slower** than one thread without atomics on our test machine: 13 ms instead of 5 ms. An atomic operation is much slower than a normal one, and when two cores update counters in the same cache line, the line must move between them. When threads fight over the same data like this, we call it **contention**.

The fix is again a per-thread copy: every thread counts into its own counters, and at the end the copies are added together. OpenMP can even do this for an array: `reduction(+ : h[:256])` gives every thread its own copy of the 256 values starting at `h`. For a large histogram the merge also takes time, and by Amdahl's law it must be parallel too: let every thread add up a different range of the counters.

### False sharing

There is a surprising version of contention, where the threads don't even use the same variables. Suppose that every thread increments its own counter, `counter[t]`, in a shared array. There is no data race: no two threads use the same variable. But the counters are 8 bytes each, side by side, so 8 of them share one cache line:

{% include viz.html id="false-sharing" alt="Two cores write their own counters, which are in the same cache line, so the line moves between the cores on every write. With alignas(64) each counter has its own line." %}

A core may write to a cache line only when no other core has a copy of it. So every write by thread 0 takes the line away from core 1, and every write by thread 1 takes it back. The line moves between the cores again and again, and the loop can be slower than with one thread. This is **false sharing**: the threads share a cache line but not data.

There are two fixes. Count in a local variable and write `counter[t]` only once at the end, as in the `std::jthread` example above. Or give every counter its own cache line:

```cpp
struct alignas(64) Counter {  // every Counter starts at a multiple of 64 bytes
    std::int64_t value = 0;
};
std::vector<Counter> counter(threads);
```

`alignas(64)` makes the size and the alignment of `Counter` 64 bytes, so two counters are never in the same line.

## A parallel prefix sum

The **prefix sum** of an array replaces every element with the sum of it and all elements before it: $$[3, 1, 4, 1]$$ becomes $$[3, 4, 8, 9]$$. It is used everywhere: in week 18 it turns counts into positions. The obvious loop `a[i] += a[i - 1]` is a dependency chain: every round needs the result of the round before. How can several threads help?

The answer is to do a little more work. Split the array into one block per thread and make **two passes**:

1. Every thread sums its own block. The threads do not depend on each other.
2. One thread computes, for every block, the sum of all blocks before it: the block's **offset**. This is a prefix sum of only $$T$$ values.
3. Every thread computes the prefix sum of its own block again, starting from its offset.

{% include viz.html id="prefix-sum" alt="A parallel prefix sum of 16 values with 4 threads: block sums 9, 22, 21 and 28, offsets 0, 9, 31 and 52, then each block is scanned from its offset." %}

Every element is now read twice, so with $$T$$ threads the speedup is less than $$T$$. On our machine the two passes over 16 MB were about 2 times faster than `std::inclusive_scan` with one thread. In OpenMP the three steps fit in one `#pragma omp parallel` region:

* `omp_get_thread_num()` and `omp_get_num_threads()` tell a thread which block is its own;
* `#pragma omp barrier` waits until all threads have finished pass 1;
* `#pragma omp single` lets only one thread compute the offsets.
