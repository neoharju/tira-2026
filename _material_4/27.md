# 27. Pages, Buffer Pool and Caching

A database is usually larger than the memory of its computer, so its data live on a disk, in **pages** of a fixed size: 8 KB in PostgreSQL, 16 KB in MySQL's InnoDB, 4 KB in SQLite. Last week's B+ tree had pages too, but all of them were in memory. This week the disk comes back.

Reading a page from an SSD takes about 100 µs; reading it from memory takes about 100 ns, a thousand times less. So every database keeps copies of the pages that it uses in memory, in the **buffer pool**. Every access to a table or an index asks the buffer pool for a page: "give me page 4711". If the page is there (a **hit**), the answer is immediate. Otherwise (a **miss**) the pool reads the page from the disk, and to make room, it throws out another page. Which page to throw out is the question of **caching**, and a good answer saves most of the disk reads.

This week we build the parts of a buffer pool:

* the **slotted page**, the format of a page that holds records of different sizes;
* the **buffer pool** itself, with pins and dirty pages, and the **CLOCK** policy that chooses which page to evict;
* **W-TinyLFU**, the policy of the cache library Caffeine, which remembers how *often* keys are used with a **Count-Min sketch**, and a sketch made faster with SIMD;
* a buffer pool for **many threads**, with shards and with **latches** on pages.

Why not let the operating system do all this with `mmap`, which maps a file into memory? Crotty, Leis and Pavlo explain it in a paper with a clear title: _Are You Sure You Want to Use MMAP in Your Database Management System?_ (2022). The operating system does not know which pages matter, it may evict any page at any moment, it writes changed pages back whenever it likes (which breaks the order of writes that crash recovery needs), and it reports I/O errors as signals. So most databases manage their pages themselves.

## Slotted pages

Rows of a table have different sizes: a name has 3 letters or 30. A **slotted page** stores records of any size in a page:

* a small **header** at the start;
* an array of **slots** after it, which grows towards the end of the page;
* the **records** at the end of the page, which grow towards the start;
* free space in the middle.

A slot holds the offset and the length of its record. Code outside the page refers to a record by its page and slot number, the **record id** (PostgreSQL calls it a ctid). The slot number never changes, even when the record moves inside the page, so indexes can keep record ids.

{% include viz.html id="slotted-page" alt="A page of 4096 bytes drawn as a bar: the header, the slot array growing from the left, free space, and the records growing from the right, each record in the color of its slot, erased records as hatched garbage. Buttons insert a small or a large record, erase a random record, and compact the page; the caption explains each step and the slot list shows offsets and lengths." %}

Erasing a record only marks its slot as free: the bytes of the record become **garbage** in the middle of the records area. A new record reuses the smallest free slot, so slot numbers stay small. When the free space between the slots and the records is too small, but the free space plus the garbage would be enough, the page **compacts**: it moves the records together at the end of the page, and the garbage becomes free space again. The records move, but their slot numbers do not.

The page is only bytes: no pointers, only offsets. So it can be written to the disk and read back as it is. In C++, the numbers in a page are read and written with `std::memcpy`:

```cpp
std::uint16_t load16(std::size_t at) const {
    std::uint16_t v{};
    std::memcpy(&v, bytes + at, sizeof v);  // one load: the compiler knows memcpy
    return v;
}
```

Why not `*reinterpret_cast<const std::uint16_t*>(bytes + at)`? Because that is undefined behaviour in C++: there is no `uint16_t` object at that address, and the address may not be aligned for one. `std::memcpy` of a small fixed size is always correct, and every compiler turns it into a single load instruction.

## The buffer pool

The buffer pool has a fixed number of **frames**, each of the size of a page, and a **page table**, a hash map from a page number to the frame that holds it. For every frame it knows:

* the **pin count**: how many users are using the page now. A pinned page may not leave the pool, because someone holds a pointer into its bytes;
* the **dirty** flag: whether someone changed the page. A dirty page must be written to the disk before its frame gets another page.

Using a page has three steps:

```cpp
std::byte* bytes = pool.fetch(page);  // pins the page: it stays in memory

// ... read or change the bytes ...

pool.unpin(page, changed);  // now the pool may evict it
```

`fetch` of a page that is not in the pool needs a frame. A frame that has never held a page is the easiest; otherwise the **replacement policy** chooses a **victim** among the frames whose pin count is 0. If the victim is dirty, it is written to the disk first. Then the new page is read into the frame. If every frame is pinned, `fetch` fails. A forgotten `unpin` is a leak: sooner or later every frame is pinned and the pool stops working. At the end of this chapter, guards make that mistake impossible.

Our disk is simulated in memory (`Disk` in `buffer_pool.hpp`), and it counts the pages that it reads and writes. These are the numbers that a buffer pool tries to keep small.

## Replacement: LRU and CLOCK

Which page should leave the pool? The best victim is the page that will be needed again the farthest in the future (Bélády, 1966). Nobody knows the future, so policies guess from the past. **LRU** (least recently used) evicts the page that has not been used for the longest time. It keeps the frames in a list: a hit moves the frame to the front of the list, and the victim is at the back.

LRU has a cost: every hit changes the list. With many threads, the list needs a lock, and every hit of every thread waits for it. **CLOCK** avoids the list. Every frame has a **reference bit**, and a hit only sets the bit of its frame: one store, no list and no lock. To find a victim, a **hand** goes around the frames like the hand of a clock. A frame with a set bit gets a second chance: the hand clears the bit and moves on. The first frame whose bit is already clear is the victim. Pinned frames are skipped. A page that is used often has its bit set again before the hand comes back, so it stays.

PostgreSQL uses a version of CLOCK, the **clock sweep**: instead of one bit, a frame has a usage count from 0 to 5. A hit adds one, and the hand subtracts one.

On our test machine, a replay of 4,000,000 page requests (Zipf's law over 65,536 pages, 4096 frames) gave hit ratios of 53.4 % with LRU and 52.3 % with CLOCK. A good LRU with its list in two arrays was not slower in one thread: 22 ns against 24 ns per request. The gain of CLOCK comes with threads, when the list would need a lock.

## Scans and frequency

LRU and CLOCK both keep the pages that were used *recently*. That fails badly for a **scan**: a query that reads a whole table once, such as `SELECT COUNT(*)`. Each page of the table is used once and never again, but each one pushes out a popular page. One large scan can empty the cache of all the popular pages.

Databases fight back in different ways:

* InnoDB's LRU list has a "young" part and an "old" part (37 % of the pool). A new page enters in the middle, at the head of the old part, and moves to the young part only if it is used again at least a second later. A scan passes through the old part and leaves the young part alone.
* PostgreSQL gives a large sequential scan a small ring of 256 KB of buffers of its own, so the scan cannot push out the rest of the pool.
* **LRU-K** (O'Neil, O'Neil and Weikum, 1993) evicts the page whose K-th most recent use is the oldest. With K = 2, a page that was used only once is evicted first.

All of these look at *how often* a page is used, not only at how recently. Counting how often every key is used would need memory for every key ever seen, also for the millions that are used once. A **sketch** counts in a small fixed amount of memory, and pays with a small error.

## The Count-Min sketch

A **Count-Min sketch** (Cormode and Muthukrishnan, 2005) has $$d$$ rows of $$w$$ counters, and a different hash function for each row. To count a key, add one to its counter in every row. To estimate how often a key was seen, take the **smallest** of its $$d$$ counters.

Two keys may share a counter in a row, and then the counter counts both. So a counter can be too large, but never too small, and the smallest of the $$d$$ counters is the one with the fewest strangers in it. With $$w = e/\varepsilon$$ and $$d = \ln(1/\delta)$$, the estimate is at most $$\varepsilon N$$ too large, with probability $$1 - \delta$$, where $$N$$ is the number of increments.

{% include viz.html id="count-min" alt="A Count-Min sketch of 4 rows of 16 counters. Buttons add the keys A to H, which are used with different frequencies; each addition lights up the key's 4 counters, one per row, and the estimate is the smallest of them, shown next to the true count. A toggle switches on the conservative update, which only increases the counters that are equal to the smallest; a button halves all counters (aging)." %}

TinyLFU, which we build next, uses a sketch with three ideas of its own:

* **Small counters.** A counter has 4 bits and stops at 15: TinyLFU only needs to know which of two keys is more popular, not by how much. 16 counters fit in a 64-bit word, and a sketch for a cache of $$n$$ keys needs about 2 bytes per key.
* **Aging.** After $$10 n$$ increments, every counter is halved. Old popularity fades, and a key that was popular yesterday does not stay forever. With 4-bit counters, halving the 16 counters of a word is one shift and one mask: `word = (word >> 1) & 0x7777777777777777`. This trick, computing on many small numbers packed in one ordinary register, is called **SWAR** (SIMD within a register).
* **The conservative update** (Estan and Varghese, 2002). Add one only to the counters that are equal to the smallest of the key's counters: the others are already too large because of other keys. The estimates become more accurate. Try the toggle in the figure.

## W-TinyLFU

**W-TinyLFU** (Einziger, Friedman and Manes, 2017) is the policy of Caffeine, a widely used cache library for Java, and it has three parts:

* a small **window**: an LRU list of 1 % of the capacity. Every new key enters here, so that a key that is suddenly popular gets a chance to show it;
* a **main** part for the other 99 %: a *segmented LRU* with a **probation** list and a **protected** list (at most 80 % of the main part). A key in probation that is used again moves to protected;
* **TinyLFU admission** between them. When the window is full, its oldest key is a **candidate** for the main part. If the main part is full too, the candidate meets the main part's **victim**, the last key of probation. The sketch decides: if the candidate has been used more often, it enters and the victim leaves; otherwise the candidate leaves.

{% include viz.html id="wtinylfu" alt="W-TinyLFU with a capacity of 10: a window of 1 key, a probation list and a protected list, drawn as rows of boxes, with the sketch estimate of each key. Step by step a trace of keys arrives: hits move keys forward or into protected, and when the window overflows, its candidate meets the victim of probation, and the one with the larger estimate stays. A scan of new keys passes through without pushing out the popular keys." %}

A scan cannot hurt W-TinyLFU: a scanned key is seen once, so it loses every duel with a popular key. The figure below runs LRU, CLOCK and W-TinyLFU on the same traces in your browser; move the size of the cache and compare.

## SIMD: a sketch in one cache line

The 4 counters of a key are in 4 rows, so in 4 different cache lines. A sketch of a large cache does not fit in the L2 cache, and then every increment and every estimate costs 4 cache misses. A **blocked** sketch puts all 4 counters of a key in one block of 64 bytes, one cache line: the key's hash chooses the block, and other bits of the hash choose one counter in each of the 4 rows of 16 counters inside the block. Blocked Bloom filters use the same idea (Putze, Sanders and Singler, 2007), and so does week 31.

Inside the block, the conservative update is a good job for SIMD. The block fits in two AVX2 registers, two rows in each. `_mm256_shuffle_epi8` (the instruction `pshufb`) is a table lookup: every byte of the result takes the byte of the first register at the position given by the same byte of the second register, within each 16-byte half. With the key's counter index in all bytes of each half, it copies the key's counter to every lane of its row:

```cpp
// idx01: the index of the key's counter of row 0 in every byte of the low half,
// and of row 1 in every byte of the high half
const __m256i c01 = _mm256_shuffle_epi8(rows01, idx01);
const __m256i c23 = _mm256_shuffle_epi8(rows23, idx23);
const __m256i m = _mm256_min_epu8(c01, c23);  // min(c0, c2) low, min(c1, c3) high
```

One more minimum with the two halves swapped gives the smallest of the 4 counters in every lane. Then a compare of the rows with that minimum, and with the indexes, selects the counters to increase, and `_mm256_adds_epu8` adds one where selected, stopping at 255. There is no branch at all. That matters: in scalar code, "is this counter equal to the minimum?" is a branch that the CPU cannot predict. Nanoseconds per increment plus estimate:

{: .grid-head }
| Counters | textbook | textbook, conservative | blocked | blocked, conservative | blocked, conservative, SIMD |
| --- | --- | --- | --- | --- | --- |
| 64 KB | 11.1 | 41.1 | 11.9 | 40.1 | 16.5 |
| 2 MB | 26.2 | 54.0 | 22.5 | 43.0 | 18.0 |
| 64 MB | 112.3 | 125.9 | 84.0 | 104.8 | 59.1 |
| 256 MB | 152.0 | 141.8 | 75.4 | 87.6 | 64.3 |

In the L2 cache (64 KB), the conservative update in scalar code costs almost four times the plain one, because of the wrong guesses; in SIMD, much of the difference disappears. In memory (64 MB), the blocked layout halves the time: one cache miss instead of four. Only both together are fast in both cases, and task 6 measures both. (Our virtual machine is noisy: runs differ by 20 % and more, so look at the shape of the table, not the last digit.)

The blocked sketch has a price: the counters of a block are shared by more keys, so they collide more often. With it, the hit ratios of W-TinyLFU in the table above were 0.3 to 1.3 points lower (31.0 % instead of 31.9 % with Zipf's law). Fast and a little less accurate, or slower and a little more accurate: such trade-offs are everywhere in a storage engine.

## Threads: a sharded pool

A buffer pool is used by all the threads of the database at the same time. The simplest correct pool puts one mutex around everything. Then every `fetch` and every `unpin` of every thread waits for the same lock, and the lock's cache line moves from core to core all the time. On our 4 cores, 1,000,000 fetches by 4 threads took 1027 ms with one lock.

The cure is **sharding**: many small pools, each with its own mutex and its own frames. A page always belongs to the same shard, chosen by a hash of its number, and two threads only wait for each other when their pages are in the same shard. With 64 shards, the same fetches took 272 ms: 3.8 times faster. PostgreSQL does the same with its page table: it is split into 128 partitions, each with its own lock.

The shards are aligned to 64 bytes (`alignas(64)` on the struct of a shard), so that two mutexes never share a cache line. Otherwise two threads that lock different shards would still fight for one cache line: false sharing, from chapter 17.

## Latches

A pin keeps a page in memory, but it does not stop two threads from changing the page at the same time, or one thread from reading while another writes. That needs a lock on the page's contents, which databases call a **latch**. (Database people say *lock* for the long-lived locks of transactions, which week 32 covers, and *latch* for the short locks that protect data structures in memory.)

Most accesses only read, so the latch is a reader-writer lock, `std::shared_mutex`: any number of readers at a time, or one writer alone. Task 8 wraps pinning and latching into **guards**, objects that release everything in their destructor (RAII):

```cpp
{
    ReadGuard root = pool.fetch_read(root_page);  // pinned and latched for reading

    // ... search in the page: root.bytes ...
}  // here the guard unlocks the latch and unpins the page, even after an exception
```

A guard can be moved but not copied, like `std::unique_ptr`: the pin and the latch have exactly one owner. One rule prevents deadlocks: **never wait for a latch while you hold the mutex of a shard**. `fetch_read` pins the page under the shard's mutex, releases the mutex, and only then waits for the latch. A pinned frame is never evicted, so the frame cannot change while the thread waits.

How much do shared latches help? We let 4 threads read the same page again and again, the root of a tree, which every search reads. When every read computes a checksum of the whole page (about 1 µs), shared latches were 2.3 to 2.8 times faster than exclusive ones: the readers really read at the same time. When every read takes only 8 bytes, shared latches were only 1.1 to 1.4 times faster. Then the time goes to pinning: the pin and the unpin lock the shard's mutex, and with 4 threads on one hot page, a pin and an unpin together took 640 ns, while a whole access with one thread took 79 ns.

So for hot pages, the mutex is the next bottleneck. Real systems make the hot path free of mutexes: PostgreSQL pins a page with one atomic compare-and-swap on the page's state. LeanStore and Umbra go further with **optimistic latches**: a reader does not write anything at all, it reads the page's version number before and after reading, and starts again if a writer changed the page in between. Part V of the course covers the atomic operations that this needs.

## Code to read

* PostgreSQL: `src/backend/storage/buffer/README` (pins, content locks and the clock sweep), `bufmgr.c`, and `freelist.c`, where `StrategyGetBuffer` runs the clock sweep and the small rings of buffers for large scans live.
* InnoDB, the storage engine of MySQL: `storage/innobase/buf/buf0lru.cc`, the LRU list with midpoint insertion (the settings `innodb_old_blocks_pct` and `innodb_old_blocks_time`).
* Caffeine by Ben Manes: W-TinyLFU in practice, with an adaptive window, and its `FrequencySketch`. The paper: Gil Einziger, Roy Friedman and Ben Manes: _TinyLFU: A Highly Efficient Cache Admission Policy_ (ACM Transactions on Storage, 2017).
* Elizabeth O'Neil, Patrick O'Neil and Gerhard Weikum: _The LRU-K Page Replacement Algorithm for Database Disk Buffering_ (SIGMOD 1993).
* Graham Cormode and S. Muthukrishnan: _An Improved Data Stream Summary: The Count-Min Sketch and its Applications_ (Journal of Algorithms, 2005).
* Andrew Crotty, Viktor Leis and Andrew Pavlo: _Are You Sure You Want to Use MMAP in Your Database Management System?_ (CIDR 2022).
* Viktor Leis and others: _LeanStore: In-Memory Data Management Beyond Main Memory_ (ICDE 2018): a buffer pool with optimistic latches that is as fast as an in-memory database when the data fit in memory.
* For more sketches: **HyperLogLog** (Flajolet, Fusy, Gandouet and Meunier, 2007) counts the *distinct* keys of a stream of billions in 12 KB, with an error of about 1 %. Redis offers it as `PFADD` and `PFCOUNT`.
