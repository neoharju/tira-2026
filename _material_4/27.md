# 27. Pages, Buffer Pool and Caching

A database is usually larger than the memory of its computer. So its data live on a disk, in **pages** of a fixed size: 8 KB in PostgreSQL, 16 KB in MySQL's InnoDB, 4 KB in SQLite. Last week's B+ tree had pages too, but all of them were in memory. This week the disk comes back.

Reading a page from an SSD takes about 100 µs. Reading it from memory takes about 100 ns, a thousand times less. So every database keeps copies of the pages that it uses in memory, in the **buffer pool**. Every access to a table or an index asks the buffer pool for a page: "give me page 4711". If the page is there (a **hit**), the answer is immediate. If it is not there (a **miss**), the pool reads the page from the disk, and it throws out another page to make room. Which page to throw out is the question of **caching**. A good answer saves most of the disk reads.

Why not let the operating system do all this with `mmap`, which maps a file into memory? Crotty, Leis and Pavlo answer in a paper with a clear title: _Are You Sure You Want to Use MMAP in Your Database Management System?_ (2022). The operating system does not know which pages are important, and it may evict any page at any moment. It writes changed pages back when it wants to, which breaks the order of writes that crash recovery needs. And it reports I/O errors as signals. So most databases manage their pages themselves.

This week we build the parts of a buffer pool, from the bytes of one page up to many threads:

1. the **slotted page**, the format of a page that holds records of different sizes;
2. the **buffer pool**, with pins and dirty pages, and **CLOCK**, the policy that chooses which page to evict;
3. **W-TinyLFU**, the policy of the cache library Caffeine, which counts how *often* keys are used with a **Count-Min sketch**, and a sketch made faster with SIMD;
4. a buffer pool for **many threads**, with shards and with **latches** on pages.

The tasks are in the folder `cpp/week27`. The headers `page.hpp`, `buffer_pool.hpp`, `sketch.hpp`, `cache.hpp` and `sharded.hpp` describe every function exactly, with the rules that the tests check. Tasks 1–4 have no speed goal: their tests are the goal.

## Slotted pages

Rows of a table have different sizes: a name has 3 letters or 30. How do we put records of any size into a page of fixed size, and still find each record quickly? A **slotted page** has four parts:

* a small **header** at the start;
* an array of **slots** after it, which grows towards the end of the page;
* the **records** at the end of the page, which grow towards the start;
* free space in the middle.

A slot holds the offset and the length of its record. Code outside the page refers to a record by its page number and its slot number, the **record id** (PostgreSQL calls it a ctid). The slot number never changes, also when the record moves inside the page, so indexes can keep record ids. Choose a size and insert records, or click a record to erase it:

{% include viz.html id="slotted-page" alt="A page of 512 bytes drawn as a bar: the header, the slot array growing from the left, free space, and the records growing from the right, each record in the color of its slot, erased records as hatched garbage. A slider sets the size of the next record; buttons insert it and compact the page, and a click on a record erases it. A row of boxes counts the bytes of the header, the slot array, the free space, the garbage and the records, and says whether the next insert fits, fits after compacting, or does not fit." %}

Erasing a record only marks its slot as free: the bytes of the record become **garbage** in the middle of the records area. A new record reuses the smallest free slot, so slot numbers stay small. When the free space between the slots and the records is too small, but the free space plus the garbage is enough, the page **compacts**. It moves the records together at the end of the page, and the garbage becomes free space again. The records move, but their slot numbers do not. When even the free space plus the garbage is too small, the record does not fit, and a database puts it into another page.

The page is only bytes: no pointers, only offsets. So it can be written to the disk and read back as it is. In C++, the numbers in a page are read and written with `std::memcpy`:

```cpp
std::uint16_t load16(std::size_t at) const {
    std::uint16_t v{};
    std::memcpy(&v, bytes + at, sizeof v);  // one load: the compiler knows memcpy
    return v;
}
```

Why not `*reinterpret_cast<const std::uint16_t*>(bytes + at)`? Because that is undefined behaviour in C++: there is no `uint16_t` object at that address, and the address may not be aligned for one. `std::memcpy` of a small fixed size is always correct, and every compiler turns it into one load instruction.

## The buffer pool

Now we have pages. The buffer pool keeps some of them in memory. It has a fixed number of **frames**, each of the size of a page. A **page table**, a hash map, tells which frame holds which page. For each frame it knows two things:

* the **pin count**: how many users are using the page now. A pinned page may not leave the pool, because someone holds a pointer into its bytes;
* the **dirty** flag: whether someone changed the page. A dirty page must be written to the disk before its frame gets another page.

Using a page has three steps:

```cpp
std::byte* bytes = pool.fetch(page);  // pins the page: it stays in memory

// ... read or change the bytes ...

pool.unpin(page, changed);  // now the pool may evict it
```

`fetch` of a page that is not in the pool needs a frame. A frame that has never held a page is the easiest. Otherwise the **replacement policy** chooses a **victim** among the frames whose pin count is 0. If the victim is dirty, the pool writes it to the disk first. Then it reads the new page into the frame. If every frame is pinned, `fetch` fails. A forgotten `unpin` is a leak: sooner or later every frame is pinned, and the pool stops working. At the end of this chapter, guards make that mistake impossible.

Our disk is simulated in memory (`Disk` in `buffer_pool.hpp`), and it counts the pages that it reads and writes. A buffer pool tries to keep these numbers small. Which victim keeps them smallest?

## Replacement: LRU and CLOCK

The best victim is the page that is needed again the farthest in the future (Bélády, 1966). Nobody knows the future, so policies guess from the past. **LRU** (least recently used) evicts the page that has not been used for the longest time. It keeps the frames in a list: a hit moves the frame to the front of the list, and the victim is at the back.

LRU has a cost: every hit changes the list. With many threads, the list needs a lock, and every hit of every thread waits for it. **CLOCK** has no list. Each frame has a **reference bit**, and a hit only sets the bit of its frame: one store, no list and no lock. To find a victim, a **hand** goes around the frames like the hand of a clock:

* a pinned frame is skipped;
* a frame whose bit is set gets a **second chance**: the hand clears the bit and moves on;
* the first frame whose bit is already clear is the victim.

A page that is used often has its bit set again before the hand comes back, so it stays. Follow the hand step by step:

{% include viz.html id="buffer-pool" alt="A buffer pool of 4 frames in a row, with the hand of CLOCK above one of them, and a list of 11 read and write requests. Step by step each request is a hit, which sets the frame's reference bit, or a miss. On a miss the hand moves one frame per step: it skips a pinned frame, clears a set bit and moves on, or takes a frame whose bit is clear as the victim; a dirty victim is written to the disk first. Counters show hits, misses, pages read and pages written. Page 2, which is used often, is never evicted." %}

PostgreSQL uses a version of CLOCK, the **clock sweep**: instead of one bit, a frame has a usage count from 0 to 5. A hit adds one, and the hand subtracts one.

We replayed 4,000,000 page requests on our test machine (Zipf's law over 65,536 pages, 4096 frames). LRU hit 53.4 % of them, and CLOCK 52.3 %. A good LRU with its list in two arrays was not slower in one thread: 22 ns against 24 ns per request. The gain of CLOCK comes with threads, when the list would need a lock.

## Scans and frequency

LRU and CLOCK both keep the pages that were used *recently*. That fails badly for a **scan**: a query that reads a whole table once, such as `SELECT COUNT(*)`. Each page of the table is used once and never again, but each one pushes out a popular page. One large scan can empty the cache of all popular pages.

Databases fight back in different ways:

* InnoDB's LRU list has a "young" part and an "old" part (37 % of the pool). A new page enters in the middle, at the head of the old part. It moves to the young part only if it is used again at least a second later. A scan passes through the old part and leaves the young part alone.
* PostgreSQL gives a large sequential scan a small ring of 256 KB of buffers of its own, so the scan cannot push out the rest of the pool.
* **LRU-K** (O'Neil, O'Neil and Weikum, 1993) evicts the page whose K-th most recent use is the oldest. With K = 2, a page that was used only once is evicted first.

All of these look at *how often* a page is used, not only at how recently. But counting how often each key is used needs memory for every key ever seen, also for the millions of keys that are used once. Can we count in a small, fixed amount of memory? A **sketch** does it, and pays with a small error.

## The Count-Min sketch

A **Count-Min sketch** (Cormode and Muthukrishnan, 2005) has $$d$$ rows of $$w$$ counters, and a different hash function for each row. To count a key, add one to its counter in each row. To estimate how often a key was seen, take the **smallest** of its $$d$$ counters.

Two keys may share a counter in a row, and then the counter counts both keys. So a counter can be too large, but never too small, and the smallest of the $$d$$ counters is the one with the fewest strangers in it. With $$w = e/\varepsilon$$ and $$d = \ln(1/\delta)$$, the estimate is at most $$\varepsilon N$$ too large, with probability $$1 - \delta$$, where $$N$$ is the number of increments.

{% include viz.html id="count-min" alt="A Count-Min sketch of 4 rows of 16 counters. Buttons add the keys A to H, which are used with different frequencies; each addition lights up the key's 4 counters, one per row, and the estimate is the smallest of them, shown next to the true count. A toggle switches on the conservative update, which only increases the counters that are equal to the smallest; a button halves all counters (aging)." %}

TinyLFU, which we build next, uses a sketch with three ideas of its own:

* **Small counters.** A counter has 4 bits and stops at 15: TinyLFU only needs to know which of two keys is more popular, not by how much. 16 counters fit in a 64-bit word, and a sketch for a cache of $$n$$ keys needs about 2 bytes per key.
* **Aging.** After $$10 n$$ increments, every counter is halved. Old popularity fades, and a key that was popular yesterday does not stay forever. With 4-bit counters, halving the 16 counters of a word is one shift and one mask: `word = (word >> 1) & 0x7777777777777777`. This trick, computing on many small numbers packed in one ordinary register, is called **SWAR** (SIMD within a register).
* **The conservative update** (Estan and Varghese, 2002). Add one only to the counters that are equal to the smallest of the key's counters: the other counters are already too large because of other keys. The estimates become more accurate. Try the toggle in the figure.

## W-TinyLFU

Now we can count. How does a cache use the counts? **W-TinyLFU** (Einziger, Friedman and Manes, 2017) is the policy of Caffeine, a widely used cache library for Java. It has three parts:

* a small **window**: an LRU list of 1 % of the capacity. Every new key enters here, so that a key that is suddenly popular gets a chance to show it;
* a **main** part for the other 99 %: a *segmented LRU* with a **probation** list and a **protected** list (at most 80 % of the main part). A key in probation that is used again moves to protected;
* **TinyLFU admission** between them. When the window is full, its oldest key is a **candidate** for the main part. If the main part is full too, the candidate meets the main part's **victim**, the last key of probation. The sketch decides: if the candidate has been used more often, it enters and the victim leaves; otherwise the candidate leaves.

{% include viz.html id="wtinylfu" alt="W-TinyLFU with a capacity of 10: a window of 1 key, a probation list and a protected list, drawn as rows of boxes, with the sketch estimate of each key. Step by step a trace of keys arrives: hits move keys forward or into protected, and when the window overflows, its candidate meets the victim of probation, and the one with the larger estimate stays. A scan of new keys passes through without pushing out the popular keys." %}

A scan cannot hurt W-TinyLFU: a scanned key is seen once, so it loses every duel with a popular key. The figure below runs LRU, CLOCK and W-TinyLFU on the same traces in your browser. It also runs **OPT**, Bélády's policy, which knows the future: no real policy can beat it, so it shows how much room is left. Change the size of the cache and compare.

{% include viz.html id="cache-policies" alt="Hit ratios of LRU, CLOCK, W-TinyLFU and OPT (which knows the future) as bars, computed in the browser on four traces of 60,000 keys: Zipf's law, Zipf's law with scans, a loop over 500 keys, and a Zipf trace whose popular keys change. A slider sets the size of the cache. With the loop and a cache of fewer than 500 keys, LRU and CLOCK get 0 %, while OPT shows that about 60 % is possible, and the caption explains why." %}

Look at the loop with a cache of 300 keys. LRU and CLOCK get **0 %**. This is not a bug: it is the worst case of LRU. The loop uses the keys 1, 2, …, 500 and starts again. When a key comes back, 499 other keys were used after it, so it is the least recently used key, and LRU has just evicted exactly that key. OPT keeps 299 keys of the loop for ever and lets the others pass: about 60 %. W-TinyLFU gets almost as much, 59 %: a new key must be used more often than the victim to enter, so most of the cache keeps the same keys. Move the cache size to 500: then the whole loop fits, and every policy hits almost always.

Our C++ caches, with a capacity of 10,000 keys and traces of 4,000,000 accesses:

## SIMD: a sketch in one cache line

W-TinyLFU asks the sketch on every access, so the sketch must be fast. But the 4 counters of a key are in 4 rows, so in 4 different cache lines. A sketch of a large cache does not fit in the L2 cache, and then every increment and every estimate costs 4 cache misses. A **blocked** sketch puts all 4 counters of a key in one block of 64 bytes, one cache line. The key's hash chooses the block, and other bits of the hash choose one counter in each of the 4 rows of 16 counters inside the block. Blocked Bloom filters use the same idea (Putze, Sanders and Singler, 2007), and so does week 31.

Inside the block, the conservative update is a good job for SIMD. The block fits in two AVX2 registers, two rows in each. `_mm256_shuffle_epi8` (the instruction `pshufb`) is a table lookup. Each byte of the result takes a byte of the first register, and the same byte of the second register gives its position, within each 16-byte half. With the key's counter index in all bytes of each half, it copies the key's counter to every lane of its row:

```cpp
// idx01: the index of the key's counter of row 0 in every byte of the low half,
// and of row 1 in every byte of the high half
const __m256i c01 = _mm256_shuffle_epi8(rows01, idx01);
const __m256i c23 = _mm256_shuffle_epi8(rows23, idx23);
const __m256i m = _mm256_min_epu8(c01, c23);  // min(c0, c2) low, min(c1, c3) high
```

One more minimum with the two halves swapped gives the smallest of the 4 counters in every lane. Then a compare of the rows with that minimum, and with the indexes, selects the counters to increase. `_mm256_adds_epu8` adds one where selected, and it stops at 255. There is no branch at all. That is important: in scalar code, "is this counter equal to the minimum?" is a branch that the CPU cannot predict. Nanoseconds per increment plus estimate:

{: .grid-head }
| Counters | textbook | textbook, conservative | blocked | blocked, conservative | blocked, conservative, SIMD |
| --- | --- | --- | --- | --- | --- |
| 64 KB | 11.1 | 41.1 | 11.9 | 40.1 | 16.5 |
| 2 MB | 26.2 | 54.0 | 22.5 | 43.0 | 18.0 |
| 64 MB | 112.3 | 125.9 | 84.0 | 104.8 | 59.1 |
| 256 MB | 152.0 | 141.8 | 75.4 | 87.6 | 64.3 |

In the L2 cache (64 KB), the conservative update in scalar code costs almost four times the plain update, because of the wrong guesses. With SIMD, most of the difference disappears. In memory (64 MB), the blocked layout halves the time: one cache miss instead of four. Only both together are fast in both cases, and task 6 measures both. (Our virtual machine is noisy: runs differ by 20 % and more, so look at the shape of the table, not at the last digit.)

The blocked sketch has a price: the counters of a block are shared by more keys, so they collide more often. With it, the hit ratios of W-TinyLFU in the table above were 0.3 to 1.3 points lower (31.0 % instead of 31.9 % with Zipf's law). Fast and a little less accurate, or slower and a little more accurate: such trade-offs are everywhere in a storage engine.

## Threads: a sharded pool

So far one thread used the pool. But a buffer pool is used by all threads of the database at the same time. The simplest correct pool puts one mutex around everything. Then every `fetch` and every `unpin` of every thread waits for the same lock. And the cache line of the lock moves from core to core all the time. On our 4 cores, 1,000,000 fetches by 4 threads took 1027 ms with one lock.

The cure is **sharding**: many small pools, each with its own mutex and its own frames. A page always belongs to the same shard, chosen by a hash of its number. Two threads wait for each other only when their pages are in the same shard. With 64 shards, the same fetches took 272 ms: 3.8 times faster. PostgreSQL does the same with its page table: it is split into 128 partitions, each with its own lock.

The shards are aligned to 64 bytes (`alignas(64)` on the struct of a shard), so that two mutexes never share a cache line. Otherwise two threads that lock different shards would still fight for one cache line: false sharing, from chapter 17.

## Latches

Sharding made `fetch` fast. But a pin only keeps a page in memory. It does not stop two threads from changing the page at the same time, or one thread from reading while another thread writes. That needs a lock on the contents of the page, which databases call a **latch**. (Database people say *lock* for the long-lived locks of transactions, which week 32 covers, and *latch* for the short locks that protect data structures in memory.)

Most accesses only read, so the latch is a reader-writer lock, `std::shared_mutex`: any number of readers at a time, or one writer alone. Task 8 wraps pinning and latching into **guards**: objects that release everything in their destructor (RAII):

```cpp
{
    ReadGuard root = pool.fetch_read(root_page);  // pinned and latched for reading

    // ... search in the page: root.bytes ...
}  // here the guard unlocks the latch and unpins the page, even after an exception
```

A guard can be moved but not copied, like `std::unique_ptr`: the pin and the latch have exactly one owner. One rule prevents deadlocks: **never wait for a latch while you hold the mutex of a shard**. `fetch_read` pins the page under the shard's mutex, releases the mutex, and only then waits for the latch. A pinned frame is never evicted, so the frame cannot change while the thread waits.

How much do shared latches help? We let 4 threads read the same page again and again: the root of a tree, which every search reads. With a checksum of the whole page in every read (about 1 µs), shared latches were 2.3 to 2.8 times faster than exclusive ones. The readers really read at the same time. When every read takes only 8 bytes, shared latches were only 1.1 to 1.4 times faster. Then the time goes to pinning: the pin and the unpin lock the shard's mutex. With 4 threads on one hot page, a pin and an unpin together took 640 ns, while a whole access with one thread took 79 ns.

So for hot pages, the mutex is the next bottleneck. Real systems remove the mutex from the hot path: PostgreSQL pins a page with one atomic compare-and-swap on the page's state. LeanStore and Umbra go further with **optimistic latches**: a reader writes nothing at all. It reads the page's version number before and after it reads the page, and it starts again if a writer changed the page in between. Part V of the course covers the atomic operations that this needs.

## Time and space

For a pool of $$F$$ frames.

### Time

{: .fit }
| Operation | Time |
| --- | --- |
| slotted page: insert | $$O(\text{slots})$$ |
| slotted page: erase; compact | $$O(1)$$; $$O(\text{page size})$$ |
| `fetch`, a hit | $$O(1)$$ expected |
| `fetch`, a miss with CLOCK | $$O(1)$$ amortized, $$O(F)$$ worst case |
| LRU access | $$O(1)$$ |
| Count-Min: increment, estimate | $$O(d)$$ for $$d$$ rows |
| aging | $$O(1)$$ amortized |
| W-TinyLFU access | $$O(1)$$, plus the sketch |
| blocked sketch with SIMD | $$O(1)$$: one cache line |

An insert into a slotted page looks for the smallest free slot. A hit finds its frame in the page table, which is a hash map. On a miss, the hand of CLOCK moves at most two rounds; then comes a disk read, and a write if the victim is dirty. LRU needs a hash map and a list. Aging halves all counters, $$dw/16$$ words, every $$10n$$ increments.

CLOCK is $$O(1)$$ amortized because each step of the hand either evicts a frame or clears a bit, and each bit was set by an earlier hit: the steps are paid by the hits and the misses. Pinned frames break this argument, and if all frames are pinned, `fetch` fails after one round. The disk read dominates every miss: 100 µs against the 20–25 ns of a hit.

### Space

{: .fit }
| Algorithm or data | Space |
| --- | --- |
| slotted page | a header, and 4 bytes per slot |
| the pool with CLOCK | $$F$$ frames, a bit and a pin count each |
| LRU | $$O(F)$$ |
| Count-Min sketch | $$d \cdot w$$ counters |
| W-TinyLFU | the cache, and the sketch |
| blocked sketch | the same counters |

The sketch is small: about 2 bytes for each key that the cache can hold.

## Bonus: page checksums

A page travels from memory to the disk and back many times. A disk can return wrong bytes, and a crash can leave a page half written (a *torn page*). So databases store a **checksum** in each page and check it on every read. PostgreSQL does this when a cluster is created with data checksums, and since PostgreSQL 18 that is the default.

PostgreSQL's checksum ([`checksum_impl.h`](https://github.com/postgres/postgres/blob/HEAD/src/include/storage/checksum_impl.h)) is designed for SIMD. It views the page of 8 KB as 64 rows of 32 words of 32 bits, and it keeps **32 independent sums**, one per column. Each word goes into its sum with a step of the FNV-1a hash: XOR, multiply by the prime 16777619, and XOR with the value shifted right by 17. At the end, two rounds of zeros mix the sums, and the 32 sums are combined with XOR. 32 sums of 32 bits are exactly 4 AVX2 registers:

```cpp
// One step of FNV-1a in 8 lanes: t = sum ^ value; sum = t * prime ^ (t >> 17)
__m256i mix_in(__m256i sum, __m256i value) {
    const __m256i t = _mm256_xor_si256(sum, value);
    return _mm256_xor_si256(_mm256_mullo_epi32(t, _mm256_set1_epi32(16777619)), _mm256_srli_epi32(t, 17));
}

std::uint32_t page_checksum(const std::uint32_t* page) {  // 2048 words, pd_checksum set to 0
    __m256i sum[4];

    for (int r = 0; r < 4; ++r)  // the 32 start values of checksum_impl.h
        sum[r] = _mm256_loadu_si256(reinterpret_cast<const __m256i*>(checksum_offsets + 8 * r));

    for (int i = 0; i < 64; ++i)  // the 64 rows of 32 words
        for (int r = 0; r < 4; ++r)
            sum[r] = mix_in(sum[r], _mm256_loadu_si256(reinterpret_cast<const __m256i*>(page + 32 * i + 8 * r)));

    for (int round = 0; round < 2; ++round)
        for (int r = 0; r < 4; ++r)
            sum[r] = mix_in(sum[r], _mm256_setzero_si256());

    const __m256i x = _mm256_xor_si256(_mm256_xor_si256(sum[0], sum[1]), _mm256_xor_si256(sum[2], sum[3]));
    __m128i y = _mm_xor_si128(_mm256_castsi256_si128(x), _mm256_extracti128_si256(x, 1));
    y = _mm_xor_si128(y, _mm_shuffle_epi32(y, 0b0100'1110));  // 4 lanes to 2
    y = _mm_xor_si128(y, _mm_shuffle_epi32(y, 0b1011'0001));  // 2 lanes to 1
    return static_cast<std::uint32_t>(_mm_cvtsi128_si32(y));
}
```

PostgreSQL then XORs the block number into the result, so that it also finds a page written to the wrong place. Then it reduces the result to 16 bits: `(checksum % 65535) + 1`. We checked pages in the L2 cache on our machine. The scalar loop, compiled without vectorization, checked 8.1 GB/s, and the AVX2 version 25.9 GB/s: 3.2 times faster. GCC vectorizes the scalar loop by itself (26.5 GB/s), because the 32 sums are independent. That is the lesson of this design: the algorithm was chosen so that SIMD works, with intrinsics or without them. A single sum would be a chain of multiplications, and nothing could make it fast.
