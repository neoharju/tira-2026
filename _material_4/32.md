# 32. Concurrency Control and MVCC

A database serves many clients at the same time. PostgreSQL starts a process for each connection, and MySQL a thread. They all use the same tables and the same indexes, and a busy server has hundreds of them. The B+ tree of week 26 was for one thread. If two threads change it at the same time, one of them can follow a pointer into a node that the other is splitting, and the tree breaks. And a client often reads many rows: the sum of all accounts in a bank, for example. If other clients move money while it reads, the sum can be wrong.

This week we make the structures of a database safe for many threads, in three steps:

1. a B+ tree for many threads with a **latch** in every node: **latch coupling** for finds and scans, inserts that release latches at **safe nodes**, and an **optimistic descent**. We also measure what latches cost, and look at the B-link tree;
2. **multi-version concurrency control** (MVCC): a store that keeps old versions, so that every transaction reads its own **snapshot** while others write. We build **snapshot reads**, **commits** with "first updater wins", and **garbage collection**;
3. **testing** concurrent code: a check of a history of transactions against a sequential model, and a stress test that must catch six stores with planted bugs.

The tasks are in the folder `cpp/week32`. Keys and values are 64-bit numbers. Every task uses threads, so every test must also pass in the `tsan` preset, under ThreadSanitizer.

## Many threads, one database

What goes wrong without care? Take the tree of week 26 and two threads. Thread A searches for the key 52. It reads the root and finds that 52 is under the child $$c$$. Before A reads $$c$$, thread B inserts a key into $$c$$, $$c$$ is full, and it splits: the keys above 50 move to a new node $$c'$$. Now A reads $$c$$ and does not find 52: a key that is in the tree is "not found". Worse things can happen too. A can read a node while B moves its keys, and see half of the old node and half of the new one. In C++, two threads that use the same memory at the same time, when one of them writes, are a **data race**, and a data race is undefined behaviour: the compiler and the CPU may reorder memory accesses in ways that break any reasoning about the program. ThreadSanitizer finds data races while the program runs.

So every shared structure needs a rule for who may read and write it when. The first half of this chapter gives the rules for one tree. The second half gives the rules for transactions that read and write many keys.

## Latches and locks

Database people use two words, as in chapter 27:

{: .grid-head }
| | Latch | Lock |
| --- | --- | --- |
| protects | a data structure in memory: a node, a page | logical data: a row, a key, a range of keys |
| is held for | a few instructions, or one page read | a whole transaction, up to minutes |
| deadlocks | are avoided: latches are always taken in a fixed order | are found and broken by the lock manager |
| is made of | `std::mutex`, `std::shared_mutex`, atomics | a table of locks |

A **latch** of this chapter is `std::shared_mutex`: any number of readers at a time (`lock_shared`), or one writer alone (`lock`). Our tree (`btree.hpp`) has one latch in each node. A latch is not a lock: it is held only while a thread reads or changes the node, and it is released before the operation of the user ends. The **locks** of transactions come in the second half, and MVCC replaces most of them with versions.

## Latch coupling

How can thread A search the tree safely while thread B splits nodes? A holds the latch of a node while it reads the node. But between the parent and the child there is a gap: A has read the pointer to the child and released the parent, but it has not latched the child yet. A split can happen in that gap. **Latch coupling**, also called **crabbing** because it moves like a crab, closes the gap:

1. Latch the root.
2. Find the child, and **latch the child before you release the parent**.
3. Repeat until you are at the leaf.

A split of the child needs the latch of the parent too, because the new node must be added to the parent. So while A holds the parent, nobody can split the child, and when A holds the child, the split cannot happen under its feet. The root pointer itself needs a latch, because a split of the root makes a new root: `root_latch` protects it.

Can two threads wait for each other forever, a **deadlock**? Not if all threads take latches in the same order. Our rule: **from the root down, and along the leaves only from left to right**. A thread that holds a node waits only for nodes below it or to its right, so the waiting can never close a cycle. Watch the latches in a small tree:

{% include viz.html id="latch-crabbing" alt="A B+ tree of height 3 with nodes of at most 3 keys, and the latches held by one thread drawn on the nodes: S for shared, X for exclusive. A toggle chooses a find, an insert that releases latches at safe nodes, or an optimistic insert; a second toggle makes the leaf full. Step by step the thread latches the root, then each child before it releases the parent; an insert releases every latch above a node with room, and a full leaf splits while its parent is held. In the optimistic insert, the inner nodes get shared latches and the leaf an exclusive one; a full leaf makes it start again with exclusive latches. A counter gives the most latches held at the same time." %}

## Find and scan: shared latches

A find only reads, so it takes shared latches. Several finds can then be in the same node at the same time. In C++:

```cpp
std::optional<Value> ConcurrentTree::find(Key key) {
    root_latch.lock_shared();
    Node* n = root;
    n->latch.lock_shared();
    root_latch.unlock_shared();

    while (n->level > 0) {
        Node* child = n->children[child_index(n, key)];
        child->latch.lock_shared();  // the child first...
        n->latch.unlock_shared();    // ...then let go of the parent
        n = child;
    }

    // ... search the leaf n, release its latch, and return
}
```

A scan goes down to the leaf of its first key in the same way. Then it walks right along the leaves: it latches the next leaf, and only then releases the current one. A writer that splits a leaf links the new leaf to the right of the old one while it holds the old leaf exclusively, so a scan that waits for the old leaf finds the new link when it gets the latch. Every thread moves along the leaves only to the right, so the scans cannot deadlock either.

## Insert: safe nodes

An insert changes the leaf, and maybe more: if the leaf is full, it splits, and its parent gets a new key. If the parent is full too, it splits as well, and so on up. So an insert takes **exclusive** latches on its way down. Does it have to keep all of them until it is done? No. A node is **safe** for an insert if it has room for one more key. An insert below a safe node can add a key to it, but it cannot split it, so nothing above the safe node changes. So when an insert latches a safe node, it releases every latch above it, and `root_latch` too.

Most nodes are safe: a node of a B+ tree is 50 to 100 % full, and only a full node is unsafe. So most inserts hold only two latches at a time: a node and its child. The full nodes on the path stay latched, because they will split. If the root itself is unsafe, the insert keeps `root_latch`, because the root can split and a new root can come.

The given `insert_into_path(path, key, value)` does the inserting and the splitting. It needs the latched path, from the highest node that is still latched down to the leaf. So the task is only the latching. That is the point of this week: the splits are those of week 26, and the latches decide whether threads can use the tree together.

## Insert: optimistic descent

Exclusive latches have a cost: every insert takes the root exclusively, even if only for a moment. No other insert and no find can pass the root at that moment. Bayer and Schkolnick (1977) saw that most inserts do not split anything, and made the common case cheap. The **optimistic descent** goes down like a find, with shared latches, and takes only the leaf exclusively. If the leaf has room, the insert is done there. If the leaf is full, the insert releases it and starts again with exclusive latches. That costs a second descent, but only for the few inserts that split a leaf: with nodes of 64 keys and random keys, about one insert in 45.

An erase needs only the leaf too, because our nodes never merge. The given `validate()` allows nodes with few keys, or with none. PostgreSQL does the same: it never merges half-empty pages, and it removes a page only when the page is empty, during `VACUUM`. A tree that never merges never frees a node while other threads use the tree. Freeing a node that another thread may still read is a hard problem, and Part V solves it with epochs and hazard pointers.

## What latches cost

Now we can measure. We used 4 threads on a tree of a million random keys, with nodes of 64 keys:

{: .grid-head }
| Work of the 4 threads | Time |
| --- | --- |
| 4 million finds, no latches at all (correct only because nobody writes) | 315 ms |
| 4 million finds, one shared lock around the whole tree | 617 ms |
| 4 million finds, latch coupling with shared latches | 1277 ms |
| 1.6 million inserts, one lock around the whole tree | 1548 ms |
| 1.6 million inserts, `insert_coarse` | 2286 ms |
| 1.6 million inserts, exclusive latches released at safe nodes | 7504 ms |
| 1 million inserts into the tree of a million keys, one lock | 1197 ms |
| 1 million inserts into the tree of a million keys, optimistic descent | 1368 ms |

This is not what the textbook promises. Latch coupling is slower than one lock around the whole tree, and the inserts with safe nodes are the slowest of all. Why?

A shared latch is not free for a reader. `lock_shared` adds one to a counter of readers inside the latch, and `unlock_shared` subtracts one: each is an atomic write to memory. All 4 threads write the counters of the root and of `root_latch` in every operation. So the cache lines of these counters move from core to core all the time, and each move costs about a hundred nanoseconds, as the false sharing of chapter 17. A find with latch coupling makes about five such moves (`root_latch` and one latch per level), and the one lock only one. The inserts with safe nodes are even worse: each one takes `root_latch` and the root **exclusively**. With 4 threads, a thread often finds them taken, and then it sleeps in the kernel until the other thread wakes it up. One insert passes these latches to the next thread several times, while `insert_coarse` passes them once.

So when is latch coupling worth it? When a thread **waits while it holds latches**. In a database on a disk, the next node may not be in the buffer pool (chapter 27), and its read from the disk takes 100 µs. A lock around the whole tree stops every thread for those 100 µs, but latch coupling stops only the threads that need the same nodes. The second test of task 2 checks exactly this. And with many more cores than our 4, one lock stops everybody, while latch coupling lets threads work in different parts of the tree.

In-memory databases do better. With **optimistic lock coupling** (Leis and others, 2016), a reader writes nothing at all. Each node has a version number, and a writer increases it. A reader reads the version, reads the node, and reads the version again: if the version changed, a writer was there, and the reader starts again. Readers then scale like the line "no latches at all", and the tree is still correct. LeanStore and Umbra use it, and week 38 builds it with atomics.

## B-link trees

Lehman and Yao (1981) removed latch coupling from searches with a small change to the tree. In a **B-link tree**, every node, not only every leaf, has a link to its right sibling and a **high key**: the largest key that may be in the node. A split first moves the upper half of the node to a new right sibling and links it, and only later adds the separator to the parent. Between these two steps, the parent sends some keys to the old node although they now live in the new one. A search that arrives at a node and sees that its key is larger than the high key knows that the node has split. It follows the right link: it **moves right**.

{% include viz.html id="blink-tree" alt="A parent with two leaves of a B-link tree, each leaf with a high key and a link to its right sibling. Step by step, a reader for key 18 reads the parent and goes to the leaf of keys up to 20; before it arrives, a writer splits that leaf: the keys 16 and 18 move to a new right sibling, the old leaf gets the high key 14, and the parent does not know yet. The reader arrives, sees that 18 is larger than the high key 14, follows the right link, and finds 18. Last, the writer adds the separator to the parent." %}

So a search needs only one latch at a time, and an insert holds only a few latches, also during a split: at most three in the original algorithm. PostgreSQL's B-trees are B-link trees: its `nbtree/README` explains the details, also how the right links let a search continue while a page is split.

## Versions instead of locks

Now the second problem of this chapter: a transaction that reads many keys while other transactions write them. A bank has 64 accounts with 1000 euros each, and transactions move money from one account to another. A report reads all 64 accounts and adds them up. The sum must be 64,000. But if a transfer moves money from account 3 to account 40 while the report is between them, the report counts the money twice, or not at all.

The classic cure is **two-phase locking**: a transaction locks every row that it reads or writes, and it keeps all locks until it commits. Then the report would lock all accounts, and every transfer would wait for the report. A long report could stop all transfers for minutes.

**Multi-version concurrency control** (MVCC) keeps the old versions instead. A write does not change the value in place: it adds a new version. Each transaction reads a **snapshot**: the data as it was when the transaction began. So the report sees the accounts as they were at one moment, while transfers go on and make new versions. **Readers never wait for writers, and writers never wait for readers.** PostgreSQL, Oracle, MySQL's InnoDB, SQL Server's snapshot isolation, CockroachDB and many others work like this. You have seen MVCC already: the sequence numbers and snapshots of the LSM tree of week 31 are MVCC.

## Snapshot reads

Our store (`mvcc.hpp`) uses **timestamps**. A commit gets the next timestamp: 1, 2, 3, … A transaction begins with a **snapshot**: the newest commit timestamp at that moment. Each key has a **version chain**, from the newest version to the oldest. A version that is not committed yet is **pending**: its commit timestamp is 0, and it knows its writer. A transaction $$T$$ with snapshot $$s$$ sees, for a key:

1. its own pending version, if it has one (a transaction reads its own writes);
2. otherwise, the newest version with a commit timestamp $$\le s$$;
3. nothing, if there is no such version or if that version is a delete.

Pending versions of other transactions are invisible. Try snapshots and transactions:

{% include viz.html id="mvcc-chains" alt="Three keys with version chains drawn from the newest version on the left to the oldest on the right, each version with its value and its commit timestamp, or as pending with its writer. A timeline below shows transactions as bars from their begin to their commit. Step by step a script runs: T1 updates account A, T2 begins and reads the old value of A, T1 commits, T3 begins and reads the new value, and T2 still reads the old one. A slider chooses a snapshot, and the version that it sees in each chain is marked." %}

Databases store versions in different ways. PostgreSQL keeps every version as a row in the table, oldest first, with the ids of the transactions that made and deleted it. InnoDB and Oracle keep the newest version in place and rebuild older versions from an **undo log**. HyPer, Hekaton and our store keep chains from the newest to the oldest in memory. Wu and others compared these designs in 2017.

## Writes and commits

A write adds a pending version at the head of the chain. A pending version also works as a lock on its key: only one transaction at a time can write a key. What if two transactions want to change the same account? Transaction A reads 1000 and wants to write 900. Transaction B also read 1000 and wants to write 1100. If both commit, one of the changes is lost: a **lost update**. Our store uses the rule **first updater wins**. A write fails if

* another transaction has a pending version of the key: it was first, or
* the newest version of the key committed after the writer's snapshot: somebody else changed the key since the writer took its snapshot.

After a failed write, the transaction must abort, and the client can try again. PostgreSQL does the same in `REPEATABLE READ`: the second writer gets the error "could not serialize access due to concurrent update".

{% include viz.html id="first-updater" alt="Two transactions A and B, both with snapshot 4, and the chain of account 1. Step by step: A writes a pending version; B tries to write the same key and fails because A's version is pending; B aborts. In the second scenario, A commits at 5 first; then B, whose snapshot 4 is older than 5, tries to write and fails because a newer version committed after its snapshot." %}

A commit is more delicate than it looks. The commit takes the next timestamp, $$t$$, and writes it into each of its pending versions. If a transaction began in the middle of this, with snapshot $$t$$, it could see some versions of the commit with $$t$$ and others still pending: half of a transfer. So our commit holds `commit_latch` **exclusively** while it stamps its versions, and it publishes `last_commit` = $$t$$ only at the end. `begin` reads `last_commit` with `commit_latch` held **shared**, so it waits until the stamping is done. The latches are always taken in the same order (`active_mutex`, then `commit_latch`, then the latch of one shard), so no deadlock is possible.

How fast is it? 400,000 transfers took 357 ms on one thread, and 1108 ms on four threads: three times **longer**. Every transaction takes `commit_latch` twice and `active_mutex` twice, so all threads meet in the same few cache lines, as the root latches did in the tree. The **transaction manager** is a famous hot spot: PostgreSQL 14 made the snapshots of its `ProcArray` much cheaper for this reason. In-memory systems such as Silo and Hekaton take timestamps with one atomic instruction and avoid the shared lists altogether. Part V shows how.

## Garbage collection

Old versions pile up: each transfer adds two versions. When can a version go? When no transaction can see it any more. The oldest snapshot of the active transactions is the **watermark**. Every reader now, and every reader that begins later, has a snapshot $$\ge$$ the watermark. So in each chain, the reader needs at most the newest version with commit timestamp $$\le$$ the watermark, and the versions above it. Everything below that version can be freed. If that version is a delete and it is the newest version of its key, the key can go too.

{% include viz.html id="mvcc-gc" alt="A timeline of commit timestamps with the snapshots of three active transactions marked, and the watermark at the oldest of them. Above it, the version chains of four keys. Step by step garbage collection walks each chain, keeps the versions newer than the watermark and the newest version at or below it, and frees the older ones. Then the oldest transaction commits, the watermark moves right, and another round frees more versions." %}

A long transaction holds back the watermark, and then nothing older than its snapshot can be freed. In PostgreSQL this is a known problem: one forgotten open transaction makes the tables grow ("bloat") until it ends, because `VACUUM` cannot remove the old row versions. Our `gc()` freed 990,000 versions of 10,000 keys in 28.5 ms. It holds the latch of one shard at a time, so readers and writers of the other shards go on.

## What snapshot isolation allows

Our store gives **snapshot isolation**: every transaction reads one snapshot, and of two transactions that write the same key, only one commits. Is that enough to make every transaction behave as if it ran alone? Not quite. A hospital has a rule: at least one of its two doctors must be on call. Both are on call now. Alice and Bob each start a transaction at the same time. Each checks that the other doctor is on call, and then takes itself off call. Their snapshots both show two doctors on call, and they write different keys, so both commit. Now nobody is on call. This is **write skew**, and no order of the two transactions one after the other could give it.

{% include viz.html id="write-skew" alt="Two transactions, Alice and Bob, on a timeline, and the two keys alice_on_call and bob_on_call. Step by step both begin with the same snapshot where both doctors are on call, each reads the other doctor's key, each writes its own key to off call, and both commit because they wrote different keys. At the end the rule 'at least one doctor on call' is broken, and the caption explains that no serial order gives this result." %}

So snapshot isolation is not **serializable**. Berenson and others described its anomalies in 1995, in _A Critique of ANSI SQL Isolation Levels_. PostgreSQL's `SERIALIZABLE` level adds **serializable snapshot isolation** (Cahill, Röhm and Fekete, 2008): it tracks which transaction read what another one wrote, and it aborts a transaction when such reads could form a cycle. Oracle's level called `SERIALIZABLE` is plain snapshot isolation. The bonus of this chapter finds write skew in a history.

## Checking a history

How do you test code like this? A concurrent bug shows up in one run of a thousand, and the next run passes. ThreadSanitizer finds data races, but a store can hold its mutex in all the right places and still return wrong values. We need to check **what the transactions saw**.

The idea is simple. Run many transactions in many threads, and record for each one its snapshot, its commit timestamp (or that it aborted), and its operations with the values that its reads returned. This is a **history**. Then replay the history against a **sequential model**: apply the committed transactions one by one in the order of their commit timestamps, and check that every read returned what the model gives at the reader's snapshot. `history.hpp` has the exact rules, also for lost updates. A correct store passes every history, and a broken one fails some of them.

A read must tell which write it saw. So the stress test writes a **unique** value every time: then a read of the value 3,000,017 means "the write of thread 0, number 17", and the checker finds that write in the history.

Our checker checked a history of 200,000 transactions with a million operations in 139 ms.

## Stress tests and mutants

The checker needs histories that are likely to show the bugs. A good **stress test** for an MVCC store:

* uses **few keys** (8), so that transactions often write the same keys, and the conflicts happen;
* has **long readers** that read every key, wait a moment and read them again: their snapshot must not change, also while garbage collection runs;
* runs **garbage collection** in its own thread all the time;
* **aborts** some transactions on purpose, and handles the writes that fail;
* writes **unique values**, and records only the operations that succeeded.

How do we know that the stress test is good? As with the fuzz harness of week 26: we give it **mutants**. `copy_store.hpp` has a simple, correct store that copies all its data at every commit, and six versions of it with a planted bug each:

{: .grid-head }
| Mutant | Its bug | What shows it |
| --- | --- | --- |
| `lost_update` | commit does not check for newer versions | two overlapping transactions both write a key |
| `read_committed` | reads see the newest data, not the snapshot | a read sees a commit after the snapshot |
| `dirty_read` | reads see writes that are not committed | a read sees a value that no committed transaction wrote |
| `torn_commit` | a commit is published in two halves | a reader sees half of a transaction |
| `eager_gc` | garbage collection frees copies that snapshots still need | a long reader sees newer data |
| `keep_aborted` | an abort makes its writes visible | a read sees the value of an aborted write |

Every mutant holds its mutex for all shared data, so ThreadSanitizer finds nothing in them: only the history shows the bugs. This is how professionals test databases. **Jepsen** (Kyle Kingsbury) runs such tests on real distributed databases, with network failures added, and it has found isolation bugs in many of them. Its checker **Elle** finds anomalies even without timestamps: from unique values it rebuilds which transaction read or overwrote which, and looks for cycles.

Our stress test on our MvccStore ran 12,000 transactions in 4 threads, with garbage collection all the time, in 180 ms.

## Time and space

For a tree of $$n$$ keys with nodes of $$B$$ keys and height $$h = O(\log_B n)$$, and a store with $$v$$ versions.

### Time

{: .fit }
| Operation | Time | Latches held at once |
| --- | --- | --- |
| find with latch coupling | $$O(\log n)$$ | 2 |
| scan of $$k$$ keys | $$O(\log n + k)$$ | 2 |
| insert with safe nodes | $$O(\log n)$$ | 2 usually, $$h + 1$$ at most |
| optimistic insert, or erase | $$O(\log n)$$ | 2 |
| snapshot read | $$O(1 + c)$$ for a chain of $$c$$ versions newer than the snapshot | 1 |
| write | $$O(1)$$ expected | 1 |
| commit of $$w$$ writes | $$O(w)$$ | 2 |
| garbage collection | $$O(v)$$ | 2 |
| check of a history of $$m$$ operations | $$O(m \log m)$$ | |

The work per node of the tree is that of week 26. Latch coupling adds two latch operations per level, and each is an atomic write that can cost a cache miss when other cores use the same node: the table of "What latches cost" shows that this dominates in memory. An insert holds more than two latches only on a path of full nodes, and the optimistic insert restarts for the inserts that split a leaf, about one in $$B/2$$ for random keys. A snapshot read walks the versions that committed after its snapshot, so long chains make old snapshots slow: another reason for garbage collection. The checker sorts the commits and does a binary search in the versions of a key for every read.

| Data | Space |
| --- | --- |

## Bonus: write skew and serializable snapshots

Our checker accepts write skew, because snapshot isolation allows it. Can a checker find it? Write skew comes from two transactions that run at the same time, where each one **reads a key that the other one writes**. Cahill, Röhm and Fekete call such an edge a read-write **antidependency**: T1 read a version, and T2 wrote the next one. Fekete and others proved in 2005 that every anomaly of snapshot isolation needs two such edges in a row between transactions that overlap, and SSI builds on this. The simplest case is two transactions with an edge in each direction:

```cpp
// The keys that a transaction read before writing them itself, and the keys that it wrote.
std::set<Key> reads_of(const TxnRecord& t) {
    std::set<Key> read, written;

    for (const Op& op : t.ops) {
        if (op.kind == Op::read && !written.contains(op.key))
            read.insert(op.key);
        else if (op.kind != Op::read)
            written.insert(op.key);
    }

    return read;
}

std::set<Key> writes_of(const TxnRecord& t) {
    std::set<Key> written;
    for (const Op& op : t.ops)
        if (op.kind != Op::read)
            written.insert(op.key);
    return written;
}

bool overlap(const TxnRecord& a, const TxnRecord& b) {  // each began before the other committed
    return a.snapshot < b.commit && b.snapshot < a.commit;
}

// Two committed transactions that overlap, where each read a key that the other wrote.
std::optional<std::pair<std::size_t, std::size_t>> find_write_skew(const History& h) {
    for (std::size_t i = 0; i < h.size(); ++i)
        for (std::size_t j = i + 1; j < h.size(); ++j) {
            const TxnRecord& a = h[i];
            const TxnRecord& b = h[j];
            if (!a.commit || !b.commit || !overlap(a, b))
                continue;

            const auto meets = [](const std::set<Key>& x, const std::set<Key>& y) {
                return std::ranges::any_of(x, [&](Key k) { return y.contains(k); });
            };

            if (meets(reads_of(a), writes_of(b)) && meets(reads_of(b), writes_of(a)))
                return std::pair{i, j};
        }

    return std::nullopt;
}
```

This loop takes $$O(m^2)$$ time for $$m$$ transactions, which is fine for a test. PostgreSQL does the same work online: it keeps a lock that conflicts with nothing (`SIReadLock`) for every key that a serializable transaction reads, and it marks an edge when another transaction writes that key. When a transaction gets an edge in and an edge out, one of the transactions aborts.

The classic fix in the application is to **materialize the conflict**: make both transactions write the same key. If each doctor also writes a key `on_call_count`, the two transactions conflict on it, and first updater wins aborts one of them. `SELECT ... FOR UPDATE` in SQL does the same: it locks the rows that it reads as if it wrote them.

Bonus exercise (no points): run 4 threads of doctors on your `MvccStore`: a transaction reads both keys `alice` and `bob`, and if both are 1, it writes 0 to its own doctor; another thread sets both back to 1 now and then. Record the history, and count the write skews with `find_write_skew`. Then add a write of a shared key to every doctor transaction, and check that the write skews disappear, and that `check_history` still finds nothing.
