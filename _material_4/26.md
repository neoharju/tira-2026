# 26. B+ Trees

In 1970, Rudolf Bayer and Edward McCreight, two researchers at Boeing, invented the **B-tree**. More than fifty years later it is the index of almost every database: PostgreSQL, MySQL, SQLite, Oracle and SQL Server all keep their tables and indexes in B-trees, and so do file systems such as Btrfs and XFS. When you look up a user by name, or list the orders of the last week, a B-tree finds them.

Last week we built a static B+ tree: fast, but built once and never changed. This week the tree changes. We build a B+ tree in memory, with pages of 64 keys:

* **find**, **insert** with splits, **range scans** along the leaves, and **erase** with borrowing and merging;
* a **bulk load** that builds a whole tree from sorted data, also with threads;
* a search inside a page with **SIMD**, for 64-bit keys;
* a **fuzzer** that compares the tree with `std::map` on millions of random operations, to find the bugs that tests miss.

## Why not a binary tree?

`std::map` is a red-black tree: a balanced binary search tree with one node per key. Every node is allocated on its own and has three pointers (left, right and parent) and a color. Two things make it slow for large data:

* **The chain of loads.** A search follows one pointer per level: about 20 levels for a million keys. In a large map, every level is a cache miss, and every load must wait for the one before (chapter 25).
* **Memory.** A `std::map<std::uint64_t, std::uint64_t>` uses about 64 bytes for an entry of 16 bytes: the node has 32 bytes of pointers and color, and the memory allocator adds its own header.

On disk the argument is even stronger. A random read from an SSD takes about 100 µs and from a hard disk about 10 ms, and it always reads a whole page of several KB. A tree whose nodes are pages, with hundreds of keys each, finds any of a billion keys with 3 or 4 page reads.

A **B+ tree** is the B-tree of databases. All keys and values are in the **leaves**. The **inner nodes** above them hold only keys, copies that guide the search, so they have room for many children. And the leaves are linked to each other in key order, so that a range of keys is a walk along the leaves.

## Pages

Our tree (`bplus.hpp`) keeps its pages in two vectors, one for the leaves and one for the inner nodes. A page is known by its number, a 32-bit `PageId`, not by a pointer:

{: .code-title }
week26/bplus.hpp (shortened)

```cpp
using Key = std::uint64_t;
using Value = std::uint64_t;
using PageId = std::uint32_t;  // the number of a page in leaves or inners

struct alignas(64) Leaf {
    std::uint32_t count;
    PageId prev, next;  // the leaves on the left and on the right
    alignas(64) Key keys[64];
    Value values[64];
};

struct alignas(64) Inner {
    std::uint32_t count;
    alignas(64) Key keys[64];
    PageId children[65];
};

class BPlusTree {
public:
    std::optional<Value> find(Key key) const;                                 // task 1
    bool insert(Key key, Value value);                                        // task 2
    void scan(Key lo, Key hi, std::vector<std::pair<Key, Value>>& out) const;  // task 3
    bool erase(Key key);                                                      // task 4
    void validate() const;

    std::vector<Leaf, NoInit<Leaf>> leaves;
    std::vector<Inner, NoInit<Inner>> inners;
    PageId root = 0;
    int height = 1;
    std::size_t count = 0;  // the number of keys
};
```

Page numbers work like the page numbers of a database file, and they have two advantages over pointers. They stay valid when a vector grows and moves all of its pages, and they take half of the space. The keys are in their own array, separate from the values (a struct of arrays), so a search reads only keys: 64 keys are 512 bytes, 8 cache lines. A leaf takes 1088 bytes and an inner node 896.

The tree has rules, and `validate()` checks all of them:

1. The keys of every page are increasing.
2. In an inner node with the keys $$k_0 < k_1 < \dots < k_{c-1}$$, every key under child $$i$$ is $$\le k_i$$, and every key under child $$i + 1$$ is $$> k_i$$.
3. Every page has at most 64 keys, and every page except the root has at least 32: it is at least half full.
4. All leaves are at the same depth, the **height** of the tree. With height 1, the root is a leaf.
5. The leaves are linked in order: `next` goes to the leaf with the next larger keys, `prev` back.

Rule 3 keeps the tree low. With all pages full, a tree of height $$h$$ holds $$64 \cdot 65^{h-1}$$ keys: 4160 keys with height 2, 270,400 with height 3, 17.6 million with height 4 and 1.1 billion with height 5. With half-full pages it holds less, but even then a million keys need only 4 levels, where `std::map` has 20.

## Find

Rule 2 tells where to go. If $$c$$ keys of an inner node are less than $$x$$, then $$k_{c-1} < x \le k_c$$, and $$x$$ can only be under child $$c$$. In the leaf, the same count is the place where $$x$$ is, if it is in the tree. So the whole search is one function, used on every level: the number of keys less than $$x$$ in a sorted array. The tree calls it through a function pointer, `node_search`, which is `std::lower_bound` at first; in tasks 6 and 7 you write faster versions with SIMD.

For a million random keys, finding every key took 306 ms in our B+ tree and 1309 ms in `std::map`: 4.3 times faster. Most of the gain is fewer cache misses: 4 pages instead of 20 nodes.

## Insert and split

To insert a key, find its leaf. If the key is already there, replace its value. Otherwise put the key at its place in the leaf and move the larger keys one step right. If the leaf had room, that is all.

If the leaf was full, it now has 65 keys, one too many, and it **splits**:

* The first 33 keys stay, and the last 32 move to a new leaf, which is linked between the old leaf and its right neighbour.
* The parent needs a key between the two leaves: the largest key that stayed. It is put into the parent, with the new leaf as the child after it.
* If the parent was full too, it splits in the same way, with one difference: of its 65 keys, 32 stay, 32 move to a new inner node, and the middle key **moves up** to the next parent. (In a leaf the key is copied up, because every key must stay in a leaf; in an inner node it moves.)
* If the root splits, a new root is made above it, with one key and two children.

The last step is the only way the tree gets taller: at the top. That is why all leaves always have the same depth. Try it with pages of 4 keys:

{% include viz.html id="bplus-ops" alt="A B+ tree with pages of at most 4 keys, drawn level by level, with empty slots and the links between the leaves. Buttons insert a random key or a key larger than all others, erase a random key, scan a range, or reset the tree. Pages that split are marked orange, pages that borrow or merge purple, and a scan marks its path and the leaves that it reads in green. The caption explains every change." %}

In C++, the insert must remember the path from the root, the pages and the children taken, because the splits go back up. A small array is enough: the height is at most about 10. There is one trap. `new_leaf()` and `new_inner()` may grow the vector of pages, and a vector that grows moves all of its elements to new memory. A reference taken before is then a **dangling reference**:

```cpp
Leaf& left = leaves[page];
const PageId right = new_leaf();  // may move every page...
left.next = right;  // ...so this may write into freed memory
```

AddressSanitizer reports such a write as a *heap-use-after-free*. Take references to pages only after the new pages exist.

## Range scans

"All orders from Monday to Friday" is a **range query**, and range queries are the reason why databases use B+ trees and not hash tables. `scan(lo, hi, out)` finds the leaf where `lo` would be, and from there walks the keys in order: to the end of the leaf, then along `next` to the following leaf, until it finds a key larger than `hi`. The cost is one search, and then one page for every 45 to 64 results. Click *Scan* in the figure above to see one.

For 100,000 scans of about 100 keys each, our tree took 63 ms and `std::map` 379 ms. A `std::map` iterator jumps from node to node, and every node may be a cache miss. The tree reads pages of keys in order, which the hardware prefetcher of chapter 25 likes.

Two cases need care: `hi` may be $$2^{64} - 1$$, the largest key, so a loop like `while (key <= hi)` must stop for another reason too; and `lo` may be larger than `hi`, when the answer is empty.

## Erase, borrow and merge

To erase a key, find it in its leaf and move the larger keys one step left. If the leaf still has 32 keys or more, that is all. If it now has 31, it **underflows**, and the tree repairs it with the help of a **sibling**, a neighbour page with the same parent:

1. **Borrow.** If a sibling has more than 32 keys, move one key over: the largest key of the left sibling, or the smallest key of the right sibling. The ranges of the two pages change, so the key in the parent between them must change too.
2. **Merge.** If the siblings have only 32 keys each, nothing can be borrowed, but 31 + 32 keys fit in one page. Move all keys into the left page, fix the leaf links, give the right page back for reuse, and remove the key and the child of the right page from the parent.
3. **Up the tree.** After a merge the parent has one key less, and it may underflow in turn. Inner nodes borrow by **rotation**: the parent's key comes down into the page, and the sibling's key goes up in its place. When inner nodes merge, the parent's key between them comes down into the merged page.
4. **The root.** If an inner root loses its last key, its only child becomes the new root, and the tree gets one level lower: again at the top.

Real databases differ here. InnoDB merges a page with its neighbour when it falls below half full (its `MERGE_THRESHOLD`). PostgreSQL never merges half-empty pages: it removes a page only when it is completely empty, during `VACUUM`. Merges are complex and slow down concurrent access (week 32), and a page that gets empty often fills again soon.

For a million random keys, erasing them all took 304 ms in our tree and 1018 ms in `std::map`.

## How full are the pages?

A split leaves two half-full pages. How full are the pages on average? It depends on the order of the keys:

{% include viz.html id="fill-factor" alt="A step chart of the number of keys in each leaf of a B+ tree with pages of 64 keys, after 20,000 keys, from the smallest keys to the largest, with lines at 32 keys (the minimum) and at the average. A toggle chooses the order of the keys: random inserts (about 70 % full on average), increasing inserts (52 %), a bulk load (100 %), or a bulk load and then half of the keys erased (59 %)." %}

For **random** keys, a new half-full page fills slowly until it splits again. Andrew Yao proved in 1978 that the pages are then $$\ln 2 \approx 69\%$$ full on average. For **increasing** keys (ids and times, very common in databases), every new key goes to the last leaf, and the left half of every split never gets another key: all pages stay about half full. Our C++ tree with a million keys:

{: .grid-head }
| How the keys came | Leaves full | Bytes per key |
| --- | --- | --- |
| Bulk load (next section) | 100 % | 17.2 |
| Random inserts | 70 % | 24.9 |
| Increasing inserts | 52 % | 33.8 |
| Bulk load, then half of the keys erased at random | 59 % | 29.0 |
| `std::map` | | about 64 |

Databases handle increasing keys with a special case. When SQLite appends to the last page, it does not split it: `balance_quick()` starts a new page with only the new key. PostgreSQL splits the last page so that the left part stays 90 % full, and InnoDB notices that the inserts go to the right and splits at the place of the new key.

## Bulk loading

When a database creates an index on a table that already has data (`CREATE INDEX`), it does not insert the keys one by one. It sorts them and builds the tree **bottom up**: first all leaves, full from the left, and then each level above from the largest key of every page below it. The given `bulk_load` in `bplus.cpp` does this. Its only special case is the end of a level: if the last page would have fewer than 32 keys, the last two pages share their keys.

For a million random keys, sorting took about 100 ms and the bulk load about 10 ms, while inserting the keys one by one took 350 ms. And the tree from the bulk load is full, so it is smaller and faster to search.

The bulk load is easy to run in parallel, because every page can be filled on its own as soon as we know where its keys start. The sizes of all leaves are known before any leaf is filled: 64 keys each, except the last two. So every thread can take its own run of leaves, and then of the inner nodes of each level:

{% include viz.html id="bulk-load" alt="29 sorted keys are loaded into a B+ tree with pages of 4 keys. Three threads fill their own runs of leaves at the same time, shown in three colors; then the level above is made from the largest key of each leaf, and then the root." %}

There is one trap, from chapter 25. `std::vector::resize` writes zeros into every new page, in the thread that calls it: all page faults happen in one thread before the parallel part begins. That is why the vectors of pages use a small allocator, `NoInit`:

```cpp
template <class T>
struct NoInit : std::allocator<T> {
    using std::allocator<T>::allocator;

    template <class U>
    void construct(U* p) noexcept {
        ::new (static_cast<void*>(p)) U;  // default-initialized: nothing is written
    }

    template <class U, class... Args>
    void construct(U* p, Args&&... args) {
        ::new (static_cast<void*>(p)) U(std::forward<Args>(args)...);
    }
};
```

`resize` creates new elements by calling `construct(p)` of the allocator. The standard allocator does that with `U()`, which fills a struct without constructors with zeros. `NoInit` uses `U` without the parentheses, which leaves the memory as it is. So `resize` only reserves the memory, and each page is first touched by the thread that fills it. With zero-filled vectors our parallel bulk load was only 1.2 times faster on 4 threads; with `NoInit`, it is 2.3 times faster: 16 million keys took 187 ms on one thread and 81 ms on four.

## SIMD: searching a node

Our keys are 64-bit numbers, so an AVX2 register holds 4 of them and an AVX-512 register 8. AVX2 has a compare for 64-bit numbers, `_mm256_cmpgt_epi64`, but it compares **signed** numbers, and our keys are unsigned. For keys below $$2^{63}$$ there is no difference. A key of $$2^{63}$$ or more has its top bit set, and as a signed number it is negative: a signed compare says it is smaller than 5. In the figure below, choose the keys *some ≥ 2⁶³* and *no flip* to see it.

The trick is to **flip the top bit** of both numbers before a signed compare. This moves the unsigned range $$[0, 2^{64})$$ onto the signed range $$[-2^{63}, 2^{63})$$ without changing the order: 0 becomes the smallest signed number, and $$2^{64} - 1$$ the largest. In scalar code:

```cpp
constexpr std::uint64_t top = std::uint64_t{1} << 63;

// a < b for unsigned numbers, computed with a signed compare
bool less_unsigned(std::uint64_t a, std::uint64_t b) {
    return static_cast<std::int64_t>(a ^ top) < static_cast<std::int64_t>(b ^ top);
}
```

With AVX2, the XOR is `_mm256_xor_si256` with the top bit in all 4 lanes. AVX-512 does not need the trick: it has unsigned compares into a mask register, such as `_mm512_cmplt_epu64_mask`.

{% include viz.html id="node-search" alt="The 16 keys of a node in registers of 4 lanes (AVX2) or 8 lanes (AVX-512). Step by step every register is compared with x in one instruction: the results appear as bits under the keys, and the count of keys smaller than x grows. A slider sets x. A toggle makes the last four keys 2^63 or larger; with AVX2 and without the flip of the top bit, the signed compare counts them wrongly." %}

There are two ways to use the compares. The **early exit** compares 4 keys at a time and stops at the first register with a key $$\ge x$$. The **full scan** compares all keys of the node and counts the ones that are less than $$x$$: it does more work, but it has no branch that depends on the keys. The full scan wins clearly. 1,000,000 searches in 4096 nodes of 64 random keys (2 MB, in the L2 cache), in ns per search:

{: .grid-head }
| Node search | ns per search |
| --- | --- |
| `std::lower_bound` (the baseline) | 52.1 |
| scalar loop with early exit | 41.1 |
| scalar count of all keys, without branches | 31.2 |
| branchless binary search (chapter 25) | 17.2 |
| AVX2, early exit | 32.2 |
| AVX2, full scan with movemask and popcount | 18.7 |
| AVX2, full scan with the counts in a register | 16.9 |
| AVX-512, early exit | 28.6 |
| AVX-512, full scan | 14.5 |

The early exit stops at a random place, so the CPU guesses the branch wrong once in almost every search, and that costs more than the compares that it saves. The best AVX2 version does not even turn the compare results into bits. A compare gives $$-1$$ (all bits one) in every lane where the key is smaller, so subtracting the result from an accumulator register counts the keys in all lanes at once; the 4 lanes are added at the end. Interesting, too: the branchless binary search of chapter 25 is as fast as AVX2 here, and only AVX-512, with 8 keys per compare, beats it.

Two details matter for correctness. A node has `count` keys, from 0 to 64, and the search must read nothing at or after `keys[count]`: those places may not exist, and the tests use arrays of exactly `count` keys with AddressSanitizer. AVX2 has masked loads (`_mm256_maskload_epi64`) that do not read the lanes whose mask bit is off; or handle the last 0 to 3 keys with scalar code. AVX-512 has masked loads for any lanes, and its compares take a mask too. In the whole tree, `find` with the AVX2 node search was 2.5 times faster than with `std::lower_bound` in the nodes, and with AVX-512 2.6 times.

## Differential fuzzing

How do you know that your tree is right? Tests check the cases that someone thought of. Bugs live in the cases that nobody thought of: a borrow from the first child, a merge that empties the root, a key equal to a key of the parent, the key $$2^{64} - 1$$.

**Fuzzing** runs a program on millions of generated inputs. **libFuzzer**, a part of LLVM, is *coverage-guided*: it watches which branches of the program every input reaches. Inputs that reach new branches are kept in a **corpus**, and new inputs are made by changing the inputs of the corpus: flipping bits, inserting and removing bytes, joining two inputs. So the fuzzer learns, step by step, inputs that go deep into the code. Every input is run with AddressSanitizer and UndefinedBehaviorSanitizer, so a memory error anywhere is found too.

A crash is easy to see, but a wrong answer is not. **Differential testing** solves this: compare the tree with another implementation of the same thing, slow but surely right. For an ordered map we have `std::map`. The harness reads the input bytes as a list of operations, runs every operation on both maps, and compares every answer. Any difference is a bug in one of them, and it is almost never in `std::map`. This is our fuzz target, `fuzz.cpp`:

```cpp
extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    w26::BPlusTree tree;

    if (!w26::differential(std::span(data, size), tree))
        __builtin_trap();  // the answers differ: libFuzzer saves this input

    return 0;
}
```

`differential` is task 5. How it reads the bytes matters a lot. Random bytes rarely make a map interesting: with one key per operation and 64-bit keys, the map almost never sees the same key twice, and it needs 65 keys in one leaf before anything splits. A good harness:

* reads small keys often, so that keys repeat: replacing a value and erasing a key that is there must happen;
* reads keys near $$2^{63}$$ and $$2^{64}$$, where signed and unsigned order differ;
* has an operation that inserts many keys at once, so that a few hundred bytes are enough for splits and merges;
* compares the size after every operation, calls `validate()` when the map has it, and at the end compares everything.

{% include viz.html id="fuzz-loop" alt="A table of ten operations decoded from bytes, run on the map under test and on std::map, with both answers shown step by step. A toggle chooses a correct map or one of three bugs: a scan that leaves out hi, an insert that keeps the old value, or an erase that always says yes. With a bug, the first operation whose answers differ is marked red, and the input is saved." %}

How is a harness graded? A harness that always says "all fine" passes every correct map. So the tests of task 5 give your harness **mutants**: maps with one planted bug each (`mutants.hpp`), and your harness must catch every one of them in 1000 random inputs, without ever failing on a correct map. This is **mutation testing**, the standard way to test a test: a harness that cannot see a planted bug would not see the same bug in your tree. The grader has more mutants than the file.

Our harness, run on our tree, survived 137,718 inputs in 61 seconds. We then planted a bug in the tree: after a borrow from the right sibling, the key in the parent was not updated. libFuzzer found an input that shows it in 2 to 3 seconds. Run the fuzzer on your own tree:

```console
$ cmake --preset fuzz && cmake --build --preset fuzz --target w26_fuzz
$ mkdir -p corpus && ./build/fuzz/week26/w26_fuzz -max_total_time=60 corpus
```

An input that breaks the tree is saved as a file `crash-...`. Give it to the program to run it again, also in gdb, until the bug is fixed; `-minimize_crash=1` makes it shorter first. The `fuzz` preset uses Clang: every file is compiled with `-fsanitize=fuzzer-no-link`, which adds the coverage counters, and the fuzz target is linked with `-fsanitize=fuzzer`, which adds libFuzzer itself.

Fuzzing is how the industry finds bugs in C and C++ code today. Google's OSS-Fuzz runs fuzzers on more than 1000 open-source projects, and by 2023 it had helped to fix over 10,000 vulnerabilities and 36,000 bugs. SQLite, the most widely used database in the world, is tested this way every day.

## Code to read

* Rudolf Bayer and Edward McCreight: _Organization and Maintenance of Large Ordered Indexes_ (Acta Informatica, 1972), the first B-tree paper; and Douglas Comer: _The Ubiquitous B-Tree_ (ACM Computing Surveys, 1979), a survey of B-trees and their variants, the B+ tree among them.
* PostgreSQL: `src/backend/access/nbtree/README`. Its B-tree follows Lehman and Yao: every page has a link to its right sibling and a "high key", so that searches can run while pages split (week 32). It also explains why PostgreSQL deletes only empty pages.
* SQLite: `src/btree.c`. Pages on disk with cells of different sizes; `balance_nonroot()` spreads the cells over up to three siblings, and `balance_quick()` handles appends at the end.
* InnoDB, the storage engine of MySQL: `storage/innobase/btr/btr0btr.cc` (splits and merges) and `btr0cur.cc` (searches with a cursor).
* Abseil's `absl::btree_map` (`absl/container/internal/btree.h`): an in-memory B-tree that can replace `std::map`, with nodes of about 256 bytes, which uses less memory and has fewer cache misses.
