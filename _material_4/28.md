# 28. Hash Tables

B+ trees keep keys in order, so they can answer range queries. When nobody needs the order, a **hash table** is faster: a key's hash tells almost directly where the key is. Databases use hash tables everywhere: for `GROUP BY` and for joins, for their caches (last week's page table), and for their in-memory indexes. Last week's page table was `std::unordered_map`, the hash table of the C++ standard library. This week we see why it is slow, and build faster ones:

* **open addressing**: linear probing, **Robin Hood hashing** and cuckoo hashing;
* the **Swiss table** of Google's Abseil library and of Rust, which checks 16 slots with one SIMD compare;
* **hash flooding**, an attack that makes a hash table a thousand times slower, and how a good hash function stops it;
* lookups in **batches**, a hash map for **many threads**, and **consistent hashing**, which spreads keys over the servers of a distributed database.

## Why not std::unordered_map?

The C++ standard promises that a pointer to an element of an `unordered_map` stays valid when the table grows, and it offers a "bucket interface" that shows how the elements are chained. Both promises force one design: every element is a **node** of its own, allocated separately, and a bucket array points to lists of nodes. A lookup reads the bucket and then follows pointers to nodes: the chain of loads of chapter 25 again. Each entry of 16 bytes takes about 40 bytes of memory: the node with the key, the value and the next pointer, the memory allocator's header, and a share of the bucket array.

There is one more detail. In libstdc++, the hash of an integer is the integer itself, `std::hash<std::uint64_t>{}(x) == x`. That works only because libstdc++ uses a prime number of buckets, so that the bucket `x % prime` depends on all the bits of `x`. A division by a prime number in every lookup is not free either.

A **flat** hash table stores the keys and values in one array. This week's tables, measured against `std::unordered_map` with random 64-bit keys:

{: .grid-head }
| 1,000,000 keys | build: ns per insert | lookups: ns per lookup | dependent lookups: ns per lookup |
| --- | --- | --- | --- |
| `std::unordered_map` | 262 | 35 | 531 |
| Robin Hood | 156 | 33 | 311 |
| Swiss table, one byte at a time | 124 | 55 | 279 |
| Swiss table with SSE2 | 60 | 20 | 253 |

Building the table, where `unordered_map` allocates a node for every key, is where flat tables win most: 4.4 times faster. In a dependent lookup, the next key comes from the value found by the last lookup, so lookups cannot overlap, and the time is the latency of the cache misses: two misses or more for `unordered_map`, about one for a flat table. Independent lookups are closer, because the CPU overlaps the misses of many lookups at the same time (chapter 25), but the Swiss table with SIMD still wins.

## Open addressing

**Open addressing** puts every key in the slot array itself. A key belongs in its **home slot** `hash % capacity`. If another key took that slot, the key goes to the next free slot after it: this is **linear probing**. A lookup starts at the home slot and walks right until it finds the key or an empty slot. The slots after each other are in the same cache lines, so the walk is cheap, as long as it is short.

The walk gets long when the table is full. Keys that collide form **clusters**, and a cluster grows faster the longer it is, because every key whose home falls inside it ends up at its end. Knuth computed the expected number of slots that a lookup reads at load factor $$\alpha$$ (the share of full slots):

$$\frac{1}{2}\left(1 + \frac{1}{1 - \alpha}\right) \text{ for a key in the table}, \qquad \frac{1}{2}\left(1 + \frac{1}{(1 - \alpha)^2}\right) \text{ for a key not in it}.$$

At $$\alpha = 7/8$$ that is 4.5 slots for a hit, but 32.5 slots for a miss. So tables grow (double) before they are too full. And erasing needs care: emptying a slot in the middle of a cluster would cut the walk of every key behind it. Either the slot becomes a **tombstone**, which lookups walk over, or the keys behind it move back.

## Robin Hood hashing

**Robin Hood hashing** (Celis, Larson and Munro, 1985) changes one rule of insertion. Every slot knows how far its key is from home. When a new key walks along a cluster and meets a key that is *closer* to its home than the new key is to its own, the new key takes the slot, and the walk continues with the key it pushed out. It takes from the rich and gives to the poor.

The total distance stays the same, but the distances become equal. No key is very far from home, so the longest walk is short. And a lookup for a missing key can stop early: when it meets a key that is closer to its home than the lookup is to its own, the missing key would have been placed before that key, so it is not in the table.

Erasing uses a **backward shift** instead of tombstones: after the erased slot, every key that is not in its home slot moves one slot back, up to the first empty slot or the first key that is at home. The table looks exactly as if the erased key had never been inserted.

## Cuckoo hashing

**Cuckoo hashing** (Pagh and Rodler, 2001) gives every key exactly two possible slots, from two hash functions. A lookup reads at most these two slots: the worst case is constant, not just the average. An insert puts the key into one of its two slots; if both are full, it throws out one of the two keys, which goes to *its* other slot, possibly throwing out a third key, like the cuckoo that throws eggs out of other birds' nests. If the chain of evictions gets too long, the table is rebuilt with new hash functions. With buckets of 4 slots, cuckoo tables work up to 95 % full. They are used in network hardware, in MemC3 (a faster memcached), and in cuckoo filters. We do not build one, but the comparison is good to know: Robin Hood makes the average walk short, cuckoo hashing makes the longest walk short.

## Swiss tables

The **Swiss table** was designed at Google for the Abseil library (2017), and Rust's standard `HashMap` uses the same design. It adds a small array of **control bytes**, one byte per slot:

* `kEmpty` for an empty slot, `kDeleted` for a tombstone;
* for a full slot, **H2**: 7 bits of the key's hash.

The other bits of the hash, **H1**, choose a **group** of 16 slots where the search starts. A lookup compares H2 with all 16 control bytes of the group at once. A full slot of another key has the same H2 only with probability 1/128, so the lookup almost never compares a key that is not the right one. If the group has no matching slot and an empty slot, the key is not in the table. Otherwise the search continues in another group: our table jumps 1, then 2, then 3 groups further, and so on (the triangular numbers), which visits every group once when the number of groups is a power of two.

{% include viz.html id="swiss-probe" alt="A lookup in a Swiss table: the key's hash is split into H1, which picks a group, and the 7 bits of H2. The 16 control bytes of the group are compared with H2 in one step, giving a mask of matching slots; the keys of those slots are compared, and an empty slot in the group ends the search. Buttons look up a key that is in the table, one that is not, and one whose group is full, so that the search jumps to the next group." %}

Erasing makes a tombstone, with one exception. If the group of the erased slot has an empty slot, no lookup ever walked through this group to reach another one, because a lookup stops at a group with an empty slot. So the erased slot can become empty, and nothing needs to remember it. When tombstones fill the table, it is rebuilt at the same size, which drops them all.

Our groups are aligned blocks of 16 slots, like the groups of Boost's `unordered_flat_map`; Abseil starts its 16-slot window at any slot.

## SIMD: a group in one compare

With SSE2, which every x86-64 CPU has, comparing H2 with 16 control bytes takes three instructions: load the 16 bytes, compare each byte with H2 (`_mm_cmpeq_epi8` gives `0xFF` in every equal byte), and collect the top bit of each byte into an ordinary integer (`_mm_movemask_epi8`). The result is a **mask**: bit $$i$$ is set when slot $$i$$ of the group may hold the key. A loop then visits the set bits from the lowest:

```cpp
for (Mask m = Group::match(ctrl, h2); m != 0; m &= m - 1) {  // m & (m - 1) clears the lowest set bit
    const std::size_t s = first_slot + std::countr_zero(m);  // the lowest set bit

    if (slots[s].key == key)
        return slots[s].value;
}
```

The empty slots and the empty-or-deleted slots are masks of the same kind. For the second one, look at the values of the control bytes: one instruction is enough.

With a table of 4 MB, in the caches, lookups with SSE2 groups were 2.0 times faster than with the same table checking one control byte at a time. And compared with `std::unordered_map`, building the table and then following a chain of dependent lookups was 2.6 times faster.

## Hash functions and hash flooding

A table whose capacity is a power of two finds the home slot with the low bits of the hash: `hash & (capacity - 1)`, without a division. Then the identity function, libstdc++'s hash for integers, is a disaster: keys that differ only in their high bits all get the same home slot. Keys like $$i \cdot 2^{20}$$, which are common (addresses, ids with a shard number in the high bits), all collide:

{: .grid-head }
| Keys $$i \cdot 2^{20}$$ in a linear-probing table | identity hash | mixing hash | `std::unordered_map` |
| --- | --- | --- | --- |
| 20,000 keys | 110.5 ms | 0.14 ms | 0.78 ms |
| 40,000 keys | 447.9 ms | 0.27 ms | 1.57 ms |

With the identity, every insert walks over all the earlier keys: the time grows with the square of the number of keys, and at 40,000 keys it is 1700 times slower. A **mixing** hash function makes every bit of the result depend on every bit of the key. Ours is the finalizer of MurmurHash3, two multiplications and three shifts:

```cpp
std::uint64_t mix(std::uint64_t x) {
    x ^= x >> 33;
    x *= 0xff51afd7ed558ccdULL;
    x ^= x >> 33;
    x *= 0xc4ceb9fe1a85ec53ULL;
    x ^= x >> 33;

    return x;
}
```

{% include viz.html id="hash-flooding" alt="64 buckets of a power-of-two table as columns, filled with keys of the form i times 2 to the power k. A toggle chooses the identity hash or the mixing hash, and a slider sets k. With the identity and k of 6 or more, all keys fall into one bucket; with the mixing hash they spread evenly." %}

An attacker can do the same on purpose. If the hash function of a web server's table is known, the attacker sends keys that all collide, and a few kilobytes of request keep a server busy for minutes: **hash flooding** (Crosby and Wallach, 2003). In 2011, this attack worked against the web frameworks of PHP, Java, Python and Ruby, because they stored the parameters of a request in hash tables. Since then, hash tables that face untrusted keys use a **secret random seed**. Python and Rust use **SipHash** (Aumasson and Bernstein, 2012), a keyed hash function designed so that collisions cannot be found without the key.

Our tables take a seed: `hash_key(key, seed)` is `mix(key ^ seed)`. `mix` is fast but can be inverted, so this protects only if the seed is secret. A server would take it from `std::random_device`, as Abseil does once per process.

## Batches of lookups

A hash join probes a table with millions of keys, one after another. In a table larger than the caches, a lookup has two cache misses, and the second depends on the first: the control bytes, and then the slot that H2 chose. The CPU overlaps the lookups of several keys, but only as many as fit in its window of instructions.

Software can do better when it knows the keys in advance. **Batching** works on 16 keys at a time: first hash all 16 and prefetch their control bytes (chapter 25); then match H2 in each group, which is now in the cache, and prefetch the slot of the first candidate; finally compare the keys. The misses of 16 keys are all on their way at the same time.

In a table of 128 MB, a lookup took 44.3 ns one by one and 29.0 ns in batches of 16: 1.5 times faster. A pipeline that prefetches the control bytes 32 keys ahead and the slots 16 keys ahead reached 25.2 ns: 1.8 times. That is less than for the searches of chapter 25, because the CPU already overlaps independent lookups by itself; what batching adds is the overlap of the *second* miss. Vectorized query engines such as DuckDB and ClickHouse probe their hash tables in batches like this.

## Threads: a sharded map

A map for many threads uses the idea of last week's buffer pool: **shards**, each a hash table with its own mutex. With 4 threads that did 90 % lookups and 10 % inserts, 64 shards were 5.3 times faster than one table behind one mutex.

One detail matters for Swiss tables. The shard must come from different bits of the hash than the ones that the table uses. If the shard came from the low 7 bits, all keys of a shard would share their H2, and every group compare would match every full slot. So the shard comes from the top bits of the hash.

## Consistent hashing

A distributed database spreads its keys over many servers. The obvious rule, `server = hash(key) % n`, has a big problem: when a server is added, almost every key moves. A key stays only if `hash % 10 == hash % 11`, so going from 10 to 11 servers moves 91 % of all keys over the network.

**Consistent hashing** (Karger and others, 1997) puts the servers and the keys on a **ring** of hash values: a key belongs to the first server at or after its hash, going around the ring. A new server takes over only the keys between itself and the server before it: about $$1/n$$ of all keys, and all of them come to the new server. With a single point per server, the arcs between the points are very unequal, and so are the loads. So every server gets many points on the ring, called **virtual nodes**.

{% include viz.html id="hash-ring" alt="A ring of hash values with the points of 2 to 6 servers in different colors and 120 keys as dots, each colored by its server. Buttons add or remove a server; the keys that move are marked, and a counter compares them with the keys that hash modulo n would move. A slider sets the virtual nodes per server, 1 to 32, and bars show the load of each server." %}

With 20 servers and 200,000 keys, the busiest server had 2.9 times the mean load with one point per server, 1.24 times with 100 virtual nodes, and 1.18 times with 200. Adding a 21st server moved 5.2 % of the keys, all of them to the new server; the ideal is $$1/21 = 4.8\,\%$$.

**Jump consistent hash** (Lamping and Veach, 2014) needs no ring and no memory at all: a loop of a few lines computes the bucket of a key from the key and the number of buckets. When the number grows from $$n$$ to $$n + 1$$, a key either stays or jumps to the new bucket, with probability $$1/(n + 1)$$, and the loads are almost equal (1.02 times the mean in our test). Its limit is that buckets can only be added or removed at the end, so it suits the shards of a database better than servers that may fail anywhere.

Amazon's **Dynamo** (DeCandia and others, 2007) built a database on the ring with virtual nodes. Every key is stored on the next $$N$$ servers of the ring; a write waits for $$W$$ of them and a read for $$R$$. With $$R + W > N$$, every read meets at least one server that has the latest write. Cassandra and many other databases use the same ring.
