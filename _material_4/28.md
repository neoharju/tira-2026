# 28. Hash Tables

B+ trees keep their keys in order, so they can answer range queries. When nobody needs the order, a **hash table** is faster: the hash of a key tells almost directly where the key is. Databases use hash tables everywhere: for `GROUP BY` and joins, for their caches (last week's page table), and for their in-memory indexes.

The tasks are in the folder `cpp/week28`. Keys and values are 64-bit numbers. The headers `robin_hood.hpp`, `swiss.hpp`, `cuckoo.hpp`, `sharded_map.hpp` and `ring.hpp` give the exact rules of each table. Most tests compare a table with `std::unordered_map` on random operations, and `validate()` checks the rules of the table. Each benchmark first checks your result: a wrong result is not timed.

## Which hash table?

C++ has a hash table in its standard library: `std::unordered_map`. But look at what large systems use:

{: .grid-head }
| Where | Hash table | Design |
| --- | --- | --- |
| Google (Abseil, C++) | `absl::flat_hash_map` | Swiss table |
| Rust, standard library | `HashMap` (hashbrown) | Swiss table |
| Go | the built-in `map` (since Go 1.24, 2025) | Swiss table |
| Boost, C++ | `boost::unordered_flat_map` | groups with SIMD, like a Swiss table |
| Meta (Folly, C++) | `F14FastMap` | groups with SIMD, like a Swiss table |
| C++ libraries | `ankerl::unordered_dense`, `tsl::robin_map` | Robin Hood hashing |
| DPDK (network packets) | `rte_hash` | cuckoo hashing |
| C++ standard library | `std::unordered_map` | chaining with nodes |

Almost nobody chooses `std::unordered_map` when speed matters. The default today is a **Swiss table**: open addressing with one control byte per slot and SIMD probing. This week we see why, and we build the designs of the table one after another, each one as an answer to a problem of the one before:

1. why `std::unordered_map` is slow, and what **open addressing** does instead;
2. **hash functions**, and **hash flooding**, an attack that makes a hash table a thousand times slower;
3. **Robin Hood hashing**, which keeps every key close to its home;
4. the **Swiss table**, which checks 16 slots with one SIMD compare, and **batches** of lookups;
5. **cuckoo hashing**, where a lookup reads at most two places;
6. a hash map for **many threads**, and **consistent hashing**, which spreads keys over the servers of a distributed database.

## Why not std::unordered_map?

The C++ standard promises that a pointer to an element of an `unordered_map` stays valid when the table grows. It also offers a "bucket interface" that shows how the elements are chained. Both promises force one design: every element is a **node** of its own, allocated separately, and a bucket array points to lists of nodes. A lookup looks like this (simplified):

```cpp
struct Node {
    Node* next;  // the next node of the same bucket
    Key key;
    Value value;
};

Value* find(Key key) {
    const std::size_t b = std::hash<Key>{}(key) % bucket_count;  // a division by a prime number

    for (Node* n = buckets[b]; n != nullptr; n = n->next)  // one cache miss per node
        if (n->key == key)
            return &n->value;

    return nullptr;
}
```

A lookup reads the bucket array and then follows pointers to nodes: the chain of loads of chapter 25 again. Each entry of 16 bytes takes about 40 bytes of memory: the node (the key, the value and the next pointer), the header of the memory allocator, and a share of the bucket array.

There is one more detail. In libstdc++, the hash of an integer is the integer itself: `std::hash<std::uint64_t>{}(x) == x`. That works only because libstdc++ uses a prime number of buckets, so that the bucket `x % prime` depends on all bits of `x`. And a division by a prime number in every lookup is not free.

A **flat** hash table stores the keys and values in one array. Here are this week's tables, measured against `std::unordered_map` with random 64-bit keys:

{: .grid-head }
| 1,000,000 keys | build: ns per insert | lookups: ns per lookup | dependent lookups: ns per lookup |
| --- | --- | --- | --- |
| `std::unordered_map` | 361 | 41 | 605 |
| Robin Hood (task 1) | 152 | 35 | 298 |
| Swiss table, one byte at a time (task 2) | 140 | 71 | 341 |
| Swiss table with SSE2 (task 4) | 84 | 38 | 349 |
| cuckoo, buckets of 4 (task 6) | 162 | 20 | 297 |

Building is where flat tables win most: `unordered_map` allocates a node for every key, and the Swiss table with SSE2 builds 4.3 times faster. In a **dependent** lookup, the next key comes from the value that the last lookup found. So lookups cannot overlap, and the time is the latency of the cache misses. `unordered_map` has two or three misses per lookup, a flat table one or two. Independent lookups are closer, because the CPU overlaps the misses of many lookups (chapter 25). (Our virtual machine is noisy: these numbers change by 10–20 % from run to run.)

## Open addressing

How does a flat table work? **Open addressing** puts every key in one array of slots. A key belongs in its **home slot**, `hash & (capacity - 1)`. If another key already took that slot, the key goes to the next free slot after it: this is **linear probing**. A lookup starts at the home slot and walks right until it finds the key or an empty slot:

```cpp
std::optional<Value> find(Key key) const {
    for (std::size_t i = hash_key(key, seed) & mask;; i = (i + 1) & mask) {  // after the last slot comes slot 0
        if (!slots[i].used)
            return std::nullopt;  // an empty slot ends the walk

        if (slots[i].key == key)
            return slots[i].value;
    }
}
```

The slots after each other are in the same cache lines, so the walk is cheap, as long as it is short. But the walk gets long when the table is full. Keys that collide form **clusters**. A cluster grows faster the longer it is, because every key whose home falls inside it ends up at its end. Knuth computed the expected number of slots that a lookup reads at load factor $$\alpha$$ (the share of full slots):

$$\frac{1}{2}\left(1 + \frac{1}{1 - \alpha}\right) \text{ for a key in the table}, \qquad \frac{1}{2}\left(1 + \frac{1}{(1 - \alpha)^2}\right) \text{ for a key not in it}.$$

At $$\alpha = 7/8$$ that is 4.5 slots for a hit, but 32.5 slots for a miss. So tables grow (double their capacity) before they are too full. Erasing needs care too: if we empty a slot in the middle of a cluster, the walk of every key behind it stops too early. So either the slot becomes a **tombstone**, which lookups walk over, or the keys behind it move back.

## Hash functions and hash flooding

The home slot `hash & (capacity - 1)` uses only the low bits of the hash, and it needs no division. So the low bits must be good. With libstdc++'s identity hash, that is a disaster: keys that differ only in their high bits all get the same home slot. Keys like $$i \cdot 2^{20}$$ are common (addresses, or ids with a shard number in the high bits), and they all collide:

{: .grid-head }
| Keys $$i \cdot 2^{20}$$ in a linear-probing table | identity hash | mixing hash | `std::unordered_map` |
| --- | --- | --- | --- |
| 20,000 keys | 110.5 ms | 0.14 ms | 0.78 ms |
| 40,000 keys | 447.9 ms | 0.27 ms | 1.57 ms |

With the identity, every insert walks over all the earlier keys. The time grows with the square of the number of keys: at 40,000 keys the table is 1700 times slower. A **mixing** hash function makes every bit of the result depend on every bit of the key. Ours (`hash.hpp`) is the finalizer of MurmurHash3, two multiplications and three shifts:

```cpp
std::uint64_t mix(std::uint64_t x) {
    x ^= x >> 33;
    x *= 0xff51afd7ed558ccdULL;
    x ^= x >> 33;
    x *= 0xc4ceb9fe1a85ec53ULL;
    x ^= x >> 33;

    return x;
}
```

{% include viz.html id="hash-flooding" alt="64 buckets of a power-of-two table as columns, filled with keys of the form i times 2 to the power k. A toggle chooses the identity hash or the mixing hash, and a slider sets k. With the identity and k of 6 or more, all keys fall into one bucket; with the mixing hash they spread evenly." %}

An attacker can do the same on purpose. Suppose that an attacker knows the hash function of a web server's table. Then the attacker can send keys that all collide, and a few kilobytes of request keep the server busy for minutes. This is **hash flooding** (Crosby and Wallach, 2003). In 2011, this attack worked against the web frameworks of PHP, Java, Python and Ruby, because they stored the parameters of a request in hash tables. Since then, hash tables that get untrusted keys use a **secret random seed**. Python and Rust use **SipHash** (Aumasson and Bernstein, 2012), a keyed hash function designed so that nobody can find collisions without the key. Abseil takes a random seed once per process.

Our tables take a seed too: `hash_key(key, seed)` is `mix(key ^ seed)`. `mix` is fast, but it can be inverted, so this protects only if the seed is secret.

## Robin Hood hashing

Linear probing has a second problem besides clusters: the walks are very unequal. A few keys are far from home, and a lookup for a key that is not there must walk to the end of the cluster. **Robin Hood hashing** (Celis, Larson and Munro, 1985) changes one rule of insertion. Every slot knows how far its key is from home. A new key walks along a cluster. When it meets a key that is *closer* to its home than the new key is to its own, the new key takes the slot. The walk continues with the key that it pushed out. It takes from the rich and gives to the poor.

The total distance stays the same, but the distances become more equal. No key is very far from home, so the longest walk is short. And a lookup for a missing key can stop early. When it meets a key that is closer to its home than the lookup is to its own, the missing key would have been placed before that key. So it is not in the table. Follow the same keys in both tables:

{% include viz.html id="open-addressing" alt="Two tables of 16 slots, one above the other: linear probing and Robin Hood hashing. The same 13 keys, A to M, with given home slots, are inserted step by step; each slot shows its key and its distance from home, colored by that distance, and the walk of the current key is outlined. In the Robin Hood table, the slots where the new key took the place of a richer key are marked. At the end both tables have a total distance of 33, but the longest distance is 9 with linear probing and 4 with Robin Hood. A lookup of the missing key Z reads 13 slots with linear probing and 6 with Robin Hood." %}

In our table (`robin_hood.hpp`), every slot stores `dist`: 0 for an empty slot, and $$d + 1$$ for a key that is $$d$$ slots after its home. So the lookup stops at a slot whose `dist` is smaller than its own, and that also covers the empty slots:

```cpp
std::size_t i = home(key);

for (unsigned d = 1;; ++d, i = (i + 1) & mask) {  // d: our distance from home, plus 1
    if (slots[i].dist < d)
        return std::nullopt;  // an empty slot, or a richer key: the key is not here

    if (slots[i].key == key)
        return slots[i].value;
}
```

Erasing uses a **backward shift** instead of tombstones. After the erased slot, every key that is not in its home slot moves one slot back. This stops at the first empty slot or at the first key that is at home. The table looks exactly as if the erased key had never been inserted, so lookups stay short also after many erases.

Is Robin Hood hashing still used? Yes. `ankerl::unordered_dense` and `tsl::robin_map`, two popular C++ hash tables, use Robin Hood hashing with the backward shift. `unordered_dense` also stores the pairs in a dense vector apart from the slots, so that iterating over all pairs is as fast as over a `std::vector`.

## Swiss tables

Robin Hood keeps the walks short, but each step of a walk still reads a whole slot of 16 or 24 bytes and compares a whole key. Can a lookup skip most slots without reading them? The **Swiss table**, designed at Google for the Abseil library (2017), adds a small array of **control bytes**, one byte per slot:

* `kEmpty` (`0x80`) for an empty slot, `kDeleted` (`0xFE`) for a tombstone;
* for a full slot, **H2**: 7 bits of the key's hash (`0x00` to `0x7F`).

The other bits of the hash, **H1**, choose a **group** of 16 slots where the search starts:

```cpp
const std::uint64_t h = hash_key(key, seed);
const auto h2 = static_cast<std::int8_t>(h & 127);  // 7 bits, stored in the control byte
std::size_t g = (h >> 7) & (groups() - 1);          // H1: the first group
```

A lookup compares H2 with all 16 control bytes of the group at once. A full slot of another key has the same H2 only with probability 1/128. So the lookup almost never compares a wrong key. If the group has no matching slot and an empty slot, the key is not in the table. Otherwise the search continues in another group. Our table jumps 1, then 2, then 3 groups further, and so on (the triangular numbers). This visits every group once when the number of groups is a power of two. Follow a lookup together with its code:

{% include viz.html id="swiss-probe" alt="A lookup in a Swiss table of 4 groups of 16 slots, next to the C++ code of find with SSE2. Step by step: the key's hash is split into H1, which picks a group, and the 7 bits of H2; the 16 control bytes of the group are loaded; _mm_set1_epi8 and _mm_cmpeq_epi8 give 0xFF where a byte equals H2; _mm_movemask_epi8 makes a 16-bit mask; countr_zero visits the set bits, and each candidate key is compared, first a false match and then the key. The highlighted code line follows the step. Buttons look up a key in the table, a missing key (an empty slot ends the search) and a key behind a full group (the search jumps to the next group)." %}

An insert puts the pair into the first empty or deleted slot of the probe sequence. An erase makes a tombstone, with one exception. Suppose that the group of the erased slot has an empty slot. Then no lookup ever walked through this group to another group, because a lookup stops at a group with an empty slot. So the erased slot can become empty, and nothing needs to remember it. When tombstones fill the table, it is rebuilt at the same size, which drops them all.

The design is now the default in several languages. Rust's standard `HashMap` (the hashbrown crate) has been a Swiss table since 2019, and Go's built-in `map` since Go 1.24 (2025). Boost's `unordered_flat_map` and Meta's F14 use groups of 15 and 14 slots with the same SIMD compare. Our groups are aligned blocks of 16 slots, like the groups of Boost; Abseil starts its window of 16 at any slot.

## SIMD: 16 slots in one compare

With `ScalarGroup` the Swiss table is not fast: it compares the 16 control bytes one at a time. With SSE2, which every x86-64 CPU has, the same work takes three instructions. `_mm_loadu_si128` loads the 16 bytes. `_mm_cmpeq_epi8` compares each byte with H2 and gives `0xFF` in every equal byte. `_mm_movemask_epi8` collects the top bit of each byte into an ordinary integer:

```cpp
// The slots of the group whose control byte is h2, as the bits of a 16-bit mask.
Mask match(const std::int8_t* ctrl, std::int8_t h2) {
    const __m128i bytes = _mm_loadu_si128(reinterpret_cast<const __m128i*>(ctrl));
    const __m128i eq = _mm_cmpeq_epi8(bytes, _mm_set1_epi8(h2));  // 0xFF where equal
    return static_cast<Mask>(_mm_movemask_epi8(eq));  // the top bit of each byte
}
```

The result is a **mask**: bit $$i$$ is set when slot $$i$$ of the group may hold the key. A loop then visits the set bits from the lowest:

```cpp
for (Mask m = Group::match(ctrl, h2); m != 0; m &= m - 1) {  // m & (m - 1) clears the lowest set bit
    const std::size_t s = first_slot + std::countr_zero(m);  // the lowest set bit

    if (slots[s].key == key)
        return slots[s].value;
}
```

The empty slots and the empty-or-deleted slots are masks of the same kind. For the empty-or-deleted slots, look at the bits of the control bytes: one instruction is enough.

Why 16 slots, and not more? AVX2 could compare 32 bytes, and AVX-512 64 bytes: `_mm512_cmpeq_epi8_mask` even returns the 64-bit mask directly, without a movemask. But most lookups end in their first group, and a wider compare must also load more bytes from memory. So Abseil and hashbrown stay with 16 bytes on x86. On ARM, NEON has no movemask instruction: there, Abseil and hashbrown use groups of 8 control bytes. Go's map uses groups of 8 slots on all machines.

In a table of 4 MB (in the caches), SSE2 groups made lookups about twice as fast as one control byte at a time. Building a table and then following a chain of dependent lookups was about 2.5 times faster than with `std::unordered_map`.

## Batches of lookups

In a table that fits in the caches, SIMD made each lookup cheap. In a table larger than the caches, the time is waiting again. A lookup has two cache misses, and the second one depends on the first: first the control bytes, then the slot that H2 chose. A hash join probes a table with millions of keys, one after another. The CPU overlaps the lookups of several keys, but only as many as fit in its window of instructions.

Software can do better when it knows the keys in advance. **Batching** works on 16 keys at a time, in three passes over the batch:

```cpp
for (std::size_t i = 0; i < 16; ++i) {  // pass 1: start the first miss of all 16 keys
    h[i] = hash_key(keys[i], seed);
    __builtin_prefetch(&ctrl[16 * group_of(h[i])]);
}

for (std::size_t i = 0; i < 16; ++i) {  // pass 2: the control bytes are here now; start the second miss
    first[i] = Group::match(&ctrl[16 * group_of(h[i])], h2_of(h[i]));
    if (first[i] != 0)
        __builtin_prefetch(&slots[16 * group_of(h[i]) + std::countr_zero(first[i])]);
}

// pass 3: compare the keys, and continue the probe where it is needed
```

The misses of 16 keys are all on their way at the same time. In a table of 128 MB, a lookup took 44.3 ns one by one and 29.0 ns in batches of 16: 1.5 times faster. A pipeline that prefetches the control bytes 32 keys ahead and the slots 16 keys ahead reached 25.2 ns: 1.8 times faster. That is less than for the searches of chapter 25, because the CPU already overlaps independent lookups by itself; batching adds the overlap of the *second* miss. Vectorized query engines such as DuckDB and ClickHouse probe their hash tables in batches like this.

## Cuckoo hashing

A Swiss table lookup usually reads one group. But that is the average. Its worst case is a long probe sequence, through many full groups. Some systems need a hard bound instead of a good average. A router must handle every packet within a fixed time, and a hash table in a network switch chip must answer in a fixed number of clock cycles. For them there is **cuckoo hashing** (Pagh and Rodler, 2001).

Every key has exactly two possible places, chosen by two hash functions, and it is always in one of them. A lookup reads at most these two places: the worst case is constant, not only the average. And both addresses are known before the first load, so the two cache misses overlap.

An insert puts the key into one of its two places. If both are full, it throws out one of the keys there. That key goes to *its* other place, and it may throw out a third key, like the cuckoo that throws the eggs of other birds out of their nests. If the chain of kicks gets too long, the table grows (or gets new hash functions), and all keys are inserted again. Try it with buckets of 1, 2 and 4 slots:

{% include viz.html id="cuckoo" alt="A cuckoo table of 16 slots: 16 buckets of 1 slot, 8 buckets of 2 or 4 buckets of 4, chosen with a toggle. Every key A to P has two buckets, listed above the table. Step by step the keys are inserted: a key goes into a free slot of one of its two buckets, or it kicks a key out, and the kicked key moves to its other bucket, possibly kicking out another key. When the kicks go round in a circle, the table must grow; the caption tells how full it got. At the end a lookup reads exactly two buckets." %}

With one slot per bucket, the kicks soon go round in circles: the table fails at about half full. With **buckets** of several slots, a key has more room in each of its two places, and the table gets much fuller before an insert fails. We filled tables of $$2^{16}$$ slots with random keys, with at most 500 kicks per insert:

{: .grid-head }
| Slots per bucket | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| full at the first failed insert | 51.7 % | 87.7 % | 96.6 % | 99.1 % |

Buckets of 4 slots of 16 bytes are exactly one cache line. So our `CuckooMap` (`cuckoo.hpp`) has buckets of 4 keys and their 4 values, and a lookup reads two cache lines at most. AVX2 compares the 4 keys of a bucket with one `_mm256_cmpeq_epi64`, and `_mm256_movemask_pd` turns the result into 4 bits:

```cpp
// The used slots of bucket b that hold the key, as bits.
unsigned match(std::size_t b, __m256i k) const {
    const __m256i keys = _mm256_load_si256(reinterpret_cast<const __m256i*>(buckets[b].keys.data()));
    const auto eq = static_cast<unsigned>(_mm256_movemask_pd(_mm256_castsi256_pd(_mm256_cmpeq_epi64(keys, k))));
    return eq & ((1u << used[b]) - 1);  // only the first used[b] slots hold pairs
}

std::optional<Value> find(Key key) const {
    const std::size_t b1 = first(key), b2 = second(key);  // both addresses before any load
    const __m256i k = _mm256_set1_epi64x(static_cast<long long>(key));
    const unsigned m1 = match(b1, k), m2 = match(b2, k);

    if (m1 != 0)
        return buckets[b1].values[std::countr_zero(m1)];

    if (m2 != 0)
        return buckets[b2].values[std::countr_zero(m2)];

    return std::nullopt;
}
```

We put 3,700,000 keys in a cuckoo table, which was then 88 % full. A dependent lookup took 696 ns in `std::unordered_map`, 450 ns in our Swiss table and 357 ns in the cuckoo table: one round trip to memory instead of two. A version with two plain loops, one bucket after the other, was as fast (340 ns). The CPU guesses that the key is not in the first bucket, and it starts the load of the second bucket early. Independent lookups were the fastest of all tables: 20 ns per lookup in the table above. The two buckets of many keys are on their way at the same time.

The price is the insert. Near the full limit, an insert needs many kicks, so building the table was slower than building the Swiss table. Cuckoo hashing is therefore used where lookups count and the worst case matters. DPDK, the library for fast packet processing, keeps its flow tables in `rte_hash`: cuckoo hashing with buckets of 8. **Cuckoo filters** (Fan, Andersen, Kaminsky and Mitzenmacher, 2014) store short fingerprints instead of keys: an alternative to Bloom filters that can also delete keys, offered for example by Redis. And some network switch chips do exact-match lookups in hardware with cuckoo tables.

## Threads: a sharded map

All tables so far are for one thread. A map for many threads uses the idea of last week's buffer pool: **shards**, each a hash table with its own mutex. With 4 threads that did 90 % lookups and 10 % inserts, 64 shards were 5.3 times faster than one table behind one mutex.

One detail matters for Swiss tables. The shard must come from other bits of the hash than the bits that the table uses. If the shard came from the low 7 bits, all keys of a shard would have the same H2, and every group compare would match every full slot. So `sharded_map.hpp` takes the shard from the top bits of the hash:

```cpp
std::size_t shard_of(Key key) const {
    const auto bits = static_cast<unsigned>(std::countr_zero(shards.size()));  // shards is a power of two
    return bits == 0 ? 0 : static_cast<std::size_t>(hash_key(key, seed) >> (64 - bits));
}
```

## Consistent hashing

One table on many threads is solved. Now take many machines: a distributed database spreads its keys over many servers. The obvious rule is `server = hash(key) % n`, and it has a big problem: when a server is added, almost every key moves. A key stays only if `hash % 10 == hash % 11`, so going from 10 to 11 servers moves 91 % of all keys over the network.

**Consistent hashing** (Karger and others, 1997) puts the servers and the keys on a **ring** of hash values. A key belongs to the first server at or after its hash, going around the ring. A new server takes over only the keys between itself and the server before it: about $$1/n$$ of all keys, and all of them go to the new server. With one point per server, the arcs between the points are very unequal, and so are the loads. So every server gets many points on the ring, called **virtual nodes**.

We put 200,000 keys on 20 servers. With one point per server, the busiest server had 2.9 times the mean load; with 100 virtual nodes, 1.24 times; and with 200, 1.18 times. Adding a 21st server moved 5.2 % of the keys, all of them to the new server; the ideal is $$1/21 = 4.8\,\%$$.

**Jump consistent hash** (Lamping and Veach, 2014) needs no ring and no memory at all. Its idea fits in a slow loop. When the number of buckets grows from $$j$$ to $$j + 1$$, a key jumps to the new bucket with probability $$1/(j + 1)$$; otherwise it stays.

```cpp
// The idea of jump consistent hash in O(n): a random stream that depends
// only on the key decides at each j whether the key jumps to bucket j.
std::int32_t slow_jump(std::uint64_t key, std::int32_t buckets) {
    std::mt19937_64 random(key);
    std::uniform_real_distribution<double> uniform(0, 1);
    std::int32_t bucket{};

    for (std::int32_t j = 1; j < buckets; ++j)
        if (uniform(random) < 1.0 / (j + 1))
            bucket = j;

    return bucket;
}
```

Every bucket gets the same share of the keys, and when the number of buckets grows by one, a key either stays or moves to the new bucket. The real algorithm computes the jumps directly, in $$O(\log n)$$ steps: read the paper for the trick. The loads are almost equal (1.02 times the mean in our test). Its limit: buckets can be added or removed only at the end. So it suits the shards of a database better than servers, which may fail anywhere.

Amazon's **Dynamo** (DeCandia and others, 2007) built a database on the ring with virtual nodes. Every key is stored on the next $$N$$ servers of the ring; a write waits for $$W$$ of them and a read for $$R$$. With $$R + W > N$$, every read meets at least one server that has the latest write. Cassandra and many other databases use the same ring.

## Time and space

For $$n$$ keys at load factor $$\alpha$$ (the share of full slots):

{: .grid-head }
| Table or operation | Time | Space |
| --- | --- | --- |
| chaining (`std::unordered_map`) | $$O(1 + \alpha)$$ expected | about 40 bytes per entry of 16 bytes |
| linear probing | $$\frac12\big(1 + \frac{1}{1 - \alpha}\big)$$ slots for a hit, $$\frac12\big(1 + \frac{1}{(1 - \alpha)^2}\big)$$ for a miss, expected | $$n/\alpha$$ slots |
| Robin Hood | the same expected slots for a hit; a miss stops early; erase with a backward shift | 1 byte of distance per slot |
| Swiss table | $$O(1)$$ expected groups of 16 slots | 1 control byte per slot, $$\alpha \le 7/8$$ |
| growth by doubling | $$O(n)$$ for one rebuild, $$O(1)$$ amortized per insert | twice the slots during the rebuild |
| cuckoo: find, insert | $$O(1)$$ in the worst case: two buckets; expected $$O(1)$$ amortized, with a rebuild when the kicks go round | buckets of 4: up to 97 % full |
| batches of lookups | the same $$O(1)$$, with the misses of 16 keys overlapped | the hashes of a batch |
| ring with $$v$$ points per server | `owner`: $$O(\log(nv))$$ by binary search over $$n$$ servers' points | $$O(nv)$$ |
| jump consistent hash | $$O(\log n)$$ expected steps for $$n$$ buckets | $$O(1)$$ |
| Bloom filter, $$k$$ bits set per key (bonus) | $$O(k)$$; one cache line in a split-block filter | $$m$$ bits; false positives about $$(1 - e^{-kn/m})^k$$ |

"Expected" needs a good hash function. With a hash that an attacker can choose keys against, every table here falls to $$O(n)$$ per operation, and building it to $$O(n^2)$$: that is hash flooding. A secret seed restores the expected bounds.

## Bonus: a Bloom filter in one register

Week 31 will ask a question many times per second: "is this key perhaps in that file on the disk?" A **Bloom filter** answers it in memory. It is an array of bits. To add a key, set $$k$$ bits chosen by hash functions. To test a key, check its $$k$$ bits: if one is 0, the key was never added; if all are 1, it probably was. A filter with 10 bits per key has about 1 % false positives. But a classic Bloom filter puts the $$k$$ bits in $$k$$ random places, so a test costs up to $$k$$ cache misses.

A **split-block Bloom filter** puts all bits of a key into one block of 256 bits: 32 bytes, half a cache line, and exactly one AVX2 register. It comes from Apache Impala, and the Apache Parquet file format uses it. The block has 8 words of 32 bits, and each key sets exactly one bit in each word. The bit of word $$i$$ is the top 5 bits of the product of the key with a constant $$s_i$$ (`salt` below, from the Parquet specification). So the mask of a key takes three instructions, and a test takes one more:

```cpp
// Parquet's 8 odd constants: one per word of the block.
constexpr std::uint32_t salt[8] = {0x47b6137b, 0x44974d91, 0x8824ad5b, 0xa2b7289d,
                                   0x705495c7, 0x2df1424b, 0x9efc4947, 0x5c6bfb31};

__m256i bloom_mask(std::uint32_t key) {  // one bit in each of the 8 words
    const __m256i s = _mm256_loadu_si256(reinterpret_cast<const __m256i*>(salt));
    const __m256i bit = _mm256_srli_epi32(_mm256_mullo_epi32(_mm256_set1_epi32(static_cast<int>(key)), s), 27);
    return _mm256_sllv_epi32(_mm256_set1_epi32(1), bit);  // 1 << bit, in each lane
}

void insert(std::uint64_t h) {
    auto* b = reinterpret_cast<__m256i*>(&blocks[((h >> 32) * blocks.size()) >> 32]);  // the high bits choose the block
    _mm256_store_si256(b, _mm256_or_si256(_mm256_load_si256(b), bloom_mask(static_cast<std::uint32_t>(h))));
}

bool may_contain(std::uint64_t h) const {
    const auto* b = reinterpret_cast<const __m256i*>(&blocks[((h >> 32) * blocks.size()) >> 32]);
    return _mm256_testc_si256(_mm256_load_si256(b), bloom_mask(static_cast<std::uint32_t>(h)));  // all mask bits set?
}
```

`((h >> 32) * blocks.size()) >> 32` maps the high 32 bits of the hash to a block number without a division. `_mm256_sllv_epi32` shifts each lane by its own amount, and `_mm256_testc_si256(a, b)` returns 1 when every bit of `b` is also set in `a`. On our machine, a filter with 10 bits per key for a million keys (1.2 MB) had 1.26 % false positives. 4,000,000 tests took 9.6 ms with AVX2 and 59.7 ms with a scalar loop over the 8 words: 6 times faster, and one cache miss per test at most.
