# 30. Spatial Indexes

Which restaurants are within 500 m of me? Which delivery drivers are near this customer? Which buildings touch this flood zone? These questions are about **places**: points and areas on a map. The indexes of the last weeks sort keys on one line. A B+ tree on the x coordinate finds all points between two x values quickly, but then it must check the y of every one of them. A box of 1 km × 1 km around Helsinki has all points of a 1 km wide band from the south coast to Lapland. A spatial index keeps points that are near each other on the map near each other in the index.

This week we build the two main families of spatial indexes:

1. **space-filling curves**, which give every point one number, so that the indexes of the last weeks can store the points: **Morton keys** with the BMI2 instructions, and **Hilbert keys**;
2. **cells**: geohash, which Redis and Elasticsearch use, and the hexagons of Uber's H3;
3. **R-trees**, the index of PostGIS, SQLite and Oracle: boxes in boxes, packed by **Sort-Tile-Recursive**;
4. **range queries** and **nearest-neighbour queries** in an R-tree, and a test of a node's 8 boxes with **one SIMD compare** per coordinate;
5. building the tree and answering batches of queries with **threads**.

The tasks are in the folder `cpp/week30`. A point has whole-meter coordinates `x` and `y`, east and north of a corner south-west of Finland, as in the national coordinates ETRS-TM35FIN with a smaller origin. A `float` holds such numbers exactly, so all compares of this week are exact. The headers `geo.hpp` and `rtree.hpp` give the exact rules, and `validate()` checks the trees. The benchmarks use 4,000,000 generated points: most of them are near the 20 largest towns of Finland, more near the larger ones, and the others are spread over the country, fewer in the north. Each benchmark first checks your result: a wrong result is not timed.

## Questions about places

Three kinds of queries come up again and again:

* a **range query**: all points inside a box, for example the map area on the screen;
* a **nearest-neighbour query**: the $$k$$ points nearest to a place, for example the 10 nearest charging stations;
* a **radius query**: all points within a distance, which is a box query and then an exact check of the distance.

Without an index, each query reads every point. For our 4,000,000 points, a range query by a scan took 14.8 ms, and a search for the 10 nearest points 43 ms. (Our virtual machine is noisy: the times of this chapter change by 10–30 % from run to run.) A map service answers thousands of such queries per second, so it needs microseconds, not milliseconds.

## Space-filling curves

The indexes of the last weeks sort numbers. Can we give every point a number, so that points near each other on the map get numbers near each other? A **space-filling curve** goes through every cell of a grid once. The place of a cell on the curve is its key.

The simplest curve is the **Z-order** curve (Morton, 1966). Write the coordinates in binary, and take their bits in turns: bit 0 of $$x$$, bit 0 of $$y$$, bit 1 of $$x$$, bit 1 of $$y$$, and so on. For $$x = 5 = 101_2$$ and $$y = 3 = 011_2$$, the **Morton key** is $$011011_2 = 27$$ (from the top: $$y_2 x_2 y_1 x_1 y_0 x_0$$). The curve visits the four quadrants of the grid in the shape of a Z, then the four quadrants of each quadrant, and so on.

The key of a point is one number, so a B+ tree, an ART or a sorted array can index it. A box on the map becomes a set of **key ranges**: the cells of the box, cut into runs of consecutive keys. Each range is one range scan in the B+ tree. Move the box in the figure, and compare the two curves:

A toggle chooses the Z-order curve or the Hilbert curve. The cells inside the box are colored by the key range that they belong to: each range is a run of consecutive keys on the curve. The Z-order curve has jumps: from one quadrant to the next, it can leave the box and come back. So a box of $$s \times s$$ cells can need many ranges. An index can also read the single range from the smallest key in the box to the largest one, and skip the points outside the box. But that range can be much larger than the box. Tropf and Herzog (1981) showed how to jump over the parts outside the box: from a key outside the box, one pass over its bits gives the next key inside the box (the "BIGMIN" key). Data lakes use the Z-order too: `OPTIMIZE … ZORDER BY` in Delta Lake sorts the rows of a table by the Morton key of some columns, so that the files hold small boxes of values and a query can skip most files.

## Morton keys with BMI2

A loop that moves one bit at a time takes 64 steps for a Morton key. The BMI2 instructions of x86-64 (Intel since Haswell, 2013, and AMD) do it in one step:

* `_pdep_u64(v, mask)`, **parallel deposit**, puts the low bits of `v`, in order, into the places of the 1 bits of `mask`;
* `_pext_u64(v, mask)`, **parallel extract**, takes the bits of `v` at the 1 bits of `mask`, and packs them at the bottom.

So a Morton key is two deposits into the even and the odd bits, and the way back is two extracts:

```cpp
constexpr std::uint64_t even_bits = 0x5555'5555'5555'5555ULL;  // bits 0, 2, 4, ...

std::uint64_t morton_encode(std::uint32_t x, std::uint32_t y) {
    return _pdep_u64(x, even_bits) | _pdep_u64(y, even_bits << 1);
}
```

{% include viz.html id="morton-bits" alt="The 8 bits of x and of y, the mask 0x5555 with its 1 bits in the even places, pdep of x, which puts the bits of x into the even places, pdep of y with the mask 0xAAAA, which puts the bits of y into the odd places, and the 16-bit Morton key, with the bits of x in blue and the bits of y in orange. Sliders set x and y, and the caption gives the key in decimal." %}

For 16,000,000 points, encoding and decoding took 65 ns per point with loops, and 3.4 ns with `pdep` and `pext`: **19 times faster**. Without BMI2, the "magic bits" method spreads the bits with five shifts and masks (`x = (x | x << 16) & 0x0000FFFF0000FFFF`, then 8, 4, 2 and 1). In a separate test it took 6.4 ns per point, where `pdep` and `pext` took 2.6 ns: about 2.4 times slower, but still 10 times faster than the loop.

There is one trap. On AMD's Zen 1 and Zen 2 (2017–2019), `pdep` and `pext` are microcoded: they run a slow loop inside the CPU, and they take up to hundreds of clock cycles, depending on the bits of the mask. Since Zen 3 (2020) they take 3 cycles, as on Intel. A library that must be fast on every machine checks the CPU, or uses the magic bits.

## The Hilbert curve

The **Hilbert curve** (Hilbert, 1891) also visits the four quadrants, then the quadrants of each quadrant, but it turns the order of each quadrant so that it never jumps: each next cell on the curve is a neighbour of the cell before. So a box on the map breaks into fewer pieces of the curve. Moon, Jagadish, Faloutsos and Saltz (2001) showed that, on average, the Hilbert curve needs fewer ranges than the Z-order curve. Toggle the curve in the figure above to see it. Google's S2 library orders its cells by the Hilbert curve for this reason.

The classic loop (the function `xy2d` on Wikipedia) reads one bit of $$x$$ and $$y$$ at each level, from the top. The two bits select a quadrant, and the place of that quadrant on the curve is the next two bits of the key. Then the loop turns the coordinates of the rest, by swapping $$x$$ and $$y$$ and by flipping their bits:

```cpp
for (std::uint32_t s = std::uint32_t{1} << 31; s > 0; s >>= 1) {
    const std::uint32_t rx = (x & s) != 0, ry = (y & s) != 0;
    d += std::uint64_t{s} * s * ((3 * rx) ^ ry);  // the place of the quadrant: 0, 1, 2 or 3
    if (ry == 0) {  // turn the quadrant
        if (rx == 1) {
            x = ~x;
            y = ~y;
        }
        std::swap(x, y);
    }
}
```

This loop has 32 rounds, and its `if` depends on the bits, so the CPU guesses it wrong about half of the time. It took 224 ns per key. A version without branches, which swaps and flips with masks, took 71 ns in another test, where the loop took 171 ns: 2.4 times faster. The 32 rounds remain a chain where each round needs the result of the round before. But look at what the loop remembers between the rounds: only how the square is turned. There are 4 possible turns: none, swapped, flipped and swapped, and flipped. So the loop is a **finite-state machine** with 4 states. It reads 2 bits per round, the two bits of one level, and these are exactly the next two bits of the Morton key. So:

* compute the Morton key with `pdep`;
* make a table of 4 × 256 entries: for each state and each byte of the Morton key (4 levels), the 8 bits of the Hilbert key and the next state;
* read the Morton key from the top, one byte at a time: 8 table lookups.

The table has 2 KB, and it stays in the L1 cache. A Hilbert key then took 7.5 ns: **30 times faster** than the loop, with no branch that depends on the data. Computing the table is a good exercise: run the four turns of the loop for each state and each byte.

## Cells: geohash, H3 and S2

A key of a space-filling curve does more than order the points. Its first bits name a **cell**: all points whose keys start with these bits are inside one square of the grid. Several systems use such cells directly.

**Geohash** (Niemeyer, 2008) is the Morton key of the longitude and the latitude, written in base 32. The first bit halves the longitude range $$[-180, 180]$$, the second bit halves the latitude range $$[-90, 90]$$, and so on. Each character adds 5 bits. The centre of Helsinki is `ud9wr3x`: a cell about 76 m wide and 153 m high (at 60° north, a degree of longitude is only half as long as at the equator). A geohash is a cell, and its prefixes are the larger cells around it: `ud9wr` is about 2.4 km wide and 4.9 km high.

Redis stores its geographic points (`GEOADD`) in a sorted set, with a 52-bit geohash as the score. A radius query (`GEOSEARCH`) chooses the length of the cell from the radius. Then it reads 9 score ranges: the cell of the centre and its 8 neighbours. Why the neighbours? Two points 300 m apart can be in different cells: a point near the Helsinki one above is `ud9wr9c`, and the two share only 5 characters. This **edge problem** is the weakness of all cells: neighbours on the map are not always neighbours in the keys.

**H3** (Uber, 2018) divides the Earth into **hexagons**. A square has two kinds of neighbours: 4 across an edge and 4 across a corner, at distances 1 and $$\sqrt{2}$$. A hexagon has 6 neighbours, all across an edge and all at the same distance. So the cells within $$k$$ steps of a cell, $$1 + 3k(k + 1)$$ of them, form a good approximation of a circle. Uber uses this for prices and the supply of drivers: the demand of each hexagon and its rings. H3 has 16 resolutions, from cells of 4 million km² to cells of under 1 m², and each cell has 7 children (only roughly inside it, because hexagons do not divide into smaller hexagons). A sphere cannot be covered by hexagons alone, so H3 also has 12 pentagons on each resolution.

{% include viz.html id="hex-cells" alt="A grid of cells around a point, with a toggle between squares, like geohash cells, and pointy-top hexagons, like H3 cells, of the same area. A slider sets k: the cells within k steps of the point's cell are colored, darker for the nearer rings, and lines mark the distances to the neighbours: 1 and 1.41 for squares, all equal for hexagons. The caption gives the number of cells, (2k + 1) squared for squares and 1 + 3k(k + 1) for hexagons, and how far the centres of ring k are: between k and 1.41 k steps for squares, and between 0.87 k and k for hexagons." %}

**S2** (Google) projects the Earth onto the 6 faces of a cube and divides each face as a quadtree, with 30 levels. A cell is a 64-bit id: the face, and the position on a Hilbert curve on that face. So the cells near each other on the Earth mostly have ids near each other. Google Maps, MongoDB (its `2dsphere` index), CockroachDB and Google BigQuery index places with S2 cells.

In the plane, hexagons are simple. With the corners `size` from the centre, the centre of the hexagon $$(q, r)$$ in **axial coordinates** is $$x = \text{size} \cdot \sqrt{3}\,(q + r/2)$$, $$y = \text{size} \cdot \tfrac{3}{2}\, r$$. To find the hexagon of a point, turn this around to fractional $$(q, r)$$, and round to the nearest hexagon. Rounding $$q$$ and $$r$$ separately is wrong near the corners. Round in **cube coordinates** $$(q, r, s)$$ with $$q + r + s = 0$$: round all three, then fix the one that changed most, so that the sum is 0 again.

## R-trees

Curves and cells cut the map into a fixed grid. The **R-tree** (Guttman, 1984) adapts to the data instead. It is a B+ tree of boxes:

* A leaf holds up to $$B$$ points (or the boxes of objects, such as buildings).
* An inner node holds up to $$B$$ children, each with its **bounding box**: the smallest box that holds everything below the child.
* All leaves are at the same depth, as in a B+ tree.

A query visits only the children whose boxes meet the query. Unlike a B+ tree, the boxes of two children can overlap, so a query may have to visit more than one child on a level. The art of the R-tree is to keep the boxes small and their overlaps small. Our nodes have $$B = 8$$ children, and they store the boxes as a struct of arrays. `min_x[8]` is one AVX2 register, and so are `min_y`, `max_x` and `max_y`:

{: .code-title }
week30/rtree.hpp (shortened)

```cpp
struct alignas(64) Node {
    float min_x[8], min_y[8], max_x[8], max_y[8];  // the boxes of the 8 slots: 128 bytes
    std::uint32_t child[8];                        // point ids in a leaf, nodes above
    std::uint16_t count, level;                    // the slots in use, and the level (0: a leaf)
};
```

An unused slot has the **empty box**: min = +∞, max = −∞. It meets no box, so the queries need no special case for it.

Guttman's R-tree inserts one box at a time. The new box goes down into the child whose box grows least. A full node **splits** into two, and Guttman's quadratic split chooses the two groups with the least wasted area. The **R\*-tree** (Beckmann, Kriegel, Schneider and Seeger, 1990) also looks at the overlap and the perimeter, and re-inserts some entries before it splits. SQLite's R\*Tree module and many others use it. PostGIS builds its R-tree on PostgreSQL's GiST framework, where the extension decides only two things: the "penalty" of putting a box into a child, and how to split a node.

## Sort-Tile-Recursive

When all points are known in advance, a database **packs** the tree instead, as the B+ tree of week 26 bulk-loaded its pages. The packed nodes are full, and their boxes are small. **Sort-Tile-Recursive** (STR, Leutenegger, Lopez and Edgington, 1997) packs $$n$$ points into $$P = \lceil n / B \rceil$$ leaves that are about square:

1. Sort the points by $$x$$, and cut them into $$S = \lceil \sqrt{P}\, \rceil$$ vertical **slices** of $$S \cdot B$$ points.
2. Sort each slice by $$y$$, and cut it into runs of $$B$$ points: the leaves.
3. Do the same with the boxes of the leaves (by their centres) to make the level above, and so on, until one node is left: the root.

So the leaves form a grid of about $$\sqrt{P} \times \sqrt{P}$$ tiles, each with $$B$$ points, and with dense data the tiles are small. Watch it, and compare it with the leaves of a tree whose points come in a random order:

{% include viz.html id="str-pack" alt="64 points of a small map are packed into leaves of 4 points. A toggle chooses the order: Sort-Tile-Recursive, the order of the Hilbert curve, or a random order. Step by step, STR sorts the points by x and cuts them into vertical slices, sorts each slice by y, and cuts it into leaves; then it packs the leaves into the nodes of the next level in the same way. Each leaf is drawn as its bounding box, and two counters give the share of the map under a leaf box and under two or more leaf boxes. With the random order, the boxes are large and cover each other." %}

Our 4,000,000 points took 1.4 s to pack by STR on one thread. A query box of 1 km × 1 km read 89 nodes on average. The same points in a random order, packed 8 to a node, give boxes that cover almost the whole country: the same query read **368,503** nodes, almost all of the tree.

Another good order is the **Hilbert curve**: sort the points by their Hilbert keys and pack them in that order, 8 to a leaf (Kamel and Faloutsos, 1993). The queries read 84 nodes, as many as with STR. This packed Hilbert R-tree is a B+ tree on Hilbert keys, with bounding boxes in its nodes. The tests and benchmarks of the queries (tasks 5, 6 and 8) use it (`pack` in `rtree.cpp`), so they do not need your STR.

## Range and nearest-neighbour queries

A **range query** is a walk from the root. At each node, the test "does the box of this slot meet the query box?" selects the children to visit. Two boxes meet when they overlap on both axes:

$$\text{min}_x \le q.\text{max}_x \;\text{and}\; q.\text{min}_x \le \text{max}_x \;\text{and}\; \text{min}_y \le q.\text{max}_y \;\text{and}\; q.\text{min}_y \le \text{max}_y.$$

In a leaf, the boxes are points, and the same test says whether the point is in the query box. A stack of nodes to visit replaces the recursion. Range queries of 1 km × 1 km took 7.3 µs each, against 14.8 ms for the scan: 2000 times faster.

A **nearest-neighbour query** cannot know which boxes to visit before it finds a near point. The **best-first** search (Hjaltason and Samet, 1999) keeps a priority queue of nodes and points, ordered by their distance from the query point. For a box, the distance is **MINDIST**: the distance from the point to the nearest place of the box, and 0 inside it:

```cpp
double min_dist2(const Rect& b, Point p) {
    const double dx = std::max({double{b.min_x} - p.x, 0.0, double{p.x} - b.max_x});
    const double dy = std::max({double{b.min_y} - p.y, 0.0, double{p.y} - b.max_y});
    return dx * dx + dy * dy;
}
```

The search takes the nearest item from the queue. A point is the next answer; a node puts its children into the queue. MINDIST is a lower bound of the distance to everything inside the box, so no point can come out of the queue before a nearer one. The search ends after $$k$$ points. It reads only the nodes whose boxes are nearer than the $$k$$-th answer, and no algorithm that uses only the boxes can read fewer. Equal distances need a rule: here a node comes before a point with the same distance, and points come by their ids. The 10 nearest points took 6.7 µs, against 43 ms for the scan.

## Time and space

For $$n$$ points, nodes of $$B$$ children and $$m$$ answers.

### Time

{: .fit }
| Operation | Time |
| --- | --- |
| Morton key with `pdep` | $$O(1)$$ |
| Hilbert key with the table | $$O(w/8)$$ |
| geohash of $$c$$ characters | $$O(c)$$ |
| hexagon of a point | $$O(1)$$ |
| the hexagons within $$k$$ steps | $$O(k^2)$$ |
| STR bulk load | $$O(n \log n)$$ |
| range query, good case | $$O(\log_B n + m/B)$$ |
| range query, worst case | $$O(n/B)$$ |
| $$k$$ nearest, best first | the nodes nearer than the $$k$$-th answer |

`pdep` takes one instruction for each coordinate; a loop over the $$w$$ bits would take $$O(w)$$. The Hilbert table does one lookup per byte of the Morton key, and a geohash halves the box 5 times for each character. The hexagon of a point is a rounding, and there are $$1 + 3k(k + 1)$$ hexagons within $$k$$ steps. The sorts of STR cost $$O(n \log n)$$; the levels above the leaves add only $$n/B$$, $$n/B^2$$, … entries. Best-first search reads the fewest nodes possible, and each item costs a push and a pop of its priority queue: $$O(\log q)$$ for a queue of $$q$$ items.

The worst case of the range query is real. Long thin boxes that all cross the query force a visit to every node. Arge, de Berg, Haverkort and Yi (2004) built the **PR-tree**, the first R-tree with a good worst case: $$O(\sqrt{n/B} + m/B)$$ nodes for any range query. For points of real maps, STR and Hilbert packing are close to the good case: our queries read 89 of the tree's 571,432 nodes.

### Space

The tree takes $$O(n)$$ space: $$n/B$$ leaves, $$n/B^2$$ nodes above them, and so on, about $$n/(B - 1)$$ nodes in all. A range query needs room for its $$m$$ answers, and a nearest-neighbour query for its priority queue.

## SIMD: eight boxes in one compare

A query tests up to 8 boxes in each node it reads, and each test is 4 compares. The scalar loop of `ScalarTest` stops at the first compare that fails, so it has branches that the CPU cannot predict. The struct of arrays makes the test a perfect fit for AVX2: one register holds `min_x` of all 8 slots, and `_mm256_cmp_ps` compares 8 floats at once:

```cpp
const __m256 a = _mm256_cmp_ps(_mm256_load_ps(n.min_x), _mm256_set1_ps(q.max_x), _CMP_LE_OQ);  // min_x <= q.max_x
const __m256 b = _mm256_cmp_ps(_mm256_set1_ps(q.min_x), _mm256_load_ps(n.max_x), _CMP_LE_OQ);  // q.min_x <= max_x
// ... the same two compares for y, then AND the four results
return static_cast<unsigned>(_mm256_movemask_ps(_mm256_and_ps(_mm256_and_ps(a, b), _mm256_and_ps(c, d))));
```

The result is a mask of 8 bits, one per slot, and the query visits the set bits with `countr_zero`, as in the Swiss table of chapter 28. The empty boxes of unused slots fail the compare `min_x <= q.max_x` (+∞ is larger than everything), so no mask of the count is needed. `_CMP_LE_OQ` is "less or equal, ordered, quiet": a compare with NaN gives false and raises no exception.

Below, four rows of 8 lanes give the results of the four compares, min_x <= q.max_x, q.min_x <= max_x, min_y <= q.max_y and q.min_y <= max_y, as 1 or 0; then their AND and the 8-bit mask from movemask. Unused slots have the empty box and are 0 in all four rows. The boxes that meet the query are green." %}

In 4 million tests of nodes in the L2 cache, the scalar loop took 50 ns per node, and AVX2 4.1 ns: **12 times faster**. Whole range queries became 1.7 times faster. A query also does other work: it reads the nodes from memory, keeps the stack, and writes the answers.

## Threads: building and querying

STR is a sort and then independent work on each slice. On one thread, the first sort by $$x$$ of all 4,000,000 points takes most of the time. But STR does not need the points of a slice in sorted order, only the right points: the slice of points $$j S B$$ to $$(j + 1) S B - 1$$ of the order by $$x$$. `std::nth_element` puts the right points on both sides of one border in $$O(n)$$ time, and the two sides are independent. So a recursive split at the middle border, in OpenMP tasks, finds all $$S$$ slices in $$O(n \log S)$$ work, mostly in parallel. Then each thread sorts whole slices by $$y$$ and makes their nodes. Every slice except the last makes exactly $$S$$ nodes, so each slice knows the places of its nodes in advance, and the threads write them without waiting for each other. The tree is exactly the tree of the sequential STR.

On our 4 cores, STR of 4,000,000 points took 1.39 s on one thread and 0.47 s in parallel: 2.95 times faster.

## Bonus: inside a polygon, eight points at a time

An R-tree answers with boxes. A real question is often about a shape: which points are inside the border of a town, a lake or a delivery zone? A spatial database answers it in two steps: the index finds the candidates whose boxes meet the box of the shape (the **filter**), and an exact test checks each candidate (the **refinement**).

The classic test is the **crossing number**: a ray from the point to the right crosses the border of the polygon an odd number of times if and only if the point is inside. For each edge from $$a$$ to $$b$$, the ray crosses it when the edge spans the $$y$$ of the point and the crossing is to the right of the point. The test of one point loops over all edges, with a branch on every edge. But each edge does the same arithmetic for every point. So turn the loops around: take 8 points in the lanes of an AVX2 register, and run over the edges once for all of them:

```cpp
// Bit i: point i (xs[i], ys[i]) is inside the polygon.
unsigned inside8(std::span<const Point> poly, const float* xs, const float* ys) {
    const __m256 px = _mm256_loadu_ps(xs), py = _mm256_loadu_ps(ys);
    __m256 in = _mm256_setzero_ps();

    for (std::size_t i = 0, j = poly.size() - 1; i < poly.size(); j = i++) {
        const Point a = poly[i], b = poly[j];
        const __m256 ay = _mm256_set1_ps(a.y), by = _mm256_set1_ps(b.y);
        const __m256 spans = _mm256_xor_ps(_mm256_cmp_ps(ay, py, _CMP_GT_OQ), _mm256_cmp_ps(by, py, _CMP_GT_OQ));
        const __m256 slope = _mm256_set1_ps((b.x - a.x) / (b.y - a.y));  // once per edge, for all 8 points
        const __m256 cross = _mm256_fmadd_ps(slope, _mm256_sub_ps(py, ay), _mm256_set1_ps(a.x));  // x of the crossing
        in = _mm256_xor_ps(in, _mm256_and_ps(spans, _mm256_cmp_ps(px, cross, _CMP_LT_OQ)));  // flip the lanes that cross
    }

    return static_cast<unsigned>(_mm256_movemask_ps(in));
}
```

An edge that does not span the point's $$y$$ can have $$b.y = a.y$$, and then the slope is ±∞ or NaN. That does not matter: the AND with `spans` drops such lanes, and the compares are "quiet", so NaN raises nothing. For a polygon of 200 corners and 1,048,576 points, the scalar test took 315 ns per point, and AVX2 50 ns: **6.3 times faster**, with the same answer for every point. GCC did not vectorize the scalar loop by itself.

Points exactly on the border are a question of rules, not of speed. The two versions compute the crossing with different roundings (one division per point, or one per edge and an FMA), so for a point within a rounding error of an edge, their answers can differ. Libraries such as GEOS and Boost.Geometry use exact predicates there.
