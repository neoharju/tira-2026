# 29. Tries and Radix Trees

Last week's hash table finds a key with one or two cache misses, but it does not keep the keys in order. A B+ tree keeps the order, but on every level it compares whole keys with a binary search or SIMD compares. A **trie** does something different. It reads the key one piece at a time, and each piece selects the next node directly, as an index into an array. There is no compare of whole keys until the end, and the path does not depend on the number of keys, only on the length of the key.

Tries are everywhere in systems:

* Every Internet router finds the route of a packet with a trie. The address is the key, and the router looks for the **longest prefix** that matches it.
* In-memory databases use the **adaptive radix tree** (ART) as their index: HyPer, for which it was designed, and DuckDB. Since version 17, PostgreSQL uses a radix tree to remember the dead rows during `VACUUM`, with up to 20 times less memory than before.
* The Linux kernel finds the pages of a file in its cache with a radix tree (the XArray), and IPv4 routes with an LC-trie (`fib_trie`). Redis keeps its streams in a radix tree.

This week we build the adaptive radix tree of Leis, Kemper and Neumann (2013), step by step:

1. what a **trie** is, and why a plain trie needs too much memory;
2. **lazy expansion** and **path compression**, which remove most of the nodes, and **adaptive nodes** of four sizes, which remove most of the empty slots;
3. **find**, **insert** and **range scans**, and what they cost;
4. a search inside a node of 16 keys with **SIMD**, for equal bytes and for the place of a byte;
5. **longest-prefix match** for IP routing, with a table that answers with one or two memory reads;
6. a tree built by **many threads**, also when the keys are uneven.

The tasks are in the folder `cpp/week29`. Keys and values are 64-bit numbers. The header `art.hpp` gives the exact rules of the tree, and `validate()` checks them. The tests of tasks 1 and 3 use trees from the given `bulk_build`, so they do not need your insert. Each benchmark first checks your result: a wrong result is not timed.

## Keys as strings of bytes

A trie does not compare keys. It looks at them as **strings of bytes**: byte 0, then byte 1, and so on. So the order of the bytes must be the order of the keys. For our 64-bit numbers, we read the bytes from the most significant byte down (big-endian). Then comparing the bytes one by one gives the same result as comparing the numbers:

```cpp
// Byte i of the key: byte 0 is bits 63-56, and byte 7 is bits 7-0.
constexpr std::uint8_t key_byte(Key key, unsigned i) {
    return static_cast<std::uint8_t>(key >> (56 - 8 * i));
}
```

Databases need other keys too, so they change each key into such a string of bytes. Such keys are called **binary-comparable**:

* A signed integer gets its top bit flipped. After the flip, −1 is `0x7F…FF` and 0 is `0x80…00`, so −1 comes first, as it should.
* A string is its bytes, followed by a byte 0 as its end. So "car" comes before "cart", and no key is a prefix of another key.
* A key of several columns, such as (city, street), is the bytes of the first column, then the bytes of the next one.

DuckDB, the ART paper and many key-value stores make their keys like this. This chapter uses 64-bit numbers, and the bonus at the end looks at strings.

## Tries

A **trie** (Fredkin, 1960, from re*trie*val) is a tree where each level reads one piece of the key. A node of a trie that reads 8 bits has 256 child pointers, one for each value of the byte. A search goes down from the root and uses byte $$d$$ of the key as the index into the node at depth $$d$$. After 8 levels, it is at the key, or it found an empty pointer on the way: then the key is not there.

The number of bits per level is the **span** $$s$$. It sets two things: the height $$k/s$$ for keys of $$k$$ bits, and the size of a node, $$2^s$$ pointers. For 64-bit keys:

{: .grid-head }
| Span $$s$$ | Height | Size of a node (8-byte pointers) |
| --- | --- | --- |
| 1 bit | 64 | 16 bytes |
| 4 bits | 16 | 128 bytes |
| 8 bits | 8 | 2 KB |
| 16 bits | 4 | 512 KB |

A search in a trie costs $$O(k/s)$$ steps, for any number of keys $$n$$. A balanced search tree costs $$O(\log n)$$ compares of whole keys: about 20 for a million keys, and every compare can be a cache miss. A trie with a span of 8 takes at most 8 steps, and each step is one load at a known place.

But look at the memory. A plain trie has a node for every prefix of every key. For a million random 64-bit keys, our count was **5,036,458 nodes** of 2 KB each: **10.4 GB** for 16 MB of keys. Almost all slots of these nodes are empty: below the first three levels, most nodes have only one child. Tries became practical only with the ideas of the next two sections.

## Lazy expansion and path compression

In the figure, the keys are 16 bits long, and each level reads 4 bits: one hex digit. So a node has 16 children (real ART nodes read a byte and have up to 256). Insert the keys one by one, and compare the three ways to store them:

{% include viz.html id="art-insert" alt="A tree of 16-bit keys written as four hex digits, where each level reads one digit. Twelve keys are inserted step by step. A toggle chooses the view: a plain trie, where every key has a node on all four levels; lazy expansion, where a key is a leaf as soon as it is the only key below a place; and a radix tree with path compression and adaptive nodes, where a node exists only where keys branch, its compressed digits are written on it, and a node grows from Node4 to Node16 at its fifth child. The caption explains each insert: a new leaf in a node, a leaf that becomes a node, a path that splits, or a node that grows. A panel counts the nodes and the bytes of each view." %}

Two ideas remove most of the nodes:

* **Lazy expansion.** When only one key is below a place in the tree, the tree stops there and stores the key as a **leaf**. The search has not looked at the rest of the key's bytes yet. So the leaf keeps the whole key, and the search compares it at the end. For a million random keys, this leaves 94,538 inner nodes instead of 5,036,458.
* **Path compression** (Morrison, 1968: PATRICIA). When all keys below a node have the same next bytes, no node branches on them. The node skips these bytes, and it remembers them as its **prefix**. For keys 0, 1, …, 999,999, the top 5 bytes are 0 in every key. So the root branches on byte 5, and its prefix is the 5 zero bytes.

With both ideas, every inner node branches: it has at least 2 children. A tree of $$n$$ keys then has at most $$n - 1$$ inner nodes, whatever the length of the keys. Such a trie is a **radix tree**.

Our tree stores the prefix in a special way. With 8-byte keys, a node can keep its whole prefix in one 64-bit word, together with its `depth`: the byte on which it branches. The other bytes of `prefix` are 0. Then the check "does the key have the prefix of this node?" is one XOR and one AND:

```cpp
// The bits of the first d bytes of a key (d = 0 ... 8).
constexpr Key prefix_mask(unsigned d) { return d == 0 ? 0 : ~Key{0} << (64 - 8 * d); }

bool has_prefix(const Inner& n, Key key) {
    return ((key ^ n.prefix) & prefix_mask(n.depth)) == 0;
}
```

The ART paper stores only the skipped bytes since the parent, and longer keys need that. For our keys, the absolute prefix makes insert simpler: when a new node goes above an old one, the old node does not change.

## The adaptive radix tree

Lazy expansion and path compression remove nodes, but a node of 256 pointers is still 2 KB. Most nodes have only a few children. The million random keys need 94,438 inner nodes: with 2 KB each, and the leaves, that is still 219 MB. The **adaptive radix tree** (ART) of Leis, Kemper and Neumann (2013) gives each node the smallest of four kinds that has room for its children:

{: .grid-head }
| Kind | Children | Layout | Bytes (ours) |
| --- | --- | --- | --- |
| Node4 | 2–4 | 4 key bytes and 4 pointers, sorted by byte | 56 |
| Node16 | 5–16 | 16 key bytes and 16 pointers, sorted by byte | 160 |
| Node48 | 17–48 | an index of 256 bytes, and 48 pointers | 656 |
| Node256 | 49–256 | 256 pointers | 2064 |

Each kind starts with a header of 16 bytes: its kind, its depth, the number of children and the prefix. In a Node48, `index[b]` is the place of the child of byte `b` in the array of 48 pointers, or the value `no_child`. So Node48 finds a child with two loads and no search, but it needs only 656 bytes. Choose a number of children and compare the layouts:

{% include viz.html id="art-nodes" alt="The four kinds of ART nodes as cards, each with a bar of its parts in bytes: the header, the key bytes or the index, and the pointers. A slider sets the number of children from 2 to 256; the kind that holds them is highlighted with its size and its bytes per child, and the kinds that are too small are faded. A chart below shows the bytes per child against the number of children, on log scales: a sawtooth for the smallest kind that fits, which stays below 43 bytes, and a falling line for a Node256 alone, which costs 1032 bytes per child at 2 children." %}

Our 1,000,000 random keys need 28,683 Node4, 44,818 Node16, 20,680 Node48 and 257 Node256: **47 MB**, 47 bytes per key. Of these, 24 bytes are the leaf. The keys 0, …, 999,999 are dense, and their tree is the other extreme: 3,923 Node256, almost all of them full, and one Node16 above them, 32 bytes per key. For a dense key set a trie wastes nothing.

There is a bound for every key set. Each inner node has at least 2 children, so we can charge its bytes to $$c - 1$$ of its $$c$$ children. Every leaf and every inner node except the root is a child, so the charges add up to $$n - 1$$ for $$n$$ keys. The largest charge per child is a Node4 with 2 children: 56 bytes. So the inner nodes of our ART never take more than **56 bytes per key**, on top of the 24 bytes of the leaf. The ART paper gives the same bound, 52 bytes, with their Node4 of 52 bytes. A plain trie, or a radix tree with only Node256, has no such bound.

## Find

A search starts at the root. At an inner node, it first checks the prefix: if the key does not have the prefix of the node, the key is not in the tree. Then it finds the child of the key's byte at the node's depth:

* **Node4**: compare the byte with the 4 key bytes;
* **Node16**: find the byte among 16 key bytes (the SIMD sections below);
* **Node48**: `index[b]`, and then the pointer at that place;
* **Node256**: the pointer `children[b]`.

At a leaf, it compares the whole key. In C++, a node is a `Node*`, and its first byte, `kind`, says which struct it really is. A `static_cast` from `Node*` to the right kind is safe after we check `kind`.

There are two ways to treat the prefixes. The **pessimistic** search checks the prefix of every node, as above. The **optimistic** search skips these checks: a wrong key arrives at a wrong leaf, and the compare at the leaf finds it. On our machine, with half of the lookups for keys that are not in the tree:

{: .grid-head }
| ns per lookup | ART, pessimistic | ART, optimistic | `std::map` | `std::unordered_map` | sorted array, `std::lower_bound` |
| --- | --- | --- | --- | --- | --- |
| 1,000,000 random keys | 81 | 72 | 808 | 30 | 202 |
| keys 0 … 999,999 | 38 | 66 | 420 | 17 | 117 |

For random keys, the optimistic search saves the work of the checks. For dense keys, it is slower. A random key has a byte that is not 0 in the first 5 bytes, so the pessimistic check at the root stops it at once. The optimistic search follows bytes 5, 6 and 7 down to a leaf: three cache misses for nothing. The ART paper uses a hybrid: pessimistic for short prefixes, and optimistic for prefixes that are too long to store in the node.

(Our virtual machine is noisy: the times of this chapter change by 10–30 % from run to run, and `std::map` changes even more. Look at the ratios, not at the last digit.) ART is 10 times faster than `std::map`, the red-black tree of C++: 3 or 4 nodes on the path, instead of 20. A good hash table is still 2–3 times faster for a lookup. It reads one or two cache lines, and ART reads one per level and then the leaf. What ART adds is the order of the keys.

## Insert

An insert walks down like find. It stops at the first place where the key leaves the tree, and there are four cases:

1. **An empty place in a node**: the node has no child for the key's byte. The new leaf becomes a child of the node. If the node is full, it **grows** first: a full Node4 becomes a Node16, a Node16 a Node48, and a Node48 a Node256. The node is copied into a node of the next kind, the old node is freed, and the pointer in the parent changes.
2. **A leaf with another key**: lazy expansion ends here. A new Node4 takes the place of the leaf. It branches on the first byte where the two keys differ, `countl_zero(old ^ key) / 8`, and its two children are the old leaf and the new one.
3. **A node whose prefix the key does not have**: the compressed path splits. A new Node4 goes above the node, at the first byte where the key and the prefix differ. Its children are the old node and the new leaf. The old node does not change, because its prefix and depth are absolute.
4. **A leaf with the same key**: the value changes, and insert returns `false`.

Follow the twelve inserts of the figure above again. Each step names its case.

The parent's pointer must change in cases 1 to 3. So the walk keeps a `Node**`: the address of the pointer that points to the current node. The pointer can be the root, or a slot in a parent node:

```cpp
Node** ref = &root;

for (;;) {
    Node* n = *ref;
    // ... the four cases: a new node goes into *ref
    ref = /* the address of the child's slot in n */;
}
```

Growing a node costs a copy of at most 48 pointers, and a node grows at most 3 times. So each insert does $$O(k)$$ work, plus the growth of one node, which is $$O(1)$$ amortized. Insert can also make at most 2 new nodes: a leaf, and one Node4.

The tree of a set of keys is always the same, in whatever order the keys come: a node exists exactly where keys branch, and its kind depends only on its number of children. (This is true because we do not erase keys. With erase, a node shrinks only when it is much smaller, so that a node with 48 or 49 children does not change its kind on every insert and erase. Then the tree depends on the history.) The given `bulk_build` builds this tree from sorted keys, from the top down, and the tests compare your tree with it.

For a million random keys in random order, an insert took 264 ns in ART, 927 ns in `std::map` and 219 ns in `std::unordered_map`. For dense keys, ART took 154 ns: it fills full Node256s, and the leaves come one after another.

## Range scans

A trie keeps its keys in order: the children of a node, in the order of their bytes, hold larger and larger keys. So a **range scan**, all keys from `lo` to `hi`, is an in-order walk that skips the subtrees outside the range. The keys below a node with depth $$d$$ and prefix $$p$$ are all between

$$\text{first} = p \qquad\text{and}\qquad \text{last} = p \mathbin{|} \lnot\,\text{mask}(d),$$

where $$\text{mask}(d)$$ is `prefix_mask(d)`. So `last` is $$p$$ with all bits after the first $$d$$ bytes set to 1. The scan uses three tests at each node:

* If the node's range $$[\text{first}, \text{last}]$$ does not meet $$[\text{lo}, \text{hi}]$$, skip the node.
* If it is inside $$[\text{lo}, \text{hi}]$$, append all its keys, with no more tests.
* Otherwise, visit only the children from the byte of `lo` to the byte of `hi`, at the node's depth. If `lo` does not have the prefix of the node, it is smaller than all keys below the node: start at the first child. In the same way, if `hi` does not have the prefix, go on to the last child. In a Node16, `lower16` finds the first child to visit.

A scan costs $$O(k)$$ steps down to the first key, and then about one step per key that it appends. A visited Node48 or Node256 can add up to 256 slot reads. The **prefix scan**, all keys that start with some bytes, is a range scan too: from the prefix with zeros to the prefix with ones. Tries are made for it, and autocomplete in a search box is a prefix scan.

How fast is it? For 100,000 scans of about 100 keys each, in 1,000,000 random keys, ART took about 160 ms in every run, and `std::map` between 150 and 270 ms: at most 1.7 times faster, and in some runs not faster at all. In both trees, every key is a node of its own, often in its own cache line, and a scan reads one line per key. The B+ tree of chapter 26 has 64 keys in a page, and it was 6 times faster than `std::map` in a test of the same size. For long range scans, a B+ tree is the better index. For point lookups and short scans, ART is better.

## Time and space

Here are the costs of this chapter's tree for $$n$$ keys of $$k$$ bytes ($$k = 8$$ for our keys), with $$m$$ results for a scan:

{: .grid-head }
| Operation | Time | Why |
| --- | --- | --- |
| find | $$O(k)$$ | at most one node per byte, and $$O(1)$$ work in each node |
| insert | $$O(k)$$, amortized | the walk, at most 2 new nodes, and a node grows at most 3 times |
| scan | $$O(k + m)$$ | down to the first key, then the keys in order (plus up to 256 slots per visited Node48 or Node256) |
| `bulk_build` | $$O(kn)$$ after sorting | each level reads the keys of each node once |
| Space | $$O(n)$$ | fewer than $$n$$ inner nodes; at most 56 bytes of inner nodes per key, plus 24 for the leaf |

Compare this with a balanced binary tree, $$O(\log n)$$ compares of whole keys, and with a B+ tree, $$O(\log_B n)$$ pages with $$O(\log B)$$ compares in each. ART does not depend on $$n$$, only on the length of the keys: with lazy expansion, the height of a tree of random keys is close to $$\log_{256} n$$, about 3 nodes for a million keys.

## SIMD: a byte among 16

A Node16 has up to 16 key bytes, sorted. A loop compares them one by one and stops at the first byte that is equal or larger. This stop is a branch at a random place, and the CPU guesses it wrong in almost every search. The ART paper finds the byte with SSE2, like the Swiss table of chapter 28. 16 bytes are one 128-bit register:

```cpp
const __m128i keys = _mm_loadu_si128(reinterpret_cast<const __m128i*>(n.keys));
const __m128i eq = _mm_cmpeq_epi8(keys, _mm_set1_epi8(static_cast<char>(b)));  // 0xFF where equal
const unsigned mask = static_cast<unsigned>(_mm_movemask_epi8(eq)) & ((1u << n.count) - 1);
```

`_mm_movemask_epi8` collects the top bit of each byte into an integer. A Node16 with 7 children has garbage in `keys[7 ... 15]`, so the AND with `(1u << count) - 1` keeps only the bits of the 7 bytes that mean something. Then the place of the byte is `std::countr_zero(mask)`, or the byte is not there if the mask is 0. The load reads all 16 bytes, also the unused ones, but they are inside the node, so the load is safe.

{% include viz.html id="node16-simd" alt="A Node16 with 11 sorted key bytes and 5 unused places with garbage, and a slider for the byte b. Step by step: the 16 bytes in a register, b in all 16 lanes, the compare, the 16-bit movemask, the mask of the count, and the answer. A toggle chooses the search: equal bytes with cmpeq and countr_zero, or the place of b with cmplt and popcount. For the place, a second toggle flips the top bit or not; without the flip, key bytes of 128 or more count as smaller than b, and the answer is wrong." %}

In 4 million searches in 4096 Node16s (640 KB, in the L2 cache), the scalar loop took 17 ns per search, and SSE2 1.45 ns: **12 times faster**. In the whole tree of a million keys, find became only 1.38 times faster. The search inside a node is now cheap, so the time goes to the cache misses between the nodes. This is Amdahl's law again.

## SIMD: where a byte belongs

Insert and scan need another search in a Node16: not "where is byte `b`?" but "how many key bytes are less than `b`?". That is the place where `b` belongs. SSE2 has `_mm_cmplt_epi8`, but it compares **signed** bytes, and our key bytes are unsigned. As a signed byte, 0x80 is −128, so the signed compare puts the bytes 128–255 before the bytes 0–127.

This is the problem of chapter 26 again, and so is the solution: flip the top bit of both sides. XOR with 0x80 moves the unsigned bytes 0–255 onto the signed bytes −128–127, in the same order:

```cpp
const __m128i flip = _mm_set1_epi8(static_cast<char>(0x80));
const __m128i keys = _mm_xor_si128(_mm_loadu_si128(reinterpret_cast<const __m128i*>(n.keys)), flip);
const __m128i less = _mm_cmplt_epi8(keys, _mm_set1_epi8(static_cast<char>(b ^ 0x80)));  // key < b, unsigned
```

The bits of `less` are a run of ones (the keys are sorted), so the answer is the number of ones after the mask of the count: `std::popcount`. The ART paper does it a little differently. It stores the key bytes of a Node16 already flipped, so a search flips only `b`. Try the toggle in the figure above: without the flip, a byte of 128 or more is counted as smaller than every byte below 128.

AVX-512 does not need the flip. With AVX-512BW and AVX-512VL, `_mm_mask_cmplt_epu8_mask(count_mask, keys, set1(b))` compares unsigned bytes. It also takes the mask of the count, and it returns the bits in a mask register. On our machine, the SSE2 version took 1.04 ns per search, and the scalar loop 16 ns. Insert with `SimdSearch` was 1.2 times faster.

## Longest-prefix match

A router does not look up whole addresses. Its table has **prefixes**: the route `10.1.0.0/16` covers every address whose first 16 bits are those of 10.1.0.0. The prefixes can contain each other: `10.0.0.0/8` contains `10.1.0.0/16`, which contains `10.1.2.0/24`. For each packet, the router must find the **longest prefix** that matches the destination address. The longest prefix is the most specific route. The global table of the Internet has about a million IPv4 prefixes, and a router port of 100 Gbit/s must do up to 150 million lookups per second (with the smallest packets), one every 7 ns.

A **binary trie** is the classic answer. It reads one bit per level, and a route ends at the node of its last bit. A lookup walks down along the bits of the address and remembers the last route that it passed: that is the longest match. Our baseline is this trie. It needs up to 32 steps, each one a load that depends on the load before it. For our table of a million routes, a lookup took 275 ns.

The fastest software tables do the opposite: they spend memory to save steps. **DIR-24-8** (Gupta, Lin and McKeown, 1998) is a multibit trie with only two levels, a span of 24 bits and then 8 bits:

* `tbl24` has $$2^{24}$$ entries, one for each value of the first 24 bits of an address. An entry holds the next hop of the longest prefix of length $$\le 24$$ that matches those 24 bits.
* For the few groups of 24 bits that also have longer prefixes, the entry points to a **group** of 256 entries in `tbl8`, one for each value of the last 8 bits.

Building the table uses **prefix expansion**: a prefix of length $$l \le 24$$ fills $$2^{24 - l}$$ entries of `tbl24`. A `/16` fills 256 entries, and a `/24` one entry. Process the routes from the shortest to the longest. Then a longer prefix overwrites the entries of the shorter prefixes that contain it. A new group starts with 256 copies of the entry that it replaces. The figure shows the same idea with addresses of 8 bits, a first table of 32 entries and groups of 8:

{% include viz.html id="lpm-dir" alt="Longest-prefix match for addresses of 8 bits. A list of eight routes with nested prefixes and their next hops, a first table of 32 entries for the first 5 bits, colored by next hop, and groups of 8 entries for the prefixes longer than 5 bits. Step by step the table is built: the routes fill their ranges from the shortest to the longest, and the two longest routes create groups. Then an address slider looks up an address: a row of its 8 bits marks where routes end on the path of the binary trie, the longest of them is highlighted in the list, and the table reads one entry, or an entry and a group, with the same answer." %}

A lookup is one load, or two for the rare addresses with a group:

```cpp
Hop Lpm::lookup(std::uint32_t address) const {
    const std::uint32_t e = tbl24[address >> 8];
    return (e & group_bit) == 0 ? e : tbl8[256 * (e & ~group_bit) + (address & 255)];
}
```

For our table of a million routes, DIR-24-8 took **8.3 ns** per lookup, and the binary trie 275 ns: 33 times faster. The price is memory: `tbl24` alone is 64 MB, for any number of routes. That does not fit in the caches, so most lookups wait for main memory. But they are independent, so the CPU overlaps many of them. When each lookup had to wait for the one before (the next address depended on the last answer), DIR-24-8 took 107 ns, and the binary trie 436 ns.

Real tables add a few details. 60 % of the routes of the global table are `/24`, so almost all lookups need only `tbl24`. Routes longer than `/24` are filtered out between networks, but a provider's own network has them. DPDK's `rte_lpm` library, which forwards packets in user space, uses this layout, and the Linux kernel uses an LC-trie, which compresses levels and paths of the binary trie.

The cost: a lookup reads 1 or 2 entries, $$O(1)$$. The binary trie needs $$O(W)$$ steps for addresses of $$W = 32$$ bits, and $$O(nW)$$ memory. DIR-24-8 needs $$2^{24} + 256\,g$$ entries for $$g$$ groups, and building it writes $$\sum 2^{24 - l}$$ entries for the routes of length $$l \le 24$$.

## Threads: building by key ranges

The given `bulk_build` needs sorted keys. Sorting 4,000,000 keys and building their tree took 520–700 ms on one thread in our runs (our machine is noisy). More than half of it was `std::sort`, and the rest made the nodes. Can threads help?

The subtrees of a node do not depend on each other. The tree of the keys that start with byte 0x00 is the same, whatever the other keys are. So the build splits into independent parts, like the partition and merge of chapter 17:

1. The smallest and the largest key give the byte where the root branches: the first byte where they differ. A parallel reduction finds them.
2. **Group** the keys by that byte, in parallel. Each thread counts the bytes of its part of the input. Then the prefix sums of the counts give each thread its own places in each group (the parallel counting sort of chapter 21). Each thread writes its keys to its places, and no two threads write to the same place.
3. **Build** the groups in parallel, one thread for each group: sort the group, and `bulk_build_nodes` makes its subtree. `schedule(dynamic, 1)` gives the next group to the next free thread.
4. Make the root, and add the subtrees as its children.

The keys of a group share their first bytes, so `bulk_build_nodes` of a group makes exactly the subtree of the full tree, with the same depths and prefixes. Sorting the groups is also less work than sorting all keys: $$n \log_2(n/256)$$ compares instead of $$n \log_2 n$$.

Memory needs care, as in chapter 25. `std::vector<Item> room(n)` fills its 64 MB with zeros on one thread. `std::make_unique_for_overwrite<Item[]>(n)` does not, and each page is first written by the thread that groups keys into it. The nodes come from `operator new`. glibc's `malloc` gives each thread its own arena, so the threads do not wait for each other there. But it is not free: in our tests, 4 threads that made 4,000,000 leaves in memory that other threads had freed took longer than one thread.

On our 4 cores, the build of 4,000,000 random keys took 454 ms on one thread, 273 ms on two and 150 ms on four. In the same run, the baseline (sort, then `bulk_build`) took 680–700 ms. Even the run on one thread is faster than the baseline, because it sorts small groups.

## Uneven ranges

Random keys fill the 256 groups evenly. Real keys are rarely random. Suppose that 70 % of the keys start with the byte 0x2A: the ids of one large customer, or the timestamps of one day. Then one group has 70 % of the work. One thread builds it, and the other threads wait. Amdahl's law limits the speedup to $$1/0.7 \approx 1.4$$. In our test, a build that grouped the keys only once was 1.32 times faster than the baseline.

The cure: a group that is too large for one thread is split again, by its own next byte, with all threads. Our build splits again every group with more than $$n / (2T)$$ keys for $$T$$ threads. Then the large group becomes 256 small groups, and the threads share them. With this rule, the skewed keys were built 2.3–2.9 times faster than the baseline in our runs. A level that splits again needs room for the moved keys too. The input of the level below can use the memory of its own group as that room, because the keys move to the other buffer first.

The tree is the same for any order of the keys, and our build depends on this. The groups of the first byte are exactly the children of the root, and so on down. A B+ tree has no such rule: its pages depend on the order of the inserts, and its parallel bulk load in chapter 26 needed sorted input and the sizes of all pages.

* Viktor Leis, Alfons Kemper and Thomas Neumann: [_The Adaptive Radix Tree: ARTful Indexing for Main-Memory Databases_](https://doi.org/10.1109/ICDE.2013.6544812) (ICDE 2013). The four kinds of nodes, lazy expansion, path compression (pessimistic, optimistic and hybrid), and the SSE2 search in Node16. Short and very readable.
* [libart](https://github.com/armon/libart) by Armon Dadgar: an ART in C for string keys, in one file ([`src/art.c`](https://github.com/armon/libart/blob/HEAD/src/art.c)), with insert, delete and prefix scans. Look at `find_child`, `add_child16` and `remove_child256`. Its nodes shrink at 37, 12 and 3 children, so that a node does not change its kind on every insert and erase.
* DuckDB: the ART indexes in [`src/execution/index/art`](https://github.com/duckdb/duckdb/tree/main/src/execution/index/art), with nodes in fixed-size buffers and keys in binary-comparable form; and the blog post [_Persistent ART Storage in DuckDB_](https://duckdb.org/2022/07/27/art-storage.html).
* PostgreSQL: [`src/include/lib/radixtree.h`](https://github.com/postgres/postgres/blob/HEAD/src/include/lib/radixtree.h), an adaptive radix tree as a C template, which `VACUUM` uses since PostgreSQL 17 to store the ids of dead rows (`TidStore`).
* The Linux kernel: [`net/ipv4/fib_trie.c`](https://github.com/torvalds/linux/blob/HEAD/net/ipv4/fib_trie.c), the IPv4 routing table as an LC-trie; Stefan Nilsson and Gunnar Karlsson: [_IP-address lookup using LC-tries_](https://doi.org/10.1109/49.772439) (IEEE Journal on Selected Areas in Communications, 1999). ## Bonus: strings as keys

This chapter's keys were 8 bytes. Most real keys are longer: names, URLs, the binary-comparable keys of several columns. Then two operations of the tree work on byte strings. A search compares a compressed prefix with the key. An insert asks where two keys first differ: at that byte, a leaf becomes a Node4, or a path splits. For our 64-bit keys, this was one instruction, `countl_zero(a ^ b) / 8`. For strings, a loop compares one byte per step, with an unpredictable stop.

SIMD compares 16 bytes in one step, as in the Node16 search, and finds the first different byte with `countr_one` of the mask of equal bytes:

```cpp
// The first place where a and b differ; both have n bytes that can be read.
std::size_t first_difference(const char* a, const char* b, std::size_t n) {
    std::size_t i = 0;

    for (; i + 16 <= n; i += 16) {
        const __m128i x = _mm_loadu_si128(reinterpret_cast<const __m128i*>(a + i));
        const __m128i y = _mm_loadu_si128(reinterpret_cast<const __m128i*>(b + i));
        const auto same = static_cast<unsigned>(_mm_movemask_epi8(_mm_cmpeq_epi8(x, y)));  // bit j: byte j is equal

        if (same != 0xFFFF)
            return i + static_cast<std::size_t>(std::countr_one(same));  // the ones before the first zero
    }

    while (i < n && a[i] == b[i])
        ++i;

    return i;
}
```

We compared 200,000 pairs of strings of 100 letters, with a common start of 0 to 99 letters. The byte loop took 51 ns per pair, `std::mismatch` 57 ns, the SSE2 version 21 ns and an AVX2 version with 32 bytes per step 20 ns. Long common starts are typical of keys in a trie: URLs that start with `https://www.`, file paths, or keys whose first column is the same.

Strings bring one more rule. A key must not be a prefix of another key, or a leaf would have to sit inside the path of another leaf. Binary-comparable strings solve this with their end byte 0, as in the first section of this chapter. But a string may contain the byte 0. Then each 0 inside the string is written as the two bytes 0x00 0xFF, and the end is the two bytes 0x00 0x01, as in CockroachDB. Inside a key, a 0x00 is always followed by 0xFF, so the end mark appears only at the end, and no key is a prefix of another. The order stays correct too: the end mark is smaller than an escaped 0, and both are smaller than every other byte.

Bonus exercise (no points): make a version of your tree for `std::string` keys, with the end byte. A leaf keeps the whole key, and an inner node keeps its depth and a pointer to the key of one of its leaves instead of the 64-bit prefix (the optimistic method of the ART paper). Insert the words of a book or the paths of all files under `/usr`, and compare the speed of find with `std::map<std::string, …>`. How much does `first_difference` with SSE2 add?
