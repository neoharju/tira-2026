# 31. LSM Trees

The B+ tree of week 26 changes its pages in place. To insert a key, it finds the leaf, changes a few bytes, and writes the whole page back to the disk: 8 KB for a record of 100 bytes, at a random place in the file. A store that takes 100,000 writes per second cannot work like that. The **log-structured merge tree**, or **LSM tree** (O'Neil, Cheng, Gawlick and O'Neil, 1996), never changes data on the disk. It collects new writes in memory, writes them out as large sorted files, and merges the files later in the background. Every write to the disk is a long sequential write.

LSM trees store a large part of the world's data. Google's Bigtable (2006) and LevelDB (2011) made them popular. RocksDB, Meta's fork of LevelDB, is inside MySQL's MyRocks, TiKV, Kafka Streams and many other systems. CockroachDB uses Pebble, and Apache Cassandra, ScyllaDB and HBase have their own LSM trees.

This week we build a small LSM-tree store, part by part:

1. the **write-ahead log**, which makes a write durable with one append, and the recovery after a crash;
2. the **memtable**, a skip list of the newest writes, with versions, deletes and snapshots;
3. **tables** on the disk, with data blocks, an index block, a filter block and checksums, and the **CRC-32C** checksum in one instruction;
4. **compaction**, which merges tables and drops old versions, and the three costs that it balances: write, read and space amplification;
5. **Bloom filters**, which let a read skip most tables, and a split-block filter that tests a key with one cache line and **one AVX2 register**;
6. **subcompactions**: one large compaction in parallel threads.

The tasks are in the folder `cpp/week31`. Keys are 64-bit numbers, and values are strings of any bytes. The given `lsm.hpp` puts all parts together into a key-value store. Its test case `store` passes when your tasks 1, 2, 3 and 5 work (tasks 4 and 6 make it faster), and `w31_bench store` measures it. Each benchmark first checks your result: a wrong result is not timed.

## Writes without seeks

How much faster is a sequential write? On our virtual machine, we wrote 8 KB pages at random places in a file, and we made each page durable with `fdatasync`. That gave about 4000 pages per second: 33 MB/s. Then we wrote 256 MB in one sequential stream, with one `fdatasync` at the end: 850 MB/s, 25 times more. An SSD prefers sequential writes too: it writes in large erase blocks, and small random writes make its internal garbage collection copy data again and again.

An LSM tree uses only sequential writes. A write goes through three places:

1. The write is appended to the end of a **log** on the disk, so that a crash does not lose it.
2. The write goes into the **memtable**: a sorted structure in memory.
3. When the memtable is full, it is written to the disk as one sorted file, a **table**, in one sequential write. This is a **flush**. A table never changes after it is written. Bigtable calls it an SSTable, a "sorted string table".

Tables pile up. A background job, **compaction**, merges small tables into larger ones and drops the versions that nobody can see any more. The tables are on **levels**: level 0 has the tables of the flushes, and each level below is larger than the level above it. Write some keys, and watch the levels:

{% include viz.html id="lsm-tree" alt="An LSM tree with a memtable of 4 versions and three levels on the disk, drawn as rows of tables, each table a box with its key range. Buttons write one random key, write 10 keys, delete a key, or look up a key. A write appends a record to the log and adds a version to the memtable; a full memtable becomes a new table of level 0; three tables on level 0 are merged into level 1, and when level 1 holds more than 12 versions, one of its tables is merged into level 2. A lookup marks the memtable and then each table that it searches, until it finds the key. Counters show the bytes written by the user and by the store, and their ratio." %}

The price is paid by the reads. A key can be in the memtable or in any table, so a read searches from the newest place to the oldest, and the first version that it finds is the answer. Much of this chapter is about keeping the reads fast while the writes stay cheap.

## The write-ahead log

The memtable is in memory, and a crash loses it. So each write first goes to the **write-ahead log** (WAL): a file that only grows at its end. After a crash, the store reads the log and builds the memtable again. When the memtable has been written to a table, its log is deleted.

Data that `write()` returns from is not on the disk yet. It is in the page cache of the operating system. Only `fsync(fd)` or `fdatasync(fd)` waits until the disk has it. On our machine, an append of 100 bytes followed by `fdatasync` took about 150 µs. So a log that syncs after every write can take at most about 6500 writes per second. Real stores use **group commit**: while one sync runs, new writes wait. The next sync makes all of them durable at once. In RocksDB, the first waiting thread becomes the leader of a "write group". It appends the records of all waiting threads, syncs once, and wakes them up. PostgreSQL and MySQL commit transactions in the same way. A store can also choose not to sync every write: RocksDB's default is `sync = false`. Then a crash of the process loses nothing, but a crash of the whole machine can lose the last writes.

A crash in the middle of a write can leave half a record at the end of the log, and the disk can put garbage there. So each record has a **checksum**. Our log (`wal.hpp`) is a string of records:

```
[crc: 4 bytes][length: 4 bytes][payload: length bytes]
```

`crc` is the CRC-32C checksum of the 4 bytes of the length and the payload (the section after the next one explains how it is computed). The payload of a record is a write batch: the puts and deletes of one write. Recovery reads records from the start. It stops at the first record that is incomplete, because the log ends inside its header or its payload, or whose checksum is wrong. It returns the records before it and the number of their bytes: the **valid prefix**. The store cuts the log to the valid prefix and appends new records after it. Bytes of zeros are not an empty record, because the checksum of 4 zero bytes is 0x48674BC7, not 0. Crash the log in the figure, and recover it:

{% include viz.html id="wal-recovery" alt="A log drawn as a row of records, each with a header and a payload, and a line that marks the bytes made durable by the last sync. Buttons append a record, sync, crash and recover. A crash keeps every synced byte and a random part of the rest, and can turn the last bytes into garbage. Recovery checks each record from the start: complete records with a correct checksum turn green, and it stops at the first record that is incomplete or has a wrong checksum, which turns red. The caption gives the number of records found and the valid prefix in bytes." %}

This is RocksDB's default "point-in-time recovery": everything up to the first damaged record, and nothing after it. LevelDB divides its log into blocks of 32 KB, and it splits a record that does not fit into fragments. After a damaged block, its reader can go on at the next block.

The length in a record is data from a disk, so treat it as input. Check that the bytes are there before you read them. Never allocate memory by a length that you have not checked: a garbage length of almost 4 GB must not make the program allocate 4 GB.

## The memtable

The memtable keeps the newest writes in key order, because a flush writes them out sorted, and because a read must find a key quickly. LevelDB and RocksDB use a **skip list** (Pugh, 1990). It is a sorted linked list with express lanes above it. Level 0 links all nodes in order. Each node gets a random **height** $$h$$, and it is on the levels $$0 \dots h-1$$. Level 1 links about one node in four, level 2 one in sixteen, and so on. A search starts on the top level of the head node. It goes right while the next node is smaller than the key, and down one level when it is not:

{% include viz.html id="skip-list" alt="A skip list of 12 keys drawn as towers of different heights, with the links of each level as arrows. A slider chooses a key. Step by step the search starts at the top of the head, moves right while the next key is smaller, and moves down a level when it is not; the visited nodes and the links followed are marked, and a counter counts the steps. A button inserts the key: it gets a random height by coin flips with probability 1/4, and the last node before it on each of its levels links to it." %}

Our rule for the height is LevelDB's: start with 1, and add one with probability 1/4, at most 12. There are no rotations and no rebalancing. With probability 1/4, a search makes about $$4 \log_4 n = 2 \log_2 n$$ steps on average.

The memtable never changes a version that it holds. Every write gets the next **sequence number** from a counter: 1, 2, 3, … A put of a key that is already there adds a new version, and a delete adds a version too, a **tombstone**. The versions are sorted by key, and the versions of one key by sequence number, newest first. We call this the **internal order**. A **snapshot** is a sequence number $$s$$: a read at snapshot $$s$$ sees the newest version with a sequence number $$\le s$$. For example, the key 7 has three versions:

{: .grid-head }
| Sequence number | Version |
| --- | --- |
| 5 | delete |
| 3 | put `"b"` |
| 1 | put `"a"` |

Then `get(7, 0)` finds nothing, `get(7, 2)` gives `"a"`, `get(7, 4)` gives `"b"`, and `get(7, 9)` finds the tombstone: the key is deleted. Each of these is one search in the skip list: for the first node that is not smaller than $$(7, s)$$ in the internal order.

Is the skip list fast? Not in our test. With a million random keys, an add took 2.1 µs and a get 2.8 µs. `std::map` took 1.2 µs and 1.4 µs. A skip list visits about twice as many nodes as a balanced tree, and each visit can be a cache miss. LevelDB and RocksDB use it for other reasons:

* Many threads can read a skip list while one thread inserts, without a lock. The insert links the new node from level 0 upwards, one pointer store at a time, so a reader sees the list with or without the new node, but never a broken list. RocksDB lets several threads insert at the same time with compare-and-swap. Part V of the course explains the atomic operations that this needs.
* Nodes never move and are never freed one by one. They come from an arena, and the whole memtable is freed at once after its flush.
* A flush is a walk along level 0.

Our memtable (`memtable.hpp`) keeps its nodes in one vector and their links in another, and a node refers to another node by its number, like the pages of week 26. It takes 51 bytes per version with the values of our test; a node of `std::map` alone takes about 100 bytes.

## Tables

A flush writes the memtable to the disk as a **table**, from start to end, and the table never changes after that. Our format (`table.hpp`) is a simple form of LevelDB's:

```
data block 0 | data block 1 | ... | filter block | index block | footer
```

* A **data block** has versions in the internal order, about 4 KB of them. A version is `[key: 8][tag: 8][value length][value]`. The tag holds the sequence number and the kind (put or delete), and the length is a **varint**: 7 bits per byte, and the top bit of a byte says that more bytes follow. So a length below 128 takes one byte. A **trailer** ends the block: the number of versions and a checksum.
* The **index block** has one entry per data block: the last version of the block (its key and sequence number), and where the block is.
* The **filter block** is a Bloom filter of the keys of the table. It comes later in this chapter.
* The **footer**, the last 56 bytes, says where the filter and the index are, and it ends with a magic number.

To read a table, a store reads its footer and its index once, when it opens the table, and keeps the index in memory. A lookup of $$(k, s)$$ is then:

1. A binary search on the index: the first block whose last version is not smaller than $$(k, s)$$. If no block is, the table has no answer.
2. Read that block, and check its checksum.
3. Scan the versions of the block to the first one that is not smaller than $$(k, s)$$. If its key is $$k$$, it is the answer. If not, the table has no version of $$k$$ that the snapshot can see.

So a lookup reads one block of the table. Look up a key and a snapshot in a small table:

{% include viz.html id="table-lookup" alt="A small table drawn as its bytes: six data blocks, the filter block, the index block and the footer. Sliders choose a key and a snapshot. Step by step the lookup reads the footer, does a binary search on the index entries (the last key and sequence number of each block), reads one data block, checks its checksum, and scans its versions to the first one that is not smaller than the key and snapshot. The caption gives the answer: a value, a delete, or nothing." %}

Why blocks, and not single versions? A disk reads whole pages anyway, and the index needs only one entry per block. Real tables also save space inside a block. LevelDB stores only the bytes in which a key differs from the key before it, and every 16th key in full: a **restart point**. A search in a block then does a binary search on the restart points. LevelDB compresses each block with Snappy, and RocksDB with LZ4 or Zstandard.

A table can come from a damaged disk, and the reader must not crash on it. The given `Table::open` checks every offset and size in the footer and the index against the size of the file before it uses them. Every check is written so that no sum can overflow. A block also has a checksum. But a checksum finds accidents: a flipped bit, a torn write, a block written to the wrong place. It does not find attacks, because anybody can compute the correct checksum of any bytes. So the reader must check every length inside a block too. Where attacks matter, systems use a cryptographic hash such as SHA-256 instead.

In a table of a million versions in memory (10,677 data blocks), a lookup took 1.05 µs.

## Checksums: CRC-32C in one instruction

A **CRC** (cyclic redundancy check) treats the bytes as a long polynomial whose coefficients are bits, and divides it by a fixed polynomial of degree 32. The remainder of the division is the checksum. In this arithmetic, adding is XOR, so the division needs only shifts and XORs. A good 32-bit CRC finds every error of up to 3 flipped bits in a block of 4 KB, every burst of errors up to 32 bits long, and any other error with probability $$1 - 2^{-32}$$. **CRC-32C** uses the polynomial of Castagnoli (1993), which finds more errors in blocks of this size than the CRC-32 of Ethernet and zip. iSCSI, ext4, Btrfs, LevelDB and RocksDB use it.

The textbook loop (Sarwate, 1988) handles one byte per step, with a table of 256 entries. This is our baseline:

```cpp
std::uint32_t c = ~crc;

for (const char ch : data)
    c = table[(c ^ static_cast<unsigned char>(ch)) & 0xFF] ^ (c >> 8);

return ~c;
```

Each step needs the `c` of the step before it: a load from the table, an XOR and a shift, one after another. That chain limits it to about 0.4 GB/s. Since SSE4.2 (Intel, 2008), x86 CPUs have an instruction for exactly this polynomial: `crc32`. `_mm_crc32_u64(c, v)` adds 8 bytes to the checksum in one instruction. ARM has a similar instruction, `crc32cx`.

{: .grid-head }
| CRC-32C of 256 KB in the L2 cache | GB/s |
| --- | --- |
| one byte per step with a table (Sarwate) | 0.40 |
| 8 bytes per step with 8 tables ("slicing-by-8") | 2.7 |
| one chain of `crc32` | 8.6 |
| three chains of `crc32`, combined with `pclmulqdq` | 25.9 |

One chain is still a chain. The `crc32` instruction has a latency of 3 cycles and a throughput of one per cycle (uops.info), so one chain uses a third of what the CPU can do. This is the lesson of latency and throughput from chapter 17. Fast libraries run three chains on three parts of the block, and combine the three checksums at the end. The checksum of A followed by B is the checksum of A "moved past" the length of B, XOR the checksum of B. Moving a checksum is a multiplication of polynomials, which `pclmulqdq` (carry-less multiplication) does in one instruction. RocksDB, the Linux kernel and Intel's ISA-L do this. In the benchmark of task 4, one chain is faster than in the table: there the blocks of 4 KB are independent, so the CPU starts the chain of the next block while the last steps of a block still run.

With one chain, each instruction starts when the one before it ends, so one instruction ends every 3 cycles; with three chains, three independent instructions run at the same time, one starting every cycle. A counter gives the bytes per cycle: 2.7 with one chain and 8 with three." %}

## Reading through the levels

Now the store has all its parts. How do the tables form levels? Level 0 holds the tables of the flushes as they are. Each of them can hold any keys, so the tables of level 0 overlap each other. Every level below level 0 is one **sorted run**: its tables are sorted by key, and their key ranges do not overlap. Each level may hold 10 times more bytes than the level above it: RocksDB's default ratio.

A read of the key $$k$$ at snapshot $$s$$ searches in this order:

1. the memtable;
2. every table of level 0 whose key range contains $$k$$, newest first;
3. on each level below, the one table whose key range contains $$k$$, if there is one: a binary search on the key ranges of the level.

The first version found is the answer. If it is a delete, the key has no value, and the read stops. This is correct because a version on a higher level is always newer than every version of the same key below it. A flush puts new tables on top, and compaction moves data down only together with all the data below it in the same key range.

The number of places that a read must look at is its **read amplification**. Our store wrote 2 million values to a million keys, and it ended with 1 table on level 0, then 4, 40 and 12 tables on levels 1, 2 and 3. A read searches the memtable and at most 4 tables.

## Compaction

A **compaction** reads some tables and writes their versions again: sorted, and without the versions that no reader can see. There are two main ways to choose which tables to compact:

* **Leveled** compaction (LevelDB, and RocksDB's default) keeps the levels below 0 as sorted runs. When level 0 has 4 tables, all of them are merged with the tables of level 1 that they overlap. When a level is larger than its limit, one of its tables, the next one after the last compaction of the level, is merged with the tables of the next level that overlap it.
* **Tiered** compaction (Cassandra's default, and RocksDB's "universal" compaction) has no limits per level. When there are several tables of about the same size, 4 in Cassandra, they are merged into one larger table.

Merging is the k-way merge of sorted runs: keep the next version of each input in a heap, and take the smallest version again and again. The rules of `compaction.hpp` decide what to keep. Our rules are those of LevelDB and RocksDB:

1. For each key, keep its newest version. Also keep, for each live snapshot $$s$$, the newest version with a sequence number $$\le s$$. Drop all other versions: no reader can see them.
2. At the **bottom**, when no older data of the keys lies below the output, drop the oldest kept versions of a key while they are deletes. A tombstone with nothing older to hide is not needed.
3. Cut the output into tables of about the target size, but only between two keys, so that all versions of a key are in one table.

For example, the key 7 has these versions, and the store has one live snapshot, 5:

{: .grid-head }
| Version | Kept? | Why |
| --- | --- | --- |
| 9: put `"c"` | yes | the newest version |
| 6: put `"b"` | no | no snapshot sees it: 6 and 7 and 8 are not snapshots |
| 4: delete | yes | the newest version that snapshot 5 sees |
| 2: put `"a"` | no | snapshot 5 sees the delete, not this |

At the bottom, the delete is the oldest kept version, so it goes too. A reader at snapshot 5 still finds no value for 7, and now the delete takes no space.

{% include viz.html id="compaction-merge" alt="Three sorted input tables with versions of the keys 2 to 9, each version a box with its sequence number and its value or delete. Toggles choose the live snapshots (none, or 5) and whether the output is the bottom level. Step by step the merge takes the smallest version of the three inputs in the internal order; at the end of each key, the versions that rule 1 keeps go to the output and the others fade out with the reason, and at the bottom the oldest deletes are dropped too. At the end, the caption compares the versions read and written." %}

Deletes are a known trap of LSM trees. A queue that adds and deletes many keys fills the levels with tombstones, and every read must skip them until a compaction reaches the bottom. Cassandra keeps tombstones for 10 days (`gc_grace_seconds`), so that a replica that was down for some time still learns about the delete. RocksDB has `DeleteRange`, which deletes a whole range of keys with one tombstone.

Our compaction of 8 overlapping tables with 2 million versions read 127 MB and wrote 87 MB in about 220 ms. It kept 1,376,858 of the versions.

## Write, read and space amplification

Compaction rewrites the same data again and again. Three numbers measure the costs of an LSM tree:

* **Write amplification**: the bytes written to the disk for each byte that the user wrote.
* **Read amplification**: the tables (or blocks) that a read looks at.
* **Space amplification**: the bytes on the disk for each byte of live data.

With leveled compaction, a byte moves down one level at a time, and each move merges it with about 10 times more data of the next level, so it is written again about 10 times per level. Write amplification is high, but every level is one sorted run: reads look at one table per level, and old versions disappear quickly, so space amplification stays near $$1 + 1/10$$. With tiered compaction, a byte is written once per tier, so write amplification is much lower. But many tables of each tier can hold the same key, so reads look at more tables, and a large merge needs room for its input and its output at the same time: up to twice the space. Compare the two in the figure:

{% include viz.html id="lsm-compaction" alt="Two simulated LSM trees get the same puts of random keys: one with leveled and one with tiered compaction. A toggle chooses which one is drawn, as rows of tables or runs, each as wide as its keys. Buttons write 100 or 1000 more keys, or reset. Three pairs of meters compare the two: the write amplification (keys written to the disk per key written by the user), the read amplification (runs that a read may search) and the space amplification (keys on the disk per live key). Leveled compaction has the higher write amplification, and tiered compaction the higher read and space amplification." %}

Our store with leveled compaction wrote 2 million values of 100 bytes to a million keys. For each byte from the user, it wrote 11.4 bytes to its simulated disk: 1 to the log, 1 in flushes, and 9.4 in compactions. Its space amplification was 1.22. Real stores measure 10–30 for leveled write amplification. You cannot have the best of all three costs at the same time: Athanassoulis and others call this the **RUM conjecture** (read, update, memory). RocksDB lets you choose with its options. Many systems start with leveled compaction for read-heavy data, and tiered for write-heavy logs and time series.

## Bloom filters

A read of a key that a table does not have still reads a block of that table. Most reads find their key only in the last level, or not at all, so they read a useless block on every level above. A **Bloom filter** (Bloom, 1970) answers the question "is this key in the table?" with "surely not" or "maybe", in a few bits per key.

A classic Bloom filter is an array of $$m$$ bits, all 0 at the start, and $$k$$ hash functions. To insert a key, set the $$k$$ bits that its hashes choose. To test a key, check its $$k$$ bits: if one of them is 0, the key was never inserted. If all are 1, the key is there, or its bits were set by other keys: a **false positive**. After $$n$$ inserts, a bit is still 0 with probability $$(1 - 1/m)^{kn} \approx e^{-kn/m}$$. A key that is not in the filter finds all its $$k$$ bits set with probability

$$p \approx \left(1 - e^{-kn/m}\right)^k.$$

The best number of hash functions is $$k = (m/n) \ln 2$$. Then half of the bits are 1, and $$p \approx 0.6185^{m/n}$$. With 10 bits per key, $$k = 7$$ and $$p = 0.82\%$$: we measured 0.821 %. Every 4.8 more bits per key divide $$p$$ by 10. Two hashes are enough to make the $$k$$ places: $$h_1 + i \cdot h_2$$ for $$i = 0, \dots, k - 1$$ (Kirsch and Mitzenmacher, 2006). Try other sizes:

{% include viz.html id="bloom-fpr" alt="A chart of the false positive rate, on a logarithmic scale, against the bits per key from 2 to 20, with three curves: the classic Bloom filter with the best number of hash functions, the classic filter with the chosen k, and the split-block filter of Parquet. Sliders set the bits per key and k; a marker shows the chosen point and the caption gives its rates, also as one false positive in how many lookups." %}

In our store, the filters cut the block reads per read from 1.37 to 0.44, and the time per read from 1.68 µs to 0.83 µs. Half of the keys that we read were never written, so without filters, these reads searched every level for nothing.

## Split-block Bloom filters

The classic filter puts the $$k$$ bits of a key anywhere in its $$m$$ bits. A filter for a large table does not fit in the cache, so a test costs up to $$k$$ cache misses. A **blocked** Bloom filter (Putze, Sanders and Singler, 2007) puts all bits of a key into one small block: one cache miss.

Apache Parquet's **split-block Bloom filter**, which Impala, Kudu and Arrow use too, has blocks of 256 bits: 8 words of 32 bits. For a 64-bit hash $$h$$ of a key:

* The block is $$\lfloor (h_{\text{high}} \cdot \text{blocks}) / 2^{32} \rfloor$$, where $$h_{\text{high}}$$ is the top 32 bits of $$h$$. This "multiply and shift" maps a 32-bit number to $$0 \dots \text{blocks} - 1$$ without a division.
* In the block, the low 32 bits $$x$$ of $$h$$ set **one bit in each of the 8 words**: in word $$i$$, the bit whose number is the top 5 bits of $$x \cdot \text{salt}_i$$ (modulo $$2^{32}$$), where the 8 salts are fixed odd numbers.

The price is a higher false positive rate: 1.27 % with 10 bits per key, against 0.82 % for the classic filter. Some blocks get more keys than others, and 8 bits in a block of 256 bits act like a small filter. About 12 bits per key give the 0.8 % of the classic filter (see the figure above). RocksDB's "FastLocalBloom" uses blocks of a whole cache line, and its Ribbon filter (2021) needs 30 % less space than a Bloom filter for the same rate, but more work per key.

The speed is the gain. We tested half inserted keys and half other keys, in nanoseconds per test:

{: .grid-head }
| Filter | 64 KB | 1.2 MB | 64 MB | 1 GB |
| --- | --- | --- | --- | --- |
| classic, 7 bits with `%` (the baseline) | 21.8 | 24.6 | 53.9 | 130.9 |
| classic, 7 bits with "multiply and shift" | 14.1 | 15.7 | 38.8 | 75.8 |
| split-block, a loop that stops at the first 0 bit | 12.0 | 12.1 | 36.5 | 57.5 |
| split-block, without branches | 4.9 | 6.3 | 24.7 | 61.0 |
| split-block, AVX2 | 3.0 | 2.8 | 15.1 | 23.1 |

Three things show in the table. First, `%` is a division, and 7 divisions cost about a third of the time of the classic filter. Second, one block instead of 7 bits all over the filter saves cache misses in the large filters. Third, the branch "is this bit 0?" goes either way for keys that are not in the filter, and the CPU guesses it wrong often. Code without that branch is much faster while the filter is in the cache.

## SIMD: eight bits in one instruction

The last row of the table is the fastest in every size. The 8 words of a block are 256 bits: one AVX2 register. The 8 bit numbers are 8 independent computations, one per word, so SIMD computes all of them at once:

```cpp
// The 8 bits of a hash, one in each lane.
__m256i mask8(std::uint64_t hash) {
    const __m256i salt = _mm256_setr_epi32(0x47b6137b, 0x44974d91, 0x8824ad5b, 0xa2b7289d,
                                           0x705495c7, 0x2df1424b, 0x9efc4947, 0x5c6bfb31);
    const __m256i x = _mm256_set1_epi32(static_cast<int>(static_cast<std::uint32_t>(hash)));
    const __m256i bit = _mm256_srli_epi32(_mm256_mullo_epi32(x, salt), 27);  // 8 numbers 0 ... 31
    return _mm256_sllv_epi32(_mm256_set1_epi32(1), bit);                     // 1 << bit in each lane
}
```

* `_mm256_set1_epi32` puts $$x$$ into all 8 lanes.
* `_mm256_mullo_epi32` multiplies the 8 lanes by the 8 salts and keeps the low 32 bits of each product. This is the multiplication modulo $$2^{32}$$ of the rules.
* `_mm256_srli_epi32(…, 27)` keeps the top 5 bits of each product: 8 bit numbers from 0 to 31.
* `_mm256_sllv_epi32` shifts the 1 of each lane left by **its own** amount. AVX2 added these variable shifts, and this is where they shine.

To insert, OR the mask into the block. To test, `_mm256_testc_si256(block, mask)` returns 1 if every bit of the mask is set in the block (it computes `~block & mask` and checks for zero). There is no loop and no branch:

{% include viz.html id="sbbf-lanes" alt="The 8 lanes of an AVX2 register for one key: the low 32 bits of the hash in all lanes, the 8 salts, the products modulo 2 to the 32 in hexadecimal, and the top 5 bits of each product. Below them, the 8 words of the block as 8 rows of 32 small cells: the mask sets one bit in each row (orange), and the bits of earlier keys are blue. A toggle chooses a key that was inserted or another key; for the other key, the lanes whose bit is missing in the block are red, and the test gives 0. Buttons step through the instructions." %}

In the L2 cache (the column of 1.2 MB), a test with AVX2 is 4.3 times faster than the loop, and in our benchmark an insert was 1.9 times faster. The surprise is the column of 1 GB: the filter is in the main memory, and each test waits for a cache miss, yet AVX2 is 2.5 times faster than the loop. The reason is the length of the code. Our compiled loop has 54 instructions, and the AVX2 version 20. The CPU runs ahead of a cache miss for up to a few hundred instructions (its reorder buffer). With short code, those instructions include the cache misses of several later tests, so several misses wait at the same time. This is the memory-level parallelism of chapter 25.

## Threads: subcompactions

The first compaction from level 0 to level 1 can be large: all tables of level 0 and the overlapping tables of level 1, gigabytes in RocksDB. While it runs, flushes go on, and level 0 fills up. If level 0 gets too many tables (20 by default), RocksDB slows down the writes, and at 36 tables it stops them: a **write stall**. So RocksDB splits one large compaction into **subcompactions** (`max_subcompactions`), and threads run them at the same time.

The parts must be key ranges, because rule 1 looks at all versions of a key together. Part $$i$$ gets the keys $$b_{i-1} \le k < b_i$$, for boundary keys $$b_1 < b_2 < \dots$$. Where do the boundaries come from? Equal ranges of keys can be very unequal in data. But the index blocks tell where the data is: every data block holds about 4 KB. Sort the last keys of all data blocks of all inputs, and take every $$(m/T)$$-th of these $$m$$ keys as a boundary, for $$T$$ parts. Each part then holds about the same number of bytes. A thread seeks every input to the start of its part (`TableIterator::seek`), merges up to the end of the part, and writes its own tables. The last table of each part can be small. No thread writes anything that another thread reads.

{% include viz.html id="subcompactions" alt="The data of a compaction drawn as a bar along the key range, darker where the keys are dense, with the boundaries of 4 parts, and a timeline of 4 threads below. A toggle chooses boundaries that split the key range into equal parts, or boundaries from the last keys of the index blocks; a second toggle chooses even or skewed keys. Step by step each thread merges its part; with equal key ranges and skewed keys, one part has most of the data, and three threads wait. The caption gives the time and the speedup." %}

The compaction of 8 tables with 2 million versions took about 240 ms on one thread and 62 ms on four: 3.8 times faster. A compaction is mostly work for the CPU: decoding, checksums, the merge, encoding. The parts share nothing, so it scales almost perfectly.

## Time and space

For a store with $$N$$ bytes of data, a memtable of $$M$$ bytes, $$n$$ versions in the memtable, and a size ratio $$r$$ between the levels ($$r = 10$$ here). Then there are about $$L = \log_r(N/M)$$ levels.

### Time

{: .fit }
| Operation | Time |
| --- | --- |
| append a record of $$b$$ bytes | $$O(b)$$, and one sync per group of writes |
| recovery of a log of $$b$$ bytes | $$O(b)$$ |
| memtable: add, get | $$O(\log n)$$ expected |
| lookup in a table of $$t$$ blocks | $$O(\log t)$$ for the index, and one block |
| CRC-32C of $$b$$ bytes | $$O(b)$$: $$b/8$$ instructions |
| a read of the store | memtable, tables of level 0, and one table per level: $$O(L)$$ table lookups |
| compaction of $$v$$ versions from $$k$$ tables | $$O(v \log k)$$ |
| write amplification, leveled | about $$r$$ per level: $$O(r L)$$ |
| write amplification, tiered | about 1 per level: $$O(L)$$ |
| filter: insert, test | classic $$O(k)$$; split-block $$O(1)$$, one block |

A search in a skip list with probability $$1/4$$ visits about $$4 \log_4 n$$ nodes on average, and the worst case is $$O(n)$$, but it is extremely unlikely. A lookup in a table reads one block, and the block has a constant number of versions. The checksum needs $$b/8$$ `crc32` instructions. One chain takes $$3b/8$$ cycles, and three chains about $$b/8$$. A merge takes the smallest of $$k$$ inputs from a heap for each version. Filters turn most of the $$O(L)$$ table lookups of a read into a test of a few bits in memory: with a rate $$p$$, a read of a key that is in the last level reads about $$1 + pL$$ blocks.

### Space

{: .fit }
| Data | Space |
| --- | --- |
| log | the records of the versions in the memtable |
| memtable | about 36 bytes per version, and its value |
| table | the versions, an index entry of 28 bytes per block, and the filter |
| filter | 10 bits per key, 1.25 bytes |
| all tables, leveled | about $$(1 + 1/r) N$$ in the best case |
| all tables, tiered | up to $$2N$$ during a large merge |

With leveled compaction, about 90 % of the data is on the last level, and the levels above can hold old versions of the same keys, so the space is about $$N (1 + 1/(r - 1))$$. Our store measured 1.22 $$N$$, because its last level was not full.

## Bonus: Merkle trees between replicas

Cassandra and Dynamo keep each key on several machines (the consistent hashing of week 28). The copies drift apart: a machine was down for an hour, or a write reached only two of three replicas. **Anti-entropy** repair finds the differences between two replicas without sending all their data. It uses a **Merkle tree** (Merkle, 1987): a hash tree over the key range. A leaf is the hash of all versions in a small range of keys, and an inner node is the hash of its two children. Two replicas compare their roots. If they are equal, the replicas hold the same data. If not, they compare the two children, and they go down only into the subtrees whose hashes differ:

```cpp
// A Merkle tree over the key space: 2^depth leaves, one per range of keys.
// node[1] is the root, and the children of node[i] are node[2i] and node[2i + 1].
struct Merkle {
    int depth;
    std::vector<std::uint64_t> node;
};

Merkle build(std::span<const Entry> sorted, int depth) {
    const std::size_t leaves = std::size_t{1} << depth;
    Merkle m{depth, std::vector<std::uint64_t>(2 * leaves, 0)};

    for (const Entry& e : sorted) {  // the leaf of a key: its top `depth` bits
        std::uint64_t& h = m.node[leaves + (e.key >> (64 - depth))];
        h = hash_key(h ^ hash_key(e.key ^ e.seq) ^ std::hash<std::string>{}(e.value));
    }

    for (std::size_t i = leaves - 1; i >= 1; --i)  // the levels above, from the bottom
        m.node[i] = hash_key(m.node[2 * i] * 31 ^ m.node[2 * i + 1]);

    return m;
}

// Appends the leaves where a and b differ.
void diff(const Merkle& a, const Merkle& b, std::size_t i, std::vector<std::size_t>& out) {
    if (a.node[i] == b.node[i])
        return;  // the same hash: the same data below, unless two hashes collide

    const std::size_t leaves = std::size_t{1} << a.depth;
    if (i >= leaves) {
        out.push_back(i - leaves);
        return;
    }

    diff(a, b, 2 * i, out);
    diff(a, b, 2 * i + 1, out);
}
```

The order of the versions in a leaf matters for its hash, and both replicas list them in the internal order. If $$d$$ leaves differ, `diff` compares $$O(d \cdot \text{depth})$$ hashes instead of all the data. Then the replicas send each other only the versions of those key ranges, and the newer versions win. Cassandra's `nodetool repair` builds such trees for each range of tokens, traditionally with $$2^{15}$$ leaves. Git, Bitcoin and the Certificate Transparency logs of the web use Merkle trees too. Between machines that might lie, the hash must be cryptographic (such as SHA-256): with our fast 64-bit hash, an attacker could make two different leaves with the same hash.
