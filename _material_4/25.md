# 25. The Memory Hierarchy and Layouts

Every app that remembers something has a **storage engine** inside: the part of a database that keeps the data in memory and on disk, and finds them again. When you open a chat, a storage engine finds the last 50 messages among billions in less than a millisecond. SQLite runs inside every phone and every web browser. PostgreSQL and MySQL run behind most web sites, and RocksDB, made at Facebook, runs inside many other systems.

This part of the course builds the data structures of storage engines, one per week:

{: .grid-head }
| Week | Topic | What it is for |
| --- | --- | --- |
| 25 | The memory hierarchy and layouts | how long a load waits, and how to wait less |
| 26 | B+ trees | the index of almost every database |
| 27 | Pages, the buffer pool and caching | which pages to keep in memory |
| 28 | Hash tables | finding a key with one or two cache misses |
| 29 | Tries and radix trees | keys as strings of bits: IP routing and in-memory indexes |
| 30 | Spatial indexes | points and rectangles on a map |
| 31 | LSM trees | fast writes: the design of RocksDB and Cassandra |
| 32 | Concurrency control and MVCC | many users who read and write at the same time |

A storage engine is fast when it moves few bytes, and when it waits for them in a clever way. So this week is about memory. A load takes 2 nanoseconds when the value is in the nearest cache, and 250 nanoseconds when it is in main memory: more than 100 times longer. We measure the levels in between. Then we put the keys of a sorted array in new orders, so that a search waits less. At the end of the week, a search in 512 MB of keys is 5 times faster than `std::lower_bound`.

### Sanitizers

A C++ program with a memory error does not always crash. It may read a wrong value and go on, and fail much later, somewhere else. **AddressSanitizer** adds a check to every memory access, and stops the program at the first bad one, with the line of the code. **UndefinedBehaviorSanitizer** catches other mistakes, such as a signed overflow or a shift by too many bits. Both are on in the `debug` preset. When a test fails there, start from the first error report. **ThreadSanitizer** (`tsan`) finds data races in the same way.

### perf

`perf stat` counts events of the CPU while a program runs. This week the interesting ones are cache misses and TLB misses (see below):

```console
$ perf stat -e cycles,instructions,cache-misses,dTLB-load-misses ./build/release/week25/w25_bench task4
```

`perf record` and `perf report` show which functions take the time, and `perf annotate` shows it line by line. perf needs access to the hardware counters, which some virtual machines do not give.

### SIMD and threads

SIMD instructions work on several values at once: AVX2 on 256-bit registers (8 `int`s), AVX-512 on 512-bit registers (16 `int`s), with extra **mask registers**. We use them through **intrinsics**: functions such as `_mm256_cmpgt_epi32` that the compiler turns into one instruction each. Intel's [Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html) lists them all. The code is compiled for AVX2. A function with AVX-512 code is marked `[[gnu::target("avx512f")]]`. If your CPU has no AVX-512, test such functions with Intel SDE, which emulates it, and measure on the course machine.

For threads we use OpenMP: `#pragma omp parallel for` before a loop divides the loop between the threads. Two threads must never write the same place without synchronization: that is a **data race**, and ThreadSanitizer finds it. The goals of the parallel tasks are for 4 threads on 4 cores.

## The memory hierarchy

A CPU core can do several additions in every clock cycle, which is about a third of a nanosecond. Main memory is far away: a value from memory arrives hundreds of cycles later. To hide this, the CPU keeps copies of recently used memory in **caches**, small fast memories near the core. Our test machine has three levels:

{: .grid-head }
| Level | Size | Shared by |
| --- | --- | --- |
| L1 data cache | 48 KB | one core |
| L2 cache | 2 MB | one core |
| L3 cache | 260 MB | all cores of the processor |
| Main memory | gigabytes, terabytes in big servers | all cores |

Caches do not store single bytes. They store **cache lines** of 64 bytes: when you read one `int`, the 15 `int`s next to it come into the cache too, and reading them is then almost free. (Chapter 17 showed how this makes a struct of arrays faster than an array of structs.)

How long does a load take? We can measure it with an array `next` that forms one random cycle: `next[i]` is the place to read after place `i`. Every load needs the result of the one before, so the loads cannot overlap, and the time per step is the **latency** of one load:

```cpp
std::uint32_t at{};

for (std::size_t step = 0; step < steps; ++step)
    at = next[at];  // the address of this load is the result of the last one
```

A small array stays in the L1 cache; in a large one, almost every load goes to memory. The figure shows the time per load for arrays from 16 KB to 1 GB:

{% include viz.html id="mem-latency" alt="A chart of the time per load against the size of the data, from 16 KB to 1 GB, both on log scales, with bands for the L1 cache, the L2 cache, and the L3 cache and memory. The time grows from 1.8 ns to 246 ns. A slider picks a size and the caption explains it; a toggle adds the curve for 2 MB pages, which is lower from 16 MB on." %}

From 1.8 ns in the L1 cache, the time grows to 5 ns in the L2 cache and 28 ns at 4 MB. Beyond that, most loads go to main memory: 125 ns at 16 MB and 246 ns at 1 GB. The core runs at about 3 GHz, so a load from memory waits about 700 cycles, and in that time the core could have run thousands of instructions.

Two notes on these numbers. Our L3 cache is 260 MB on paper, but it is shared with the other cores of a large server processor, and in this test it was fast only up to a few MB. And chapter 17 gave 80–100 ns for main memory: that is typical for a desktop computer when the TLB of the next section knows the address. A large server is slower, and random loads in a large array miss the TLB too.

The numbers are different on every machine, but the shape is always the same: every level is several times larger and several times slower than the one before. A program is fast when most of its loads are served by the small levels.

## Pages and the TLB

The addresses that a program uses are **virtual**. The operating system divides memory into **pages** of 4 KB, and keeps a **page table** that says where each virtual page is in the physical memory. Every load must translate its address. Reading the page table every time would cost more loads (the table has four levels), so the core keeps recent translations in a small cache, the **TLB** (translation lookaside buffer). Its first level has about 100 entries and its second level about 2000. With 4 KB pages, that covers 8 MB. A random load in a larger array usually misses the TLB too, and then the core must walk the page table before it can even start the load. In a virtual machine, such as our test machine, a TLB miss costs even more: the address goes through two page tables, the one of the virtual machine and the one of the real machine.

Linux can also use **huge pages** of 2 MB. One TLB entry then covers 512 times more memory, and the page table has one level less. With **transparent huge pages**, Linux does this by itself for large memory areas. Many systems, ours too, have the setting `madvise`: a program must ask for huge pages.

```cpp
void* p = std::aligned_alloc(2 << 20, bytes);  // bytes must be a multiple of 2 MB
madvise(p, bytes, MADV_HUGEPAGE);  // Linux: please use 2 MB pages here
```

The setting is in the file `/sys/kernel/mm/transparent_hugepage/enabled`. This week's class `Keys` (in `layout.hpp`) asks for huge pages when you give it `huge_pages = true`. The toggle in the figure above shows the effect: for 1 GB, 180 ns per load instead of 246 ns.

Huge pages are not free. A 2 MB page must be 2 MB of free physical memory in one piece, so the system may have to move other pages to make one, and memory is given in larger steps. Some databases avoid transparent huge pages: Redis turns them off for its own process, because they made its latency less predictable and its memory use larger. Others, such as PostgreSQL, can put their main memory area on huge pages.

## Many loads at once

Reading an array **in order** is much faster than reading it at random. We summed arrays of 32-bit numbers:

{: .grid-head }
| Array | 1 thread | 2 threads | 4 threads |
| --- | --- | --- | --- |
| 1 MB (in the L2 cache) | 27.4 GB/s | 53.9 GB/s | 91.3 GB/s |
| 16 MB | 19.4 GB/s | 39.8 GB/s | 67.1 GB/s |
| 256 MB | 7.6 GB/s | 13.4 GB/s | 23.8 GB/s |
| 1 GB | 8.0 GB/s | 14.1 GB/s | 25.6 GB/s |

One thread reads 1 GB at 8 GB/s, that is, one 64-byte line every 8 ns. But a single load from memory takes 246 ns! Both are true, because one core can wait for many cache lines at the same time. When the loads are independent, the core does not wait for the first one before it starts the next. And the **hardware prefetcher** notices that the program reads in order, and asks for the next lines before the program does. **Little's law** connects the numbers: the amount of data on its way is the bandwidth times the latency,

$$8\ \text{GB/s} \times 246\ \text{ns} \approx 2000\ \text{bytes} \approx 30\ \text{cache lines}.$$

So one core keeps about 30 lines on their way. More threads keep more lines on their way: 4 threads read memory at 25.6 GB/s, 3.2 times faster than one. A loop that reads memory gets faster with threads until it reaches the bandwidth of the memory, a few hundred GB/s in a big server.

This is the main idea of the week: **latency is the enemy, and overlap is the cure.** A chain of loads where every address comes from the value before (a linked list, a tree, a binary search) is slow, because it waits for each load. The rest of the chapter makes searches that wait for fewer loads, and for several at a time.

## Counting cache misses

When the data do not fit in the cache, counting instructions does not predict the time. Counting **block transfers** does. The **I/O model** of Aggarwal and Vitter (1988) has a fast memory of size $$M$$, a slow memory of any size, and data that move between them in blocks of $$B$$ items. The cost of an algorithm is the number of blocks it moves. For a database, the slow memory is the disk and a block is a page of 4–16 KB. For us, the slow memory is the main memory and a block is a cache line: $$B = 16$$ keys of 4 bytes.

In this model, a binary search over $$n$$ sorted keys costs about $$\log_2 (n/B)$$ transfers: every step jumps far from the one before, except the last $$\log_2 B$$ steps, which stay inside one line. A search tree with $$B$$ keys in every node, so that a node is one block, costs only $$\log_{B+1} n$$ transfers. For $$n = 2^{27}$$ keys and $$B = 16$$:

$$\log_2 \frac{2^{27}}{16} = 23 \qquad\text{and}\qquad \log_{17} 2^{27} \approx 6.6.$$

That is the idea of the **B-tree**: a transfer brings a whole block, so let every block decide as much as it can. Database pages are much larger than cache lines, and the nodes of a database B-tree have hundreds of keys: with 500 keys per node, three levels hold more than 100 million keys. Next week we build such a tree.

### The cache-oblivious idea

The best block size depends on the level: 64 bytes for the caches, 4 KB for the pages and the TLB, perhaps 16 KB for the disk. A **cache-oblivious** layout is good for every block size at once, without knowing any of them (Frigo, Leiserson, Prokop and Ramachandran, 1999). The classic example is the **van Emde Boas layout** of a binary search tree. Cut the tree at half of its height, into a top tree and many bottom trees of about $$\sqrt n$$ keys each. Store the top tree first and then the bottom trees one after another, each of them laid out in the same way, recursively. At some depth of the recursion the small trees have about $$B$$ keys, and so a search reads $$O(\log_B n)$$ blocks, whatever $$B$$ is.

The idea is beautiful, but in practice it loses. Khuong and Morin (2017) measured all these layouts: the explicit layouts of the next sections, made for 64-byte lines, are faster on today's machines, and the van Emde Boas layout is harder to compute. We do not use it in the tasks.

## Binary search and branches

`std::lower_bound` finds the first key that is not less than $$x$$. Inside, every step is an `if`: go left or right. For a random $$x$$ the CPU cannot predict that branch. It guesses wrong half of the time, and each wrong guess costs about 15–20 cycles (chapter 17). A **branchless** binary search computes the step as a number instead, and the compiler turns the multiplication by a `bool` into a conditional move (`cmov`). This is the baseline of this week (`baseline.cpp`):

```cpp
Key branchless_lower_bound(std::span<const Key> sorted, Key x) {
    if (sorted.empty())
        return none;

    const Key* base = sorted.data();
    std::size_t len = sorted.size();

    while (len > 1) {
        const std::size_t half = len / 2;
        base += (base[half - 1] < x) * half;  // a conditional move, not a branch
        len -= half;
    }

    return *base < x ? none : *base;
}
```

The branchless search is much faster for small arrays: 12.2 ns instead of 68.6 ns for $$2^{10}$$ keys. But for 512 MB of keys it is *slower*: 947 ns against 903 ns. Why? When the CPU guesses a branch, it goes on **speculatively**: it starts the load of the next step before it knows whether the guess was right. Half of the guesses are right, so the branchy search often has its next load on the way early, and a wrong guess costs little compared with a load from memory. The branchless search must wait for every load before it even knows the next address. For data in memory, overlapping loads matters more than avoiding wrong guesses. This explanation is from Khuong and Morin, and the rest of the chapter follows their paper.

## The Eytzinger layout

In 1590, Michael Eytzinger numbered the ancestors of a person like this: the person is 1, and the father of person $$k$$ is $$2k$$ and the mother $$2k + 1$$. You know this numbering from binary heaps. We use it for the implicit search tree of a sorted array. Its root, the middle key, goes to place 1, and the children of the key at place $$k$$ go to places $$2k$$ and $$2k + 1$$. So the keys are stored in **breadth-first order**: the root, then the two keys of the second level, then the four keys of the third level, and so on.

The figure shows 15 keys in both layouts, with cache lines of 4 keys (a toy machine: real lines hold 16). Move $$x$$ and follow a search:

{% include viz.html id="search-layouts" alt="A binary search tree of 15 keys above a row of 16 memory places, in cache lines of 4. A toggle switches between the sorted layout and the Eytzinger layout, and a slider sets x. Step by step the search walks down the tree, and the cache lines that it has read are marked. Dashed boxes mark the lines that hold the first two levels of the tree, which every search reads: three lines in the sorted layout, one line in the Eytzinger layout, where place 0 is unused. A side panel shows these counts, the answer so far and k in bits." %}

The search is the same tree walk in both layouts, but it reads different lines. All searches start with the same few keys: the middle key, then the key at a quarter or at three quarters, and so on. In the sorted array each of these keys is in its own cache line, with 15 neighbours that the search does not need. In the Eytzinger layout they are packed together: the first 4 levels (15 keys) fill one line, and the first 20 levels (a million keys) fill 4 MB instead of 64 MB. So the caches hold 4 more levels of the tree, and every search finds more of its first steps there. (In the small figure, one search can even read more lines in the Eytzinger layout. What counts is that the top levels need few lines, and all searches share them.)

The search is short, and it has no branch that depends on the keys:

```cpp
std::size_t k = 1;

while (k <= n)
    k = 2 * k + (e[k] < x);  // left: append a 0 bit to k, right: append a 1
```

The bits of $$k$$ are the path. After the leading 1, every step adds a 0 (left) or a 1 (right). When $$k$$ falls off the bottom of the tree, the answer is the key where the search went left for the last time: that is the smallest key $$\ge x$$ on the path. For example, $$k = 10111$$ in binary means: left, then right three times. The last left step was made at node $$1$$, the bits before that 0. In general: remove the trailing ones and then one zero. `std::countr_one` in `<bit>` counts the trailing ones. If the search never went left, no key is $$\ge x$$, and the bits that remain are 0: put `none` at place 0, and the answer is right with no extra test.

For arrays that fit in the caches the Eytzinger search is fast: 33 ns for $$2^{16}$$ keys (256 KB), where `std::lower_bound` took 138 ns and the branchless search 52 ns. But for 512 MB it took 842 ns, hardly better than `std::lower_bound` (903 ns). The packed top levels help, but every level near the bottom is still one load from memory, and the search waits for each of them. Unless we ask for them early.

## Prefetching

The Eytzinger layout has one more gift. The descendants of node $$k$$ four levels down are the 16 nodes $$16k, 16k + 1, \dots, 16k + 15$$, next to each other in memory. If the array starts at a cache line, with place 0 first, these 16 keys are exactly one cache line. So at node $$k$$ the search can ask for the line where it will be four steps later. It does not yet know which of the 16 keys it will need, but it knows that they are all in that one line.

`__builtin_prefetch(address)` (GCC and Clang) asks the CPU to start loading the cache line of `address`, and goes on without waiting. It is only a hint: it never causes an error, even for an address outside the array. Here it is in a loop that sums values from random places, with each place prefetched 8 rounds before it is needed:

```cpp
for (std::size_t j = 0; j < idx.size(); ++j) {
    if (j + 8 < idx.size())
        __builtin_prefetch(&data[idx[j + 8]]);

    sum += data[idx[j]];
}
```

In the Eytzinger search, the prefetch at node $$k$$ asks for the line of node $$16k$$:

{% include viz.html id="prefetch-lines" alt="An Eytzinger array of 64 places in four cache lines of 16, with the levels of the tree marked above it. A slider sets x. Step by step a search walks down the array; at each of its first nodes it asks for the cache line four levels below, drawn as an arrow, and when the search arrives there, the line is already loaded." %}

With prefetching, up to four loads of one search are on their way at the same time. The price is bandwidth: the search loads 16 keys to use one of them. But one search uses only a few GB/s, far less than the memory can give. For $$2^{27}$$ keys the search took 299 ns instead of 842 ns: 2.8 times faster. For small arrays it is slower (26 ns instead of 16 ns for $$2^{13}$$ keys): the data are in the cache anyway, and the prefetches are extra work.

Near the bottom of the tree, $$16k$$ is past the end of the array. The prefetch does not mind, but C++ does: making a pointer past the end of an array is undefined behaviour, even if it is never read. Compute such addresses as integers (`std::uintptr_t`), and turn them into a pointer only for the prefetch.

## A static B+ tree

From the fifth level down, the Eytzinger search uses one key of every line that it loads. A **B-tree** uses the whole line: a node of 16 keys (64 bytes, one line) has 17 children. Each line then narrows the search to $$1/17$$ instead of $$1/2$$, and a search of $$2^{27}$$ keys reads 7 lines instead of 23.

A database B-tree changes with every insert (next week). Ours is **static**: built once from sorted keys, and never changed. Then it needs no pointers. Like in the Eytzinger layout, the places of the children follow from arithmetic. The tree of this week (`layout.hpp`) is a **B+ tree**: all keys are in the leaves, and the nodes above them hold copies of keys that guide the search.

* Level 0 has the **leaves**: the sorted keys in nodes of 16, and then at least one `none` as padding. `none` is `INT32_MAX`, larger than every key.
* Above them, node $$t$$ of level $$j$$ has the children $$17t, 17t + 1, \dots, 17t + 16$$ of level $$j - 1$$, as far as they exist. Its key $$i$$ is the **largest key under child $$17t + i$$**, or `none` if that child does not exist.
* The top level has one node, the root. All levels are stored in one array, from the root down.

To search for $$x$$, count the keys of the node that are less than $$x$$. If the count is $$c$$, all keys under the children before child $$c$$ are less than $$x$$, and the largest key under child $$c$$ is not, so the answer is under child $$c$$. In the leaf, the count is the place of the answer.

{% include viz.html id="static-btree" alt="A static B+ tree with nodes of 4 keys and 5 children over 30 keys in 8 leaves, padded with infinity. A slider sets x. Step by step the search compares x with all keys of a node at once; the rows below the tree show the keys, the results of the compare, and their count, which is the child to follow, and in the leaf the place of the answer." %}

For $$2^{27}$$ keys the tree has 7 levels: 8,388,609 leaves, and 524,291 nodes above them. The upper levels take only 6 % more memory than the keys, and the top four of them (116 KB) stay in the cache. Sergey Slotin, who studied this layout in detail, calls it an **S+ tree**.

## SIMD: a node in one compare

Counting the keys that are less than $$x$$ is a perfect job for SIMD. AVX2 compares 8 `int`s in one instruction. `_mm256_cmpgt_epi32(a, b)` sets all 32 bits of a lane to 1 where $$a > b$$, and to 0 elsewhere. `_mm256_movemask_ps` collects the top bit of every lane into an ordinary integer of 8 bits, and `std::popcount` counts its ones. For the first 8 keys of a node:

```cpp
const __m256i xs = _mm256_set1_epi32(x);  // x in all 8 lanes
const __m256i keys = _mm256_load_si256(reinterpret_cast<const __m256i*>(node));
const __m256i less = _mm256_cmpgt_epi32(xs, keys);  // all ones where key < x
const auto bits = static_cast<unsigned>(_mm256_movemask_ps(_mm256_castsi256_ps(less)));
const int count = std::popcount(bits);  // the number of keys < x among the 8
```

`_mm256_castsi256_ps` only changes the type, from integers to floats, because the movemask instruction that we need is defined for floats; it costs nothing. The load can be aligned (`load`, not `loadu`), because every node starts at a cache line. Our keys are signed `int32_t`, and `cmpgt` compares signed numbers, so the result is right. Next week's keys are unsigned, and we will need a trick.

Two such compares do a whole node, and there is no branch on the keys at all: the CPU never guesses wrong, and every level costs one load and a few instructions. With AVX-512, `_mm512_cmplt_epi32_mask(keys, xs)` compares all 16 keys at once and returns the result directly as 16 bits in a mask register (a `__mmask16`): one compare per node.

When the keys fit in the caches, the time is instructions and wrong guesses. ## Threads: waiting together

A search in the B+ tree of 512 MB spends most of its time waiting for memory. While one core waits, the other cores can wait too, for their own searches. The searches are independent and only read the tree, so they run in parallel without any care: a `#pragma omp parallel for` over the queries, where every thread writes the results of its own queries. In the benchmark of task 7, the searches took 200 ns each on one thread, 87 ns on two and 56 ns on four: 3.6 times faster on 4 cores.

That is better than the speedup of reading memory in order (3.2 times, above). Reading in order is limited by the bandwidth of the memory, but the searches use little bandwidth. Each new thread adds its own waiting loads, and the memory has room for them. The figure compares four kinds of work on 1, 2 and 4 threads:

{% include viz.html id="thread-scaling" alt="A bar chart of the speedup over one thread, with 1, 2 and 4 threads, for four kinds of work: reading 1 MB from the L2 cache (3.3 times faster with 4 threads), reading 1 GB from memory (3.2), searches in the static B+ tree of 512 MB (3.6), and building that tree (2.9)." %}

Even one thread can wait for several searches at once: run 8 searches through the tree together, one level at a time, so that their loads overlap. Databases use this **interleaving** in joins and hash tables, under the names *group prefetching* (Chen, Ailamaki, Gibbons and Mowry, 2004) and *AMAC* (Kocberber, Falsafi and Grot, 2015). The tasks do not need it, but try it if you want to go further.

## First touch and NUMA

`new` and `malloc` of a large block do not give physical memory. They give *virtual* addresses, and the operating system finds a physical page only when the program first writes to it. The first write causes a **page fault**: the kernel takes a free page, fills it with zeros, maps it, and then lets the write go on. This happens in the thread that touches the page first, and it takes time: on our machine, creating a zero-filled `std::vector` of 544 MB took 294 ms, about 2 µs for every 4 KB page.

A large server has two or more processors (**sockets**), each with its own memory. Every core can read all of the memory, but the memory of the other socket is slower to reach: its loads go through the link between the sockets, which they all share. This is called **NUMA**, non-uniform memory access. Linux places a page in the memory of the socket whose core touches it first. This is the **first-touch** rule:

{% include viz.html id="first-touch" alt="Two sockets, each with two threads and its own memory, and an array of 16 pages. A toggle chooses whether one thread or all four threads write the array first. Each page appears in the memory of the socket whose thread touched it first. Then the threads read their halves of the array: with one writer, the threads of socket 1 read every page from the other socket." %}

The classic mistake is to create an array in one thread and then work on it with many. `std::vector<int> v(n)` writes zeros to all of it in the thread that creates it. So every page lands in the memory of one socket, and all the page faults are paid by one thread. The cure is to allocate without writing, and let every thread write its own part first, with the same `schedule(static)` that later reads it. In C++, `std::make_unique_for_overwrite<int[]>(n)` (C++20) allocates an array without writing to it. The class `Keys` does the same, with an alignment.

Building the static B+ tree of 512 MB this way took 417 ms with one thread, 215 ms with two and 145 ms with four: 2.9 times faster. Our test machine has one socket, so it shows only half of the story: there, the gain is the page faults in parallel. On a machine with two sockets, the placement of the pages matters as well. `numactl --hardware` shows the memory nodes of a machine, and `numactl --interleave=all ./program` spreads the pages of a program over all of them, a quick fix for programs that you cannot change.

## Code to read

* Paul-Virak Khuong and Pat Morin: _Array Layouts for Comparison-Based Searching_ (ACM Journal of Experimental Algorithmics, 2017). The sorted, Eytzinger, B-tree and van Emde Boas layouts measured side by side, with the explanation of why branchy binary search wins for large arrays. This chapter follows it.
* Sergey Slotin: _Algorithms for Modern Hardware_ (en.algorithmica.org/hpc), the chapters on binary search and static B-trees. They go further than this chapter, with AVX2 code and many measurements.
* Changkyu Kim and others: _FAST: Fast Architecture Sensitive Tree Search on Modern CPUs and GPUs_ (SIGMOD 2010). A static tree in blocks within blocks: for SIMD registers, for cache lines and for pages.
* bcache, a block cache in the Linux kernel (`drivers/md/bcache/bset.c`), and its successor, the bcachefs file system (`eytzinger.h`). Both search the keys inside their B-tree nodes with a binary tree stored in an array in Eytzinger order.
* Ulrich Drepper: _What Every Programmer Should Know About Memory_ (2007). Long, and in places old, but still the best explanation of caches, TLBs and NUMA.
* Matteo Frigo, Charles Leiserson, Harald Prokop and Sridhar Ramachandran: _Cache-Oblivious Algorithms_ (FOCS 1999).
* The Linux documentation of transparent huge pages (`Documentation/admin-guide/mm/transhuge.rst`), and the `numactl` tool.
