# 25. The Memory Hierarchy and Layouts

Every app that remembers something has a **storage engine** inside. The storage engine is the part of a database that keeps the data in memory and on disk, and finds them again. When you open a chat, a storage engine finds the last 50 messages among billions in less than a millisecond. SQLite runs inside every phone and every web browser. PostgreSQL and MySQL run behind most web sites. RocksDB, made at Facebook, runs inside many other systems.

This part of the course builds the data structures of storage engines, one per week:

| 26 | B+ trees | the index of almost every database |

| 32 | Concurrency control and MVCC | many users who read and write at the same time |

A storage engine is fast when it moves few bytes, and when it waits for them in a clever way. So this week is about memory. A load takes 2 nanoseconds when the value is in the nearest cache. It takes 250 nanoseconds when the value is in main memory: more than 100 times longer. First we measure the levels between these two. Then we put the keys of a sorted array in new orders, so that a search waits less. At the end of the week, a search in 512 MB of keys is 5 times faster than `std::lower_bound`.

The tasks are in the folder `cpp/week25`. You build, test and measure them as in Part III. Each task comes right after the section that it needs. The keys are sorted 32-bit `int`s made by `sorted_keys`: every key is 1 to 15 larger than the key before it. Every search returns the **lower bound** of $$x$$: the smallest key $$\ge x$$, or `none` if there is no such key. The benchmarks search $$2^{27}$$ keys (512 MB) with $$2^{19}$$ random queries. A benchmark first checks your result: a wrong result is not timed.

## The memory hierarchy

A CPU core can do several additions in each clock cycle, and a clock cycle is about a third of a nanosecond. Main memory is far away: a value from memory arrives hundreds of cycles later. To hide this delay, the CPU keeps copies of recently used memory in **caches**. Caches are small, fast memories near the core. Here are the levels of a current workstation processor, the AMD Ryzen Threadripper PRO 9995WX (2025, 96 cores):

{: .grid-head }
| Level | Size | Shared by |
| --- | --- | --- |
| L1 data cache | 48 KB | one core |
| L2 cache | 1 MB | one core |
| L3 cache | 32 MB | the 8 cores of one chiplet |
| Main memory | up to terabytes, in 8 channels of DDR5 | all 96 cores |

The processor has 12 chiplets, so AMD lists its L3 cache as 384 MB. But each chiplet has its own 32 MB, and a core reads only that part fast. Data in the L3 cache of another chiplet come almost as slowly as data from memory. So a program that wants to stay in the L3 cache must stay within about 32 MB per group of 8 cores.

Our test machine is smaller. It is a virtual machine with 4 cores of an Intel Xeon Platinum 8558 (Emerald Rapids, 48 cores). Each core has an L1 data cache of 48 KB and an L2 cache of 2 MB. The L3 cache of 260 MB is shared by all 48 cores of the processor, and so also by the other virtual machines on it. All measurements in this chapter come from this machine.

Caches do not store single bytes. They store **cache lines** of 64 bytes. When you read one `int`, the 15 `int`s next to it come into the cache too, and reading them after that is almost free. (Chapter 17 used this to make a struct of arrays faster than an array of structs.)

How long does a load take? We measure it with an array `next` that forms one random cycle: `next[i]` is the place to read after place `i`. Every load needs the result of the load before it. So the loads cannot overlap, and the time of one step is the **latency** of one load:

```cpp
std::uint32_t at{};

for (std::size_t step = 0; step < steps; ++step)
    at = next[at];  // the address of this load is the result of the last one
```

A small array stays in the L1 cache. In a large array, almost every load goes to main memory. The figure shows the time per load for arrays from 16 KB to 1 GB:

{% include viz.html id="mem-latency" alt="A chart of the time per load against the size of the data, from 16 KB to 1 GB: the size on a log scale, the time on a linear scale from 0 to 250 ns, with bands for the L1 cache, the L2 cache, and the L3 cache and memory. The time stays under 10 ns up to 1 MB, then grows to 28 ns at 4 MB, 125 ns at 16 MB and 246 ns at 1 GB. A second curve for 2 MB pages is lower from 16 MB on, 180 ns at 1 GB; the area between the curves is shaded. A slider picks a size." %}

In the L1 cache a load takes 1.8 ns, and in the L2 cache 5 ns. At 4 MB it takes 28 ns. With more data, most loads go to main memory: 125 ns at 16 MB and 246 ns at 1 GB. The core runs at about 3 GHz, so a load from memory waits about 700 cycles. In that time the core could run thousands of instructions.

On our machine the L3 cache was fast only up to a few MB. It is shared with the other cores and the other virtual machines, so our program does not get all of it. Chapter 17 gave 80–100 ns for main memory: that is typical for a desktop computer when the TLB of the next section knows the address. A large server is slower, and random loads in a large array also miss the TLB.

The numbers are different on every machine, but the shape is always the same. Each level is several times larger and several times slower than the level before it. A program is fast when most of its loads come from the small levels.

## Pages and the TLB

The addresses that a program uses are **virtual**. The operating system divides memory into **pages** of 4 KB. A **page table** tells where each virtual page is in physical memory, so every load must translate its address. A walk through the page table would cost more loads (the table has four levels). So the core keeps recent translations in a small cache, the **TLB** (translation lookaside buffer).

The first level of the TLB has about 100 entries, and the second level about 2000. With pages of 4 KB, this covers 8 MB. A random load in a larger array usually misses the TLB too. Then the core must walk the page table before it can start the load. In a virtual machine such as ours, a TLB miss costs even more. The address goes through two page tables: the one of the virtual machine and the one of the real machine.

Linux can also use **huge pages** of 2 MB. One TLB entry then covers 512 times more memory, and the page table has one level less. With **transparent huge pages**, Linux does this automatically for large memory areas. Many systems, ours too, have the setting `madvise`: a program must ask for huge pages.

```cpp
void* p = std::aligned_alloc(2 << 20, bytes);  // bytes must be a multiple of 2 MB
madvise(p, bytes, MADV_HUGEPAGE);  // Linux: please use 2 MB pages here
```

The setting is in the file `/sys/kernel/mm/transparent_hugepage/enabled`. This week's class `Keys` (in `layout.hpp`) asks for huge pages when you give it `huge_pages = true`. The figure above shows the effect: for 1 GB of data, a load takes 180 ns instead of 246 ns.

Huge pages are not free. A 2 MB page must be 2 MB of free physical memory in one piece, so the system may have to move other pages to make one. Some databases avoid transparent huge pages: Redis turns them off for its own process, because they made its latency less predictable and its memory use larger. Other databases, such as PostgreSQL, can put their main memory area on huge pages.

## Many loads at once

Reading an array **in order** is much faster than reading it at random. We added up arrays of 32-bit numbers:

{: .grid-head }
| Array | 1 thread | 2 threads | 4 threads |
| --- | --- | --- | --- |
| 1 MB (in the L2 cache) | 27.4 GB/s | 53.9 GB/s | 91.3 GB/s |
| 16 MB | 19.4 GB/s | 39.8 GB/s | 67.1 GB/s |
| 256 MB | 7.6 GB/s | 13.4 GB/s | 23.8 GB/s |
| 1 GB | 8.0 GB/s | 14.1 GB/s | 25.6 GB/s |

One thread reads 1 GB at 8 GB/s: one cache line of 64 bytes every 8 ns. But one load from memory takes 246 ns! Both numbers are correct, because one core can wait for many cache lines at the same time. When the loads are independent, the core starts the next load before the first one arrives. Also, the **hardware prefetcher** sees that the program reads in order, and it asks for the next lines before the program does. **Little's law** connects the numbers: the amount of data on its way is the bandwidth times the latency,

$$8\ \text{GB/s} \times 246\ \text{ns} \approx 2000\ \text{bytes} \approx 30\ \text{cache lines}.$$

So one core keeps about 30 lines on their way. More threads keep more lines on their way: 4 threads read memory at 25.6 GB/s, 3.2 times faster than one thread. A loop that reads memory gets faster with more threads, until it reaches the bandwidth of the memory: a few hundred GB/s in a large server.

This is the main idea of the week: **latency is the enemy, and overlap is the cure.** A chain of loads where each address comes from the value before it is slow, because the core waits for each load. Linked lists, trees and binary search are such chains. The rest of the chapter makes searches that wait for fewer loads, and for several loads at a time.

## Counting cache misses

How do we compare algorithms when the data do not fit in the cache? Counting instructions does not predict the time. Counting **block transfers** does. The **I/O model** of Aggarwal and Vitter (1988) has a fast memory of size $$M$$ and a slow memory of any size. Data move between them in blocks of $$B$$ items, and the cost of an algorithm is the number of blocks that it moves. For a database, the slow memory is the disk and a block is a page of 4–16 KB. For us, the slow memory is main memory and a block is a cache line: $$B = 16$$ keys of 4 bytes.

In this model, a binary search over $$n$$ sorted keys costs about $$\log_2 (n/B)$$ transfers. Each step jumps far from the step before, except the last $$\log_2 B$$ steps, which stay inside one line. A search tree with $$B$$ keys in each node, so that a node is one block, costs only $$\log_{B+1} n$$ transfers. For $$n = 2^{27}$$ keys and $$B = 16$$:

$$\log_2 \frac{2^{27}}{16} = 23 \qquad\text{and}\qquad \log_{17} 2^{27} \approx 6.6.$$

That is the idea of the **B-tree**: a transfer brings a whole block, so let each block decide as much as it can. Database pages are much larger than cache lines, and the nodes of a database B-tree hold hundreds of keys. With 500 keys per node, three levels hold more than 100 million keys. Next week we build such a tree.

A **cache-oblivious** layout tries to be good for every block size at once, without knowing any of them (Frigo, Leiserson, Prokop and Ramachandran, 1999). The best-known example is the van Emde Boas layout of a search tree. It is elegant, but Khuong and Morin (2017) measured it, and the layouts of this chapter, made for 64-byte lines, were faster. So we do not use it.

## Binary search and branches

Before we change the layout, we must understand the search itself. `std::lower_bound` finds the first key that is not less than $$x$$. Inside, every step is an `if`: go left or go right. For a random $$x$$, the CPU cannot predict that branch. It guesses wrong half of the time, and each wrong guess costs about 15–20 cycles (chapter 17). A **branchless** binary search computes the step as a number instead. The compiler turns the multiplication by a `bool` into a conditional move (`cmov`). This is the baseline of this week (`baseline.cpp`):

```cpp
Key branchless_lower_bound(std::span<const Key> sorted, Key x) {
    if (sorted.empty())
        return none;

    const Key* base = sorted.data();
    std::size_t len = sorted.size();

    while (len > 1) {
        const std::size_t half = len / 2;
        base += (base[half - 1] < x) * half;  // a conditional move, not a branch
        len -= half;
    }

    return *base < x ? none : *base;
}
```

The branchless search is much faster for small arrays: 12.2 ns instead of 68.6 ns for $$2^{10}$$ keys. But for 512 MB of keys it is *slower*: 947 ns against 903 ns. Why? When the CPU guesses a branch, it continues **speculatively**: it starts the load of the next step before it knows whether the guess was right. Half of the guesses are right, so the branchy search often has its next load on the way early. A wrong guess costs little compared with a load from memory. The branchless search must wait for each load before it even knows the next address. For data in memory, overlapping loads is more important than avoiding wrong guesses. This explanation comes from Khuong and Morin, and the rest of the chapter follows their paper.

So we have two problems. Each step of the search is a load from memory, and the steps cannot overlap. The next sections attack both problems.

## The Eytzinger layout

All searches start with the same few keys: the middle key, then the key at a quarter or at three quarters, and so on. In a sorted array, each of these keys is in its own cache line, with 15 neighbours that the search does not need. What if we put them next to each other?

In 1590, Michael Eytzinger numbered the ancestors of a person like this: the person is 1, and the father of person $$k$$ is $$2k$$ and the mother is $$2k + 1$$. You know this numbering from binary heaps. We use it for the implicit search tree of a sorted array. The root, the middle key, goes to place 1. The children of the key at place $$k$$ go to places $$2k$$ and $$2k + 1$$. So the keys are stored in **breadth-first order**: the root, then the two keys of the second level, then the four keys of the third level, and so on.

The figure shows 15 keys in both layouts, with cache lines of 4 keys (a toy machine: real lines hold 16 keys). Move $$x$$ and follow a search:

{% include viz.html id="search-layouts" alt="A binary search tree of 15 keys above a row of 16 memory places, in cache lines of 4. A toggle switches between the sorted layout and the Eytzinger layout, and a slider sets x. Step by step the search walks down the tree, and the cache lines that it has read are marked. Dashed boxes mark the lines that hold the first two levels of the tree, which every search reads: three lines in the sorted layout, one line in the Eytzinger layout, where place 0 is unused. A side panel shows these counts, the answer so far and k in bits." %}

The search is the same tree walk in both layouts, but it reads different lines. In the Eytzinger layout the first 4 levels (15 keys) fill one line, and the first 20 levels (a million keys) fill 4 MB instead of 64 MB. So the caches hold 4 more levels of the tree, and every search finds more of its first steps there. (In the small figure, one search can read more lines in the Eytzinger layout. What counts is that the top levels need few lines, and all searches share them.)

The search is short, and it has no branch that depends on the keys:

```cpp
std::size_t k = 1;

while (k <= n)
    k = 2 * k + (e[k] < x);  // left: append a 0 bit to k, right: append a 1
```

The bits of $$k$$ are the path. After the leading 1, each step adds a 0 (left) or a 1 (right). When $$k$$ falls off the bottom of the tree, the answer is the key where the search went left for the last time: the smallest key $$\ge x$$ on the path. For example, $$k = 10111$$ in binary means: left, then right three times. The last left step was made at node $$1$$, the bits before that 0. In general: remove the trailing ones and then one zero. `std::countr_one` in `<bit>` counts the trailing ones. If the search never went left, no key is $$\ge x$$, and the bits that remain are 0. Put `none` at place 0, and the answer is correct without an extra test.

For arrays that fit in the caches, the Eytzinger search is fast: 33 ns for $$2^{16}$$ keys (256 KB), where `std::lower_bound` took 138 ns and the branchless search 52 ns.

## A static B+ tree

From the fifth level down, the Eytzinger search uses one key of each line that it loads. A **B-tree** uses the whole line. A node of 16 keys (64 bytes, one line) has 17 children. Then each line narrows the search to $$1/17$$ instead of $$1/2$$, and a search in $$2^{27}$$ keys reads 7 lines instead of 23.

A database B-tree changes with every insert (next week). Ours is **static**: we build it once from sorted keys, and we never change it. Then it needs no pointers. As in the Eytzinger layout, arithmetic gives the places of the children. The tree of this week (`layout.hpp`) is a **B+ tree**: all keys are in the leaves, and the nodes above them hold copies of keys that guide the search.

* Level 0 has the **leaves**: the sorted keys in nodes of 16, and then at least one `none` as padding. `none` is `INT32_MAX`, larger than every key.
* Above them, node $$t$$ of level $$j$$ has the children $$17t, 17t + 1, \dots, 17t + 16$$ of level $$j - 1$$, as far as they exist. Its key $$i$$ is the **largest key under child $$17t + i$$**, or `none` if that child does not exist.
* The top level has one node, the root. All levels are stored in one array, from the root down.

To search for $$x$$, count the keys of the node that are less than $$x$$. If the count is $$c$$, all keys under the children before child $$c$$ are less than $$x$$, and the largest key under child $$c$$ is not. So the answer is under child $$c$$. In the leaf, the count is the place of the answer.

{% include viz.html id="static-btree" alt="A static B+ tree with nodes of 4 keys and 5 children over 30 keys in 8 leaves, padded with infinity. A slider sets x. Step by step the search compares x with all keys of a node at once; the rows below the tree show the keys, the results of the compare, and their count, which is the child to follow, and in the leaf the place of the answer." %}

For $$2^{27}$$ keys the tree has 7 levels: 8,388,609 leaves, and 524,291 nodes above them. The upper levels take only 6 % more memory than the keys, and the top four of them (116 KB) stay in the cache. Sergey Slotin, who studied this layout in detail, calls it an **S+ tree**.

## SIMD: a node in one compare

How do we count the keys of a node that are less than $$x$$? A loop with 16 compares would be slow. But counting is a perfect job for SIMD. AVX2 compares 8 `int`s in one instruction. `_mm256_cmpgt_epi32(a, b)` sets all 32 bits of a lane to 1 where $$a > b$$, and to 0 elsewhere. `_mm256_movemask_ps` collects the top bit of each lane into an ordinary integer of 8 bits, and `std::popcount` counts its ones. For the first 8 keys of a node:

```cpp
const __m256i xs = _mm256_set1_epi32(x);  // x in all 8 lanes
const __m256i keys = _mm256_load_si256(reinterpret_cast<const __m256i*>(node));
const __m256i less = _mm256_cmpgt_epi32(xs, keys);  // all ones where key < x
const auto bits = static_cast<unsigned>(_mm256_movemask_ps(_mm256_castsi256_ps(less)));
const int count = std::popcount(bits);  // the number of keys < x among the 8
```

`_mm256_castsi256_ps` only changes the type, from integers to floats, because the movemask instruction that we need is defined for floats. It costs nothing. The load can be aligned (`load`, not `loadu`), because each node starts at a cache line. Our keys are signed `int32_t`, and `cmpgt` compares signed numbers, so the result is correct. Next week's keys are unsigned, and we will need a trick.

Two such compares do a whole node, and there is no branch on the keys at all. The CPU never guesses wrong, and each level costs one load and a few instructions. With AVX-512, `_mm512_cmplt_epi32_mask(keys, xs)` compares all 16 keys at once. It returns the result directly as 16 bits in a mask register (a `__mmask16`): one compare per node.

## Prefetching

The B+ tree reads 7 lines for a search in 512 MB. But it still reads them one after another: the next node is known only when the current node arrives. Can one search wait for several lines at the same time? In the Eytzinger layout it can, because of one more property of that layout.

The descendants of node $$k$$ four levels down are the 16 nodes $$16k, 16k + 1, \dots, 16k + 15$$, next to each other in memory. If the array starts at a cache line, with place 0 first, these 16 keys are exactly one cache line. So at node $$k$$, the search can ask for the line where it will be four steps later. It does not yet know which of the 16 keys it will need, but it knows that all of them are in that one line.

`__builtin_prefetch(address)` (GCC and Clang) asks the CPU to start loading the cache line of `address`, and continues without waiting. It is only a hint: it never causes an error, also for an address outside the array. Here it is in a loop that adds up values from random places. Each place is prefetched 8 rounds before it is needed:

```cpp
for (std::size_t j = 0; j < idx.size(); ++j) {
    if (j + 8 < idx.size())
        __builtin_prefetch(&data[idx[j + 8]]);

    sum += data[idx[j]];
}
```

In the Eytzinger search, the prefetch at node $$k$$ asks for the line of node $$16k$$:

{% include viz.html id="prefetch-lines" alt="An Eytzinger array of 64 places in four cache lines of 16, with the levels of the tree marked above it. A slider sets x. Step by step a search walks down the array; at each of its first nodes it asks for the cache line four levels below, drawn as an arrow, and when the search arrives there, the line is already loaded." %}

With prefetching, up to four loads of one search are on their way at the same time. The price is bandwidth: the search loads 16 keys to use one of them. But one search uses only a few GB/s, far less than the memory can give. For $$2^{27}$$ keys the search took 299 ns instead of 842 ns: 2.8 times faster. For small arrays it is slower (26 ns instead of 16 ns for $$2^{13}$$ keys): the data are in the cache anyway, and the prefetches are extra work.

Near the bottom of the tree, $$16k$$ is past the end of the array. The prefetch does not mind, but C++ does: making a pointer past the end of an array is undefined behaviour, also if nobody reads it. Compute such addresses as integers (`std::uintptr_t`), and turn them into a pointer only for the prefetch.

## Threads: waiting together

A search in the B+ tree of 512 MB spends most of its time waiting for memory. While one core waits, the other cores can wait too, for their own searches. The searches are independent and only read the tree. So they run in parallel without any care: put `#pragma omp parallel for` before the loop over the queries, and let each thread write the results of its own queries. In the benchmark of task 7, the searches took 200 ns each on one thread, 87 ns on two threads and 56 ns on four: 3.6 times faster on 4 cores.

That is better than the speedup of reading memory in order (3.2 times, above). Reading in order is limited by the bandwidth of the memory, but the searches use little bandwidth. Each new thread adds its own waiting loads, and the memory has room for them. The figure compares four kinds of work on 1, 2 and 4 threads:

## First touch and NUMA

Threads made the searches faster. Can they also make the building of the tree faster? Yes, but first we must know where memory comes from.

`new` and `malloc` of a large block do not give physical memory. They give *virtual* addresses, and the operating system finds a physical page only when the program writes to it for the first time. The first write causes a **page fault**: the kernel takes a free page, fills it with zeros, maps it, and then lets the write continue. This happens in the thread that touches the page first, and it takes time. On our machine, creating a zero-filled `std::vector` of 544 MB took 294 ms: about 2 µs for each 4 KB page.

A large server has two or more processors (**sockets**), and each socket has its own memory. Every core can read all of the memory, but the memory of the other socket is slower to reach. Its loads go through the link between the sockets, and they all share that link. This is called **NUMA**, non-uniform memory access. (The chiplets of the Threadripper above are a smaller version of the same idea.) Linux places a page in the memory of the socket whose core touches it first. This is the **first-touch** rule:

{% include viz.html id="first-touch" alt="Two sockets, each with two threads and its own memory, and an array of 16 pages. A toggle chooses whether one thread or all four threads write the array first. Each page appears in the memory of the socket whose thread touched it first. Then the threads read their halves of the array: with one writer, the threads of socket 1 read every page from the other socket." %}

The classic mistake is to create an array in one thread and then work on it with many threads. `std::vector<int> v(n)` writes zeros to all of it in the thread that creates it. So every page lands in the memory of one socket, and one thread pays for all the page faults. The cure: allocate without writing, and let each thread write its own part first, with the same `schedule(static)` that later reads it. In C++, `std::make_unique_for_overwrite<int[]>(n)` (C++20) allocates an array without writing to it. The class `Keys` does the same, with an alignment.

Building the static B+ tree of 512 MB this way took 417 ms with one thread, 215 ms with two and 145 ms with four: 2.9 times faster. Our test machine has one socket, so it shows only half of the story: there, the gain is the page faults in parallel. On a machine with two sockets, the place of the pages matters as well. `numactl --hardware` shows the memory nodes of a machine. `numactl --interleave=all ./program` spreads the pages of a program over all nodes, a quick fix for programs that you cannot change.

## Bonus: eight searches in one register

A search waits for one load at each step. Prefetching (task 6) and threads (task 7) overlap the loads of one search or of many searches. There is a third way, and it needs only one thread and no prefetch: run 8 searches in the 8 lanes of an AVX2 register. AVX2 has a **gather** instruction: `_mm256_i32gather_epi32(base, index, 4)` loads 8 `int`s from 8 independent addresses `base[index[i]]`. So one step of 8 searches is one gather, and the 8 loads are on their way at the same time.

The lanes must take the same number of steps. Pad the Eytzinger array up to $$2^h - 1$$ places with `INT32_MIN`. At a padded place every search goes right, and right steps at the end do not change the answer: the answer removes the trailing ones of $$k$$ anyway. Keep `none` (`INT32_MAX`) at place 0.

```cpp
// Lower bounds of 8 queries. e[0] is none (INT32_MAX); e[1 ... 2^h - 1] holds
// the keys in Eytzinger order, padded with INT32_MIN.
__m256i eytzinger_search8(const std::int32_t* e, int h, __m256i x) {
    const __m256i one = _mm256_set1_epi32(1);
    __m256i k = one;

    for (int step = 0; step < h; ++step) {
        const __m256i key = _mm256_i32gather_epi32(e, k, 4);  // 8 loads in one instruction
        const __m256i right = _mm256_and_si256(_mm256_cmpgt_epi32(x, key), one);  // e[k] < x
        k = _mm256_add_epi32(_mm256_add_epi32(k, k), right);  // k = 2k + (e[k] < x)
    }

    return k;  // the answer of lane i is e[k_i >> (countr_one(k_i) + 1)]
}
```

AVX2 has no instruction that counts trailing ones in each lane, so the last step is a loop over the 8 lanes in ordinary code. For 32.5 million keys (128 MB), one search after another took 548 ns per query on our machine. Eight searches in the lanes took 234 ns per query: 2.3 times faster, with one thread. The gather is not faster than 8 single loads, but it keeps 8 loads in flight without a branch.

Bonus exercise (no points): add a prefetch four levels down to each lane, as in task 6. There is no prefetch-gather in AVX2, so you need 8 `__builtin_prefetch` calls per step. Does it help? Then compare with 16 searches in two registers, with their steps interleaved.
